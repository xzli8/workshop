\datedsubsection{\textbf{Bnto AI Shopping Assistant Maya (0 $\rightarrow$ 1)}}{Sole Owner}

\textbf{Project Background}: Maya is the AI-agent shopping assistant of Bnto, a US fashion rental and resale e-commerce platform. It handles three kinds of conversations: finding items and outfits, checking subscriptions and orders, and asking about platform policies. LLMs are probabilistic, stateless, speak natural language, and are slow and expensive. Turning one into a reliable production component means: control flow and terminal states cannot be left to the model; outputs must be structured and validated; context must be reassembled by code within a token budget; high-risk actions require human approval; quality must be measured and regression-tested with eval datasets. Built from scratch in Python (FastAPI) on LangGraph in three months.\\

\textbf{Key Responsibilities}: Sole designer and implementer. Built a minimal end-to-end single-agent skeleton, then the eval system, then function calling (with human approval), memory and RAG, each gated by eval datasets; then split by domain behind a Router, upgraded to manager-style multi-agent for cross-domain questions.\\

\begin{itemize}
    \item \textbf{Orchestration: a main agent coordinates, sub-agents own their domains.} The main agent calls the Fashion, Account and FAQ sub-agents as tools (manager pattern): in parallel and merged for cross-domain questions, passed straight through for a single domain. FAQ is a fixed retrieve $\rightarrow$ rerank $\rightarrow$ answer chain; Fashion and Account are ReAct agents. All model outputs are structured; terminal states are guaranteed by types, and abnormal exits fall back to code.
    \item \textbf{Function Calling: the model decides, code constrains.} Business capabilities (item search, subscription, orders, receipts, FAQ) and third-party services such as weather are wrapped as agent-callable tools; the Fashion and Account agents choose and combine them, and code constrains them at three points. Arguments: search criteria are vocabulary-normalized and contract-validated; zero results go back to the model to relax them. Identity: user\_id is injected by code and never visible to the model. High-risk actions: execution is suspended with LangGraph interrupt and the state persisted in a Postgres checkpointer; after the user approves, the exact call frozen in the checkpoint resumes, after verifying ownership and pending-approval state to block privilege escalation and duplicate execution. The same tools are also served as an MCP server (server-side identity, high-risk actions confirmed via elicitation) for external agents.
    \item \textbf{Memory \& RAG: hybrid recall, budgeted truncation.} The conversation window is truncated by token budget; turns beyond it are incrementally summarized and recalled through vector + keyword retrieval fused with RRF. FAQ hybrid search takes 10 candidates, an LLM reranker keeps the top 5, and answers cite only passage IDs given to the model.
    \item \textbf{Eval-driven: layered datasets, baseline comparison.} 10 LangSmith datasets (760 cases) across unit, chain and end-to-end levels, all evaluators in code and reproducible. Model decisions are evaluated with external dependencies faked; result quality is evaluated against real services. Every change is run several times and compared with the pre-change code to separate noise from regression.
    \item \textbf{Results: 98\% eval pass rate, seconds-level latency, half a cent per turn.} Account tool selection and facts 79/80; human approval and execution count 40/40 (passed three repeated runs); FAQ retrieval hit 147/150 (vector-only 134/150); intent classification 148/150; long context 30/30 (window-only 9/30); Fashion criteria extraction 98/100, tool decisions 49/50; terminal-state completeness 50/50. Measured P99 about 5.7s per turn (at least two LLM calls, progress streamed over SSE); average cost about \$0.005 per turn (85\% prompt cache hit rate).
\end{itemize}

\datedsubsection{\textbf{Bnto Recommendation Serving Platform (0 $\rightarrow$ 1)}}{Technical Leader}

\textbf{Project Background}: Bnto, a US fashion rental and resale e-commerce platform, had no recommendation system before this project: product listing pages (PLP) used fixed ordering and the home page had no feed. The algorithm team was building recall and ranking models from scratch in parallel, so engineering needed a serving platform that could host them without being blocked by their schedule. Launched in three months across three scenes (PLP, Feed, product drill-down) over about 8k products, serving hundreds of thousands of daily requests.\\

\textbf{Key Responsibilities}: Technical leader of two engineers, collaborating with two algorithm engineers. Owned industry research, HLD/LLD, the main pipeline, state layer and experiment framework, and blending and survey-card integration, delivered in four steps (end-to-end skeleton $\rightarrow$ experiment framework $\rightarrow$ state layer $\rightarrow$ algorithm ranking). One engineer built the feature data link (client tracking $\rightarrow$ Kafka $\rightarrow$ ClickHouse/Flink), the other the survey-card targeting, frequency control and submission loop.\\

\begin{itemize}
    \item \textbf{Contract: defining the engineering/algorithm boundary.} Rank requests carry candidate identity only (type + id + recall sources); the algorithm fetches its own features by key, keeping training and serving consistent. Recall stays on the engineering side, and algorithm output enters the recall index as offline artifacts. Both sides iterate independently without affecting each other.
    \item \textbf{Pipeline: fixed orchestration, pluggable strategies.} Parallel multi-route recall (per-route timeout and thread-pool isolation, failed routes skipped, merge and dedup by type + id with recall sources unioned, served/exposure-history filtering) $\rightarrow$ model ranking (RPC to the algorithm, falling back to recall order on timeout or failure) $\rightarrow$ re-rank policy chain $\rightarrow$ blending (slot planning, quotas, masonry height ledger) $\rightarrow$ batched per-type fill (unfillable items dropped). A new recall route, policy or card type is one class plus one registration line, with zero changes to the main pipeline.
    \item \textbf{State layer: compute once, reuse across pages.} The first request runs the full pipeline and caches the whole batch (the full ordered type + id list before pagination plus the experiment-group snapshot); paging within the batch slices the cache by cursor without re-running the pipeline. Dedup is layered by memory span (in-batch merge, in-session served, cross-session exposed) and applied once after the recall merge. Every layer has a degradation path (invalid cursor treated as a miss and rebuilt, cache down runs the full pipeline, dedup down relaxes), so a state-layer failure only costs dedup and caching.
    \item \textbf{Experiments \& data: frozen at entry, returned untouched.} Experiments: assignment and eligibility are decided once at the entry and frozen with the batch, so paging never switches groups; strategies hang on fixed decision points; code only registers strategies and experiment config maps groups to strategies, so a new experiment needs no release; the assignment rule can be swapped for an external experimentation platform. Attribution: exp\_group travels with each card, returns untouched with every tracking event, and effects are compared per group. Data: client events are written once to Kafka and consumed three ways: ClickHouse keeps the detail for T+1 offline features and per-group analysis, Flink aggregates in-session behavior into real-time features read at ranking time, and exposure events flow back for cross-session dedup.
    \item \textbf{Results: CTR +18\%, new cards live in 2 days.} The first A/B test (model ranking vs recall order) lifted product-card CTR by 18\% and add-to-cart rate by 11\%; first-page full-pipeline P99 about 200ms, paging P99 under 50ms, page success rate 99.99\%. In the first month after launch, three card types (brand, collection, survey) and three re-rank policies (brand/category scatter, source segmentation, drill-down path exclusion) shipped at about 2 days each.
\end{itemize}

\datedsubsection{\textbf{Meituan Healthcare BFF Evolution: Hardcoded $\rightarrow$ DAG $\rightarrow$ GraphQL}}{Project Leader}

\textbf{Project Background}: The Meituan Healthcare User API is the single entry point for all consumer-facing healthcare requests. It aggregates, orchestrates and shapes the capabilities of dozens of domain services for the front end (the BFF, Backend For Frontend, layer), deployed across 5 sets with 50 machines in total and serving peak traffic of about 5k QPS. Its original hardcoded implementation could no longer keep up as the business and its scenarios grew; this six-month project rebuilt it in three phases into a new architecture of Units, DAG scheduling and a GraphQL contract.\\

\textbf{Key Responsibilities}: Project leader of five engineers. Owned the upfront research, the three-phase plan, the overall design and project management, and personally implemented the Phase 3 integration of GraphQL with the DAG engine. Migrated with traffic comparison throughout: the legacy service forwarded each request to the new one and logged every mismatch; traffic switched only after mismatches reached zero, so users always got the legacy result.\\

\begin{itemize}
    \item \textbf{Phase 1: Tackling the hardest problems} (goal: stop the bleeding at low cost; optimal not required)\\
    \textbf{Problem}: aggregation logic was organized by page with no reusable unit beneath it, so the same business rules, fault handling and timeouts were reimplemented per page and drifted apart; each page's parallel structure was derived from its dependencies by hand.\\
    \textbf{Solution}: split the aggregation logic into reusable batch-style logic units (Units), build a layered parallel scheduling engine, and make orchestration configuration-driven.\\
    \textbf{Actions}: defined Units behind a uniform batch interface with built-in dependency declaration, per-unit timeout, strong/weak dependency and fallback value, with thread pools isolated per downstream service; the engine layers Units by dependency with Kahn's algorithm (parallel within a layer, sequential across layers) and validates cycles and unregistered Units at load time; page configuration lists only the Units it needs and the engine fills in intermediate dependencies.\\
    \textbf{Result}: one implementation per piece of logic; development efficiency up about 30\% (by average requirement lead time).
    \item \textbf{Phase 2: Building general capabilities} (goal: fix the known gaps of Phase 1 and build the best current solution)\\
    \textbf{Problem}: the layered model had barriers between layers, so total latency was the sum of each layer's slowest Unit rather than the critical path.\\
    \textbf{Solution}: a DAG-based scheduling engine in which each Unit waits only on its own predecessors and fires as soon as they complete.\\
    \textbf{Actions}: built the DAG scheduling engine (CAS-driven node state machine, predecessor counting); failures propagate along edges, so a strong-dependency failure skips only its downstream subgraph while sibling branches continue; the request-level deadline is pushed down into every Unit's RPC timeout; node-level tracing outputs the request timeline; configuration gained per-page strong/weak and timeout overrides and conditional inclusion. Units and page configurations were untouched, and both engine generations consume the same dependency graph.\\
    \textbf{Result}: core interface P99 down 30-40\% on average.
    \item \textbf{Phase 3: Pushing the capability limit} (goal: remove the architectural coupling between front end and back end)\\
    \textbf{Problem}: response shape was fixed at design time in configuration, one per client per page, so every client difference or shape change needed a backend release; data capability was coupled to response shape.\\
    \textbf{Solution}: introduce GraphQL with the schema as the front-end/back-end contract, moving the decision on response shape from design time to front-end request time; the schema owns shape, the DAG owns data fetching.\\
    \textbf{Actions}: implemented query analysis that maps selected fields to a Unit subgraph with transitive dependencies for the DAG engine, so unselected Units never run; fetchers read a request-scoped result store and Unit data flows only along dependency edges (indexed by producer, written once, read by dependency), eliminating shared-context bloat; parse, validation and query-analysis results are cached by query hash, with a persisted-query allow-list and depth/complexity limits. Rejected the DataLoader + level-dispatch route: it fixes only hanging loads, not barriers or cross-branch dependencies.\\
    \textbf{Result}: field changes, multi-client differences and new pages are all handled on the query side without backend releases, a further about 20\% gain in development efficiency; backend page configurations dropped to zero; performance unchanged.
\end{itemize}

\datedsubsection{\textbf{Amazon Vendor Account Management System Global Expansion}}{Core Developer}

\textbf{Project Background}: VAMOS is Amazon's vendor account management system, launched in Japan and then expanded to the EU, Brazil, Mexico and more. My team owned the platform: the multi-tenant service framework and core front-end interactions on which each marketplace's business team built its own logic.\\

\begin{itemize}
    \item \textbf{Performance: batch fetch, in-memory aggregation.} After the EU launch of the per-dimension summary view, the API timed out persistently. Logs, metrics and distributed tracing showed the EU had far more dimensions than Japan, and calling downstream once per dimension multiplied RPC volume and exhausted the thread pool. Enlarged the thread pool to keep the launch on schedule, then switched to a single batched RPC with in-memory aggregation, cutting downstream calls from dozens or hundreds to one and eliminating the timeouts; the approach became a framework capability reused by later marketplaces.
    \item \textbf{Multi-tenancy: marketplace as tenant, isolated at three layers.} Data is sharded by marketplace into separate databases and tables, and configuration and deployment are independent per marketplace; business teams implement their own logic on one shared framework.
    \item \textbf{Multi-marketplace front end: core first, iterate fast.} Built the marketplace filter widget; the PM/UX proposal with filter templates and search history was estimated at 10 person-days; shipped marketplace switching and precise filtering first with extension points reserved, in 4 person-days to keep the launch on schedule, and completed the full interaction within a week.
\end{itemize}
