0 总览

两分钟版本

BNTO 之前没有推荐系统，我负责工程侧从零搭建，带两个人，和算法两人协作，三个月上线。先定契约：工程和算法之间只传商品身份和命中的召回源，特征算法自己按 key 取，召回留在工程侧，算法以离线产物进召回索引。两侧独立迭代，互不影响。主链路编排固定、策略可插拔：多路并行召回、算法模型排序、重排策略链、混排、按 type 填充五段。状态层是 cursor 加 cache 加三层去重，batch 内翻页不重跑上游，状态层故障页面永远有降级兜底。实验是扁平模型、入口一次判定冻结、固定分流点，exp_group 随卡片下发、随埋点回流，在 ClickHouse 里按组算效果；同一份事件另一路经 Flink 聚合成实时特征写进 Redis，排序请求期读。上线后首个实验商品卡点击率提升 18%，首页全链路 TP99 约 200 毫秒，页面成功率 99.99%，新增一类卡片或一条策略平均两天上线。

BNTO 是美国时尚租赁电商。项目开始前没有推荐：PLP 按固定规则排序，首页没有信息流。算法团队同期从零起步做召回和排序模型，工程侧需要一套能承接算法、又不被算法进度绑住的推荐服务。项目产出四样东西，和简历的四条一一对应：一份工程与算法之间的契约；一条编排固定、策略可插拔的主链路；一个由 cursor 和 cache 组成、任何故障下页面都有降级兜底的状态层；一套从分流、归因到数据回流的实验闭环。

0.1 四个子系统，各解决一个问题

子系统解决的问题关键决策节
契约工程和算法各管什么，接口怎么定才两边都能独立演进只传身份（type + id + source），特征不过线，召回归工程1
主链路召回、排序、重排、混排、填充怎么编排，新策略怎么加编排固定，策略可插拔；硬过滤归召回源2
状态层无限流怎么翻页、怎么不重复、存储挂了怎么办cursor + cache，三层去重，每层状态有降级路径3
实验归因与数据闭环怎么分流、怎么归因、算法拿什么训练、实验拿什么算效果扁平实验，入口一次判定冻结，固定分流点；exp_group 随卡片下发随埋点回流；一份事件三路消费：ClickHouse 离线特征、Flink 实时特征、曝光历史4

0.2 三条设计原则

  • 编排固定，策略可插拔。主链路的顺序写死在代码里，每个阶段是一个接口加若干实现。新增一路召回、一条重排策略、一种卡片，是加一个类和一行注册，不动主链路。
  • 身份传递。链路上流动的候选只有 type + id 和命中的召回源，展示数据在最后一步按页填充。算法看不到展示数据，工程看不到特征。
  • 页面永远有降级兜底。每个外部依赖都有降级路径：召回单路失败跳过，排序超时回落召回原序，Redis 任何一层挂只损失去重和缓存，卡片填不出就丢。

1 契约：工程与算法的边界

1.1 三句话边界

两个团队同时从零起步，先定边界再各自开工。边界定在三句话上。

约定内容为什么
只传身份加召回源排序请求 = requestId、scene、exp_group、userId/deviceId、candidates[(type, id, sources)]；响应 = 有序 [(type, id, score)] + modelVersion展示数据算法不需要，特征工程不该有。请求体只有身份，几 KB
特征不过线算法按 userId/itemId 自取特征，工程不组装、不透传特征训练和服务读同一份特征，保证一致性；工程不随特征迭代发版
召回归工程索引是基建，候选集是资格控制（在售、可租、场景池），算法的召回模型以离线产物写入索引，由工程侧 Recaller 读可售与否、场景约束是业务规则，归工程；算法只管"像不像"，不管"能不能卖"

1.2 召回索引

索引是召回路读的物理存储，归工程持有。算法离线算好的东西写进去，线上召回是工程查表，算法不在请求路径上。

存储放什么谁写谁读
OpenSearch 商品索引商品倒排字段（在售、品类、品牌、价格）；kNN 向量字段：商品向量、图片向量商品同步写倒排；算法离线写向量全量池、场景池、相似品 Recaller
Redisi2i 邻居表（item_cf 算出的每个商品的相似商品列表）、用户向量、热门与新品有序列表、搜索历史算法离线批任务；热门由定时任务刷新算法召回路、兜底级、搜索历史 Recaller
MySQL 与配置运营位、货盘、问卷池运营后台运营位 Recaller、Blender 供给方

"算法以离线产物进入召回索引"落到具体就是：item_cf 的邻居表和向量由算法每日离线算好，写进 Redis 和 OpenSearch；线上算法召回路按用户最近行为过的商品查邻居表、按用户向量查 kNN，取并集交给排序。算法迭代召回模型只换表里的内容，不换工程代码。

命中的召回源 sources 只在服务端内部流转，不下发客户端。

备选与取舍

特征随请求过线。否决：工程要维护一份特征组装逻辑，算法每加一个特征工程就发一次版，训练用的特征和线上传的特征两个来源，一致性靠人。召回也交给算法。否决：可售、库存、场景池这些资格规则是业务侧的，放算法侧等于算法要理解业务规则的每次变化。算法直接出页面。否决：分页、去重、混排、卡片填充都是工程问题，算法服务不该有 Redis 和商品库依赖。

面试追问

算法换模型，工程改什么？
不改。契约里 modelVersion 随响应返回，写进日志和埋点。模型迭代是算法侧发版，工程侧的 Ranker 实现只有一个 RPC 客户端。
算法要一个新特征，比如用户最近浏览，怎么给？
不经过工程。长期行为在 ClickHouse 里，算法离线算特征进自己的特征存储；当前 session 的行为由 Flink 聚合成实时特征写进 Redis，两者线上都按 userId 取。工程侧的义务是把两条回流做稳，见 4.3。

2 主链路

2.1 五个阶段

Context ─► recall：Recaller × N 并行 ─► 合并 ─► 去重过滤 ─► rank：Ranker N 选 1 ─► rerank：RerankPolicy 链 ─► blend：Blender ─► 写缓存 ─► 切片 ─► fill：Assembler

五个阶段的顺序固定，每个阶段一个接口、若干实现；缓存与切片属于状态层，见 3。

阶段角色机制
Context一次请求的全部输入，入口构建后只读deviceId 必传，登录加传 userId；scene 由端点决定；requestId 入口生成；实验分组入口一次盖章冻结
recall（Recaller）一路召回，对场景无感知场景到召回路的映射在注册表里；全部并行，每路独立超时与线程池隔离，单路失败跳过；合并按 type + id 去重，sources 取并集；硬过滤（可售、在架）归召回源，在每路返回后立即做；去重过滤（下发历史、曝光历史）在合并后、进 Ranker 前做一次，见 3。现有：算法召回、搜索历史、相似品、下钻同款
rank（Ranker）决定顺序，N 个实现选 1由分流点决定用哪个，见 4.1；RPC 调算法；超时或失败回落到召回原序
rerank（RerankPolicy 链）确定性业务规则，链式，按 order 执行每条声明支持的场景。现有：礼品卡剔除、品牌与品类打散、来源分段、下钻剔除当前商品
blend（Blender）把非商品卡插进商品流，仅 Feed见 2.2
fill（Assembler）按 type 批量填充展示数据同类卡片一次批量查询，填不出即丢；type 间串行，一页的数据量不值得并行

硬过滤归召回源。不可售的候选进了链路，去重、排序、切 batch 都在为不能展示的东西干活，切 batch 时还会挤掉能卖的。上线第一周 Feed 被清空就是这个原因，见第 5 节。规则：谁产出候选，谁保证候选可展示；主链路不加兜底过滤。

打散是滑动窗口贪心。在排序结果上按窗口大小 W 内同品牌至多 K 个、同品类至多 G 个逐位选取，不满足就向后找第一个满足的候选换上来，找不到按优先级放宽约束。作用范围 scatter_size 是独立配置，不等于 batch 大小：默认等于 batch 大小时，头部堆积的同品牌商品会被推到 batch 尾部集中出现，放大到全列表才是有效的。

2.2 混排与问卷卡接入

Feed 里除商品卡还有品牌卡、合集卡、问卷卡、堆叠卡。非商品卡不进 Ranker，目标不可比，走独立的混排层。

  • PositionPlanner 决定位置。输入排序后商品数和场景规则，输出可插入的位置列表：首屏保留位、每类卡片的配额、密度红线（每 N 张商品卡至多一张插卡）。
  • Supplier 决定内容。每类卡片一个供给方，返回候选卡；选型器按配额和去重键挑。品牌和合集来自运营配置的货盘，问卷来自 SurveyManager。
  • ColumnLedger 管瀑布流对齐。双列瀑布流里宽卡要两列齐平才能插，服务端按卡片样式的常量高度记两列账，插宽卡前用窄卡补齐高度差，补不齐降级为窄卡或顺延。
  • 失败降级。任何供给方失败，这一页只出商品卡。

问卷卡的边界。SurveyManager 是独立闭环：问卷池由运营配置，谁能看（定向）、看多少（采样率）、看过不再看（去重加冷却期）、每天多少张（配额）都在它里面，状态在 Redis。主链路侧只有一个 SurveySupplier，问它"这个用户当前该出哪张"，拿到一张或空。三处接入点：

  • 常规插卡：Blender 按配额向 SurveySupplier 要卡。
  • Tune Feed 触发卡：客户端检测到连续 X 次曝光无交互，上报一次即忘；服务端把意图记进 cursor 的标志位，下一次能插的位置出一张风格问卷卡，每 session 至多一张，出卡前客户端刷新则意图随 cursor 丢弃。状态在 cursor 里而不是 Redis，是因为它的生命周期恰好等于一条 cursor 链。
  • 提交后立刻生效：问卷提交事务完成后发进程内事件，监听者失效该设备的 Feed batch 缓存，下一页走全链路重建，算法请求期读到新答案。不做异步重建覆盖，因为 cursor 里的 offset 是相对当前 batch 的，覆盖会让客户端的 offset 落到新 batch 上丢掉前面的内容。
备选与取舍

非商品卡进 Ranker 统一排序。否决：问卷的目标是收集偏好，品牌卡的目标是导流，和商品的转化目标不可比，业内一致做法是独立混排层。重排和混排合并成一层。否决：重排作用在商品序上、趋向模型化；混排作用在坑位上、趋向运营策略化，两者演进方向不同，只共享未来的规则配置平台。Recaller 和 Assembler 共享并行框架。否决：表面都是扇出，失败、超时、合并语义全不同，共享只会得到参数汤。

面试追问

召回路挂了怎么兜底？踩过什么坑？

坑：兜底当成一路召回并行跑。第一版把全量商品池 Recaller 和其他路并行，合并时对等去重。结果其他路只召一部分、算法只需排这一部分的前提被抹掉：合并集合变成整个商品池，排序候选从几百涨到 8k，排序耗时涨、模型在它没学过的长尾上打分，正常请求也被污染。传 source 给算法不能治这个，那解决的是排序质量，不是数量。

解法：兜底是合并环节的补足策略，不是一路召回。召回分两级：主路并行；合并后若全部主路失败或合并数少于阈值，兜底级出"目标数减已有数"个候选，排除已有 id，打 source = fallback。兜底源是 Redis 里定时刷新的热门或新品有序列表，毫秒级，可以并行发起、合并时再决定用不用。兜底候选不进 Ranker，按热度直接接在主路结果后面；进了也由来源分段策略保证在主路段之后。用了兜底的 batch 标记 degraded：缓存 TTL 缩短，日志留痕，实验分析剔除。PLP 不兜底，全池快照供给不足就是真的没货。

业界叫分级召回加配额补足：主路个性化，兜底级预计算热门，下一级只填上一级的缺口。source 作为排序特征是另一件事，标准做法，但目的是提质量。

新增一路召回要改什么？
一个实现类加注册表一行。要做实验就不进默认名单，由实验配置指定名单，与注册全集取交集生效，胜出后改默认名单撤配置。
排序超时回落召回原序，用户会感知吗？
会变差但不会失败，且 exp_group 照常下发，事后能从 modelVersion 为空的比例知道降级量。超时设在算法 TP99 之上，正常情况不触发。
为什么 Assembler 串行？
一页 20 张卡最多三四种 type，每种一次批量查询十几毫秒。性能来源是按 type 批量，不是 type 间并行。

3 状态层：cursor + cache

状态层是 cursor 和 cache 的组合：首次请求跑全链路生成一个 batch 整体缓存，batch 内翻页按 cursor 查 cache 切片下发；去重和降级围绕这两样展开。

PLP 和 Feed 都是无限流加 cursor 分页，同一套机制两种参数：PLP 单 batch 快照翻到尾 nextCursor 为空，Feed 多 batch 链式，翻到尾同步生成下一 batch。

3.1 cursor

不透明、版本化、base64url，载荷 v1:offset:blendState:flags，客户端原样回传。解析失败、伪造、版本不符一律视为缓存 miss，重建 batch 从头返回，页面不报错。选择自定义而不复用仓库里明文 xxx_20 的 cursor 约定，因为后者解析失败会抛异常，且需要在 cursor 里藏 batch 标识和混排状态。

3.2 batch 缓存

Redis kv，key = deviceId + scene，value = 分页前全量有序 [(type, id)] 加实验分组快照，固定 TTL 30 分钟，写一次不续期。翻页命中缓存直接切片，不重跑召回到混排。快路径下发的 exp_group 取快照而不是 Context 现值：ramp 期间用户可能换组，而这条 batch 是按旧组生成的。

3.3 三层去重

层回答的问题结构过期
batch 内多路召回同一商品合并时按 type + id随 batch
session 内流里会不会重复下发历史，Redis SET，key = deviceId + scene，每页返回前写入实际下发的 id滑动 TTL，每次写入重置，时长等于 batch 缓存 TTL；session 是导出概念，没有实体
跨 session用户是否真看过曝光历史，Redis ZSET，user 维度，member = type + id，score = 曝光时间戳，由埋点回流异步写入固定窗口 7 天，写入时按 score 裁剪，key TTL 随写入重置

两个过滤都在合并后、进 Ranker 前做一次：不为要剔除的候选付排序成本，也不在混排后剔除破坏坑位。session 层记下发而不记曝光：客户端有预取缓冲，曝光回流有秒级延迟，赶不上补给；误伤限于一个 TTL 窗口，且曝光层不记未曝光的，自愈。PLP 免除跨 session 去重，查询结果要求完整。

存储选型

结论：两层都用精确结构。曝光历史原设计是 Bloom Filter 加分代轮换过期。推翻的理由是商品池约 8k 有界，一个用户的曝光集合最多几千个 id，BF 两个数量级的内存优势失去前提，而 1% 误判在小池子里等于藏掉约 80 件商品。回切触发：商品池涨一到两个数量级时重评 BF。决策链是需求 → 存储选型 → 过期策略，不能用下游决策证明上游选择。

面试追问

为什么缓存 key 是 deviceId 而不是 userId？
分流单元是 deviceId，batch 内容和实验组相关，按 userId 共享会让同一用户两台设备串组。曝光历史是用户级事实，才用 user 维度。
batch 尾同步生成下一 batch，用户会等吗？
会等一次全链路，TP99 约 200 毫秒。预取是后期项：需要 cursor 携带 batch 标识，翻页与重建两个写者的并发才能处理。v0 先不做，等延迟数据说话。
Redis 挂了实验还准吗？
分桶是纯函数，不依赖 Redis。exp_group 的下发不受影响，只是去重和缓存退化，两组同等退化，不引入组间偏差。

4 实验归因与数据闭环

4.1 实验

实验模型

{ "id": 101, "name": "feed_ranker_v1", "unit": "deviceId",
  "decisionPoint": "feed_ranker",
  "groups": [ { "id": 0, "name": "control",  "weight": 50, "strategy": "recall_order" },
              { "id": 1, "name": "model_v1", "weight": 50, "strategy": "reco_model",
                "whitelist": { "userIds": ["..."] } } ] }
  • 扁平，不分层。每个实验独立 salt（salt = 实验 id），天然正交；互斥是例外不是默认。后继实验必须换新 id，避免 carryover。
  • 分桶：MurmurHash3(id : unit) mod 100，按组数组顺序累积分配，组序参与分桶，ramp 只能单调挪权重。权重和必须恰好 100，部分和与手误不可区分。
  • 白名单先于 hash，userId 命中优先于 deviceId，命中即归组并正常下发 exp_group，分析时剔除。weight 允许为 0，表示仅白名单可进组，开量前验证。
  • 加载语义：Nacos 热加载；单个实验校验不过剔除并告警，其余正常生效；整份配置解析失败保留上一份可用配置。不在启动时硬失败，因为配置改动时间和发版时间脱钩，崩溃时机不可控。
  • 请求内冻结：入口一次分桶写进 Context，下游只读，中途配置刷新不影响在途请求。

显式分流点

代码里定义稳定的分流点常量（feed_ranker、feed_recaller），实验配置声明自己控制哪个分流点以及组到策略的映射，启动校验一个分流点至多一个运行中的实验，启动日志打印分流点到实验的绑定表。消费方按分流点解析出策略和命中的实验组，从不写死实验名。新策略是发版注册，新实验、新分组、换代是纯配置。

准入与分桶在一处

准入条件（比如有浏览历史才进排序实验）以谓词传进分桶函数，在分桶前判定。不能先分桶再在链路深处按条件跳过：那会让用户被盖上实验组的章却拿到对照组的行为，效应被稀释成"没效果"，且看不出来。

4.2 归因

exp_group = 实验 id - 组 id（如 101-1），两个机器 id，从第一天就写进埋点，因为埋点格式一旦落地不可改。随每张卡片的 tracking 块下发，客户端原样附在每个事件上回传，ClickHouse 里按 exp_group 分组算指标。分析前先做 SRM 校验：组间样本比偏离配置权重超过阈值，实验作废查分流。

备选与取舍

隐式参数匹配（实验只发参数，消费方按 key 读值，不知道哪个实验在驱动）。否决：换代必然发版，"零改代码跨实验"是假优势；消费方不知道谁在驱动分流，排障和 ramp 都是盲的。这是设计期推翻的第一版。分层实验（Google layers）。否决：分层是规模问题的解，本项目同时运行的实验个数用独立 salt 就正交，不需要层。沿用老 ABTestUtil 的 JSON。否决：它没有 salt、没有组 id、权重不校验，后继实验复用 key 会 carryover。

面试追问

用户换设备怎么办？
分流单元默认 deviceId，登录用户换设备会换组，接受为向零稀释。取 deviceId 而不是 userId，是因为下单必须登录，若以 userId 分流，游客登录瞬间换组，正好卡在转化漏斗中段。
怎么保证实验组的行为真的生效了？
三处对得上：启动日志的分流点绑定表，卡片 tracking 里的 exp_group，服务端日志里该请求实际用的 Ranker 名。抽一个白名单用户三处核对。

4.3 数据

客户端事件写一次 Kafka，三路消费，各回答一个问题：这个用户过去 N 天是什么样、这个用户刚刚做了什么、这个用户看过什么。

客户端 TrackingEvent ─► 上报网关 ─► Kafka
   五组字段：request（request_id）/ user / experiment（exp_group）/ item（type, id）/ event（曝光、点击、加购、下单）
                                       │
                                       ├─► ClickHouse 明细表（按天分区）
                                       │      ├─► 算法：T+1 提取长期行为特征，按行为类型加权、半衰期衰减，训练排序模型
                                       │      └─► 实验分析：按 exp_group 聚合 CTR、加购率、浏览深度，SRM 校验
                                       ├─► Flink ─► Redis 实时特征：session 内点击、加购序列，品类与品牌偏好计数，Ranker 请求期读
                                       └─► 曝光历史：曝光事件异步写入 Redis ZSET（见 3）
路径回答的问题时效消费者
Kafka → ClickHouse过去 N 天是什么样写入秒级可查，特征 T+1算法离线训练与特征；实验分析；排障
Kafka → Flink → Redis刚刚做了什么秒级Ranker 请求期按 userId 读实时特征
Kafka → 曝光历史看过什么秒级召回合并后的跨 session 去重
  • 离线与实时的分工。ClickHouse 那路慢但全，算的是长期偏好；Flink 那路快但窄，算的是当前 session 的即时意图。两类特征都由算法按 userId 取，各自权重算法定。这是 Lambda 的形状，批和流各算一份，但不需要互相校验，因为两边算的是不同的特征。
  • Flink 作业做什么。按 userId 分区，滚动窗口聚合最近 K 次点击和加购的商品 id 序列、按品类和品牌的偏好计数，去重同一 request_id 内的重复上报，结果写 Redis，key 为 userId 或 deviceId，TTL 随窗口。checkpoint 落对象存储，失败从 Kafka offset 重放，状态小，重算便宜。
  • 服务端只下发四个字段：request_id、exp_group 随卡片下发，type、id 是卡片本身。position 由客户端按渲染顺序计数，它比服务端更准；召回源、排序分、模型内部不下发。
  • 客户端归因，服务端不记曝光日志。曝光的定义（可视 50%、1 秒）只有客户端知道；服务端记的是下发，下发不等于曝光。服务端曝光账本在需要可信分母做小效应决策时再加，升级点是签名加接收校验。
  • ClickHouse：事件是追加写、按天分区、按 exp_group 和 event 聚合的列式查询，明细保留供算法回溯。特征口径和实验口径来自同一份数据。
  • 算法侧的用法：点击、收藏、加购、下单按意图强度加权，各自半衰期从实测回访周期取，窄窗口的高频行为不挤掉宽窗口的高意图行为。这是算法的事，工程侧的义务是事件不丢、字段不改。

面试追问

实时特征为什么要 Flink？算法请求期直接查 ClickHouse，或者写个 consumer 记 Redis 不行吗？
请求期查 ClickHouse 是第一版的做法，零行为用户每次打两遍行为库，首页 2 秒，见第 5 节。普通 consumer 记 Redis 能做简单计数，窄场景够用；要窗口聚合、同一请求内去重、多流 join、失败后状态恢复，就是流处理器的事。Flink 提供的是带状态的窗口计算加 checkpoint，consumer 自己写这些等于重造一个小 Flink。
客户端上报能被篡改，实验结论还可信吗？
当前阶段接受，靠数据清洗。敏感内幕不下发、实验用中性 id，篡改者得不到信息。要防篡改是服务端签名加校验，需要服务端接收端，和服务端曝光账本是同一个升级点。
为什么不直接落 MySQL？为什么是 ClickHouse 不是数仓？

按负载分：事件是追加写、宽表、按 exp_group 和 event 聚合出几行，是 OLAP 形状；MySQL 是行式、按主键读写几行的 OLTP。在业务库上 GROUP BY 几十万到百万行，既慢又拖垮线上事务。行式和列式互斥，同一份数据在两边各存一份，业务库和分析库不共用。

按温度分：ClickHouse 是列式 LSM，写入后秒级可查，定位是实时分析；Snowflake、BigQuery 是冷数仓，按查询计费，适合隔天报表。实验监控要看当天最新数据，所以是 ClickHouse。

使用上两条：列式写要批量、点查慢，所以客户端不直连，中间过 Kafka 缓冲成批写入；明细按天分区保留供算法回溯，实验指标按 exp_group 预聚合成天表，查询只扫需要的列。

Feed 上线第一周被清空
算法召回 top-60 里 73% 不可售，可售过滤在最后填充时做，切 batch 时可售的被不可售的挤掉，重建一次更空。修：可售过滤挪到算法召回路返回后立即做。结论沉淀为原则：硬过滤归召回源，主链路不兜底。
打散范围默认等于 batch 大小
头部 120 个候选里 47% 是同一品牌，窗口约束只能装 24 个，剩下 32 个被推到 batch 尾部连成 39 个一串。修：scatter_size 独立配置，放大到全列表。代价线性，每 id 约 0.2 毫秒。
零行为用户首页 2 秒
算法特征回填对空结果不写标记，零行为用户每次都打行为数据源，且一次 batch 构建里召回和排序各打一遍。修：空结果写负标记；行为窗口每请求算一次放进 Context 共享。首页 TP99 从 2.0 秒到 0.8 秒主要来自这里；剩下的大头是算法侧请求期查行为库，实时特征上线后降到约 200 毫秒。
瀑布流宽卡上方出现空白
ColumnLedger 假设商品卡等高，带营销标签的商品卡多一行 20 像素，两列标签分布不均时账本漂移，最大一次差 108 像素。修：卡片高度差进账本，标签由服务端下发时已知。

6 追问清单

1. 规模多大？
商品池约 8k，三个场景，日均推荐请求十万级，峰值几十 QPS。这个项目的卖点不是规模，是从零定边界和分层，以及把一套设计在三个月里落地并跑出实验结论。
2. 为什么不像 BFF 那个项目分阶段演进？
那个是改造，起点是运行中的系统，每一步要止血并承接下一步。这个是从零建，没有历史包袱，正确的做法是先把边界和分层一次定对，再按层落地。递进在交付顺序上：设计冻结 → 骨架 → 实验 → 状态 → 接算法 → 混排上线，每一步都有真实请求验证上一步。
3. 你个人做了什么，两个同学做了什么？
我做业内方案调研、HLD/LLD 撰写、主链路、状态层、实验框架开发、混排与问卷卡接入。一位同学做数据链路：埋点契约、上报、Kafka 到 ClickHouse、Flink 实时特征作业、算法取数口径。一位同学做 SurveyManager 的闭环。算法团队两人做召回排序模型和离线评测。
4. 设计期推翻过什么？
两处。实验模型第一版是隐式参数匹配，推翻为显式分流点，见 4.1。曝光去重第一版是 BF 加分代轮换，推翻为精确 ZSET，见 3。两次都是先写进 LLD 又改掉，代码没有返工。
5. 和 BFF 项目的关系？
BFF 讲的是取数编排：一个页面几十个下游怎么并行、怎么按需。这个讲的是推荐 serving：候选怎么来、怎么排、怎么翻页去重、怎么做实验。两个项目的共同点是先定契约再分层，边界一旦定对，两边独立演进。
6. 如果重来？
可售过滤从第一天放在召回源，第一周的事故不会有。cursor 第一版就带 batch 标识，预取和提交后异步重建都会解锁。埋点先于 Feed 上线两周跑通，首个实验能早两周出结果。
7. 和业界标准架构比，缺什么？为什么现在不做？

主干一致：五段漏斗、身份传递加算法自取特征、独立混排层、结果缓存加已下发过滤、扁平实验、客户端埋点一份事件走离线与实时两路，每一条都有业界对应。缺的是六件事，每件有明确的不做理由和触发条件。

缺什么业界做法现阶段触发条件与演进
在线学习实时样本拼接，模型分钟级更新特征实时，模型 T+1 训练实时特征上线后若证明行为时效性对效果贡献大，再做样本流与在线更新
行为实时反馈到当前 batchbatch 短或强信号触发重建，点了一件下一页就变实时特征已进 Ranker，但 batch 缓存 30 分钟内不重排；问卷提交触发 evict扩到加购、点击是加一个事件监听，代价是重建频率和算法压力
粗排召回几万 → 双塔粗排几千 → 精排池子 8k，召回退化为资格过滤，个性化全在排序候选过万加双塔粗排，先缩量再谈换协议
冷启动与探索新品保量坑位、ε-greedy 探索位运营位召回加打散，人工保量混排层加探索 Supplier，按新品曝光配额插坑
服务端分配日志serving log 记录每次下发和分组，做 SRM、召回路归因、反事实评估客户端归因，只能做组间 uplift第一个小效应决策时加签名和接收端，历史不可回补是已接受的代价
熔断与舱壁Sentinel / resilience4j，依赖变慢时快速失败召回每路独立线程池和超时；Ranker 超时回落召回原序第一次算法变慢引发告警时加熔断器，慢比挂危险

两处会被追的小点。服务端算瀑布流高度账本，一般是客户端布局：坑位和顺序必须服务端定，归因和频控依赖它，账本只预判宽卡可插性，客户端仍有实测校验降级。去重和缓存按 deviceId，跨设备会重复：缓存跟分流单元走，否则串组；曝光历史才按 user。
