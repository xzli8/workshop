# 分页方法（offset 与 cursor）

> HLD 子页。原页：https://app.notion.com/p/3a6128bc62c681e5b697efb60737f9b9 ，最后编辑 2026-07-23，导出 2026-09-18。

列表数据分页有两种经典方法：基于偏移量（offset-based）和基于游标（cursor-based）。它们适用的场景不同，下面分别讲怎么做、各自的优缺点，最后做一个对比。

## 基于偏移量的分页（offset-based）

客户端传"第几页 + 每页多少条"，服务端按偏移量切片。

```sql
SELECT * FROM items
ORDER BY sort_key
LIMIT :pageSize OFFSET (:pageNum - 1) * :pageSize;
```

请求参数通常是 `pageNum + pageSize`（或等价的 `offset + limit`），响应里可以带上总条数，前端据此算出总页数、渲染页码。

**优点**

- 实现简单，几乎所有数据库/ORM 直接支持。
- 可随机跳页：能直接跳到任意一页（第 1 页、第 50 页、最后一页）。
- 容易给出总数与总页数，适合需要页码导航的界面。
- 服务端无状态：每次请求自带 `pageNum`，不依赖上一次请求。

**缺点**

- **深分页性能差**：`OFFSET N` 要求数据库先扫描并丢弃前 N 行，N 越大越慢。
- **数据漂移会漏读/重读**：翻页期间如果列表有新增或删除，后一页的偏移量锚定的是"位置"而不是"数据"，会导致某些条目被跳过或重复出现。
- 不适合内容实时变化、只往下滚的无限流。

## 基于游标的分页（cursor-based / keyset）

以"上一页最后一条记录的排序键"作为锚点，取它之后的一段。

```sql
SELECT * FROM items
WHERE sort_key < :lastSortKey      -- 上一页最后一条的排序键
ORDER BY sort_key
LIMIT :pageSize;
```

服务端把这个锚点（排序键的值，或更复杂的续接信息）编码成一个游标——通常 base64 成一个不透明字符串返回给前端。前端下次翻页时原样带回，不解析、不拼接。游标可以只是排序键（keyset 分页），也可以是服务端自定义的令牌，里面还能携带排序方向、快照引用等额外状态。

**优点**

- **深分页性能稳定**：`WHERE sort_key < :last` 直接走索引定位，不需要扫描并丢弃前面的行，翻到多深都一样快。
- **数据漂移下不漏不重**：锚定的是数据（排序键的值）而不是位置，翻页期间列表增删不影响续接的正确性。
- 天然适配只往下滚的无限流。
- 令牌不透明时，服务端可以自由改变游标内部结构而不破坏前端契约。

**缺点**

- **不能随机跳页**：只能从当前位置顺序往前/往后翻，无法直接跳到第 N 页。
- 一般**不提供总数/总页数**（要额外查，且深分页场景下总数意义不大）。
- 实现更复杂：排序键必须**唯一且有序**，否则同值记录会在页边界漏或重，需要用"排序键 + 唯一 id"的复合游标。
- 排序维度受游标绑定，切换排序方式往往要重置游标。

## 对比小结

| 维度 | offset-based | cursor-based |
|---|---|---|
| 随机跳页 | 支持 | 不支持（只能顺序翻） |
| 深分页性能 | 差（扫描并丢弃前 N 行） | 好（走索引定位） |
| 数据漂移一致性 | 差（漏读/重读） | 好（锚数据不锚位置） |
| 总数 / 总页数 | 容易给出 | 一般不给 |
| 服务端状态 | 无状态 | 无状态或有状态（取决于令牌设计） |
| 实现复杂度 | 低 | 高（排序键须唯一有序） |
| 适用场景 | 稳定、需要页码跳转的列表 | 实时变化、无限下滚的流 |
