Agent 工程追问清单

项目介绍

1 分钟版

Maya 是 Bnto 的 AI 导购助手。Bnto 是美国的时尚租售电商，Maya 处理三类对话：找衣服和搭配、查订阅和订单、问平台规则。我一个人用三个月，基于 LangGraph 和 FastAPI 从 0 搭建。核心难点是把概率性的模型做成可靠的线上组件：流程控制和终态交给代码，模型只做决策；质量靠评测集量化回归。架构从单 Agent 起步，按领域拆成路由分流，跨领域问题多了以后升级为 manager 多 Agent 协作。10 个评测集共 760 条，通过率 98%，单轮 P99 约 5.7 秒，每轮成本约半美分。

2–3 分钟版

  • 背景：Maya 是 Bnto（美国时尚租售电商）的 AI 导购助手，处理找衣服和搭配、查订阅和订单、问平台规则三类对话。我独立完成，三个月从 0 到上线，Python、FastAPI、LangGraph，评测用 LangSmith。
  • 核心问题：大模型概率性、无状态、输出自然语言、慢且贵。原则：控制流和终态不交给模型，每轮必须以按钮或文本收尾；输出结构化并校验；上下文由代码在 token 预算内重组；高风险操作人工审批。
  • 演进：单 Agent 搭最简骨架跑通，马上建评测，之后每加一个能力都用评测集验收；规则和工具变多、Fashion 开始误调账户工具，按领域拆成路由分流，prompt 和评测按领域隔离；跨领域和多跳问题变多（「下次扣费是哪天，顺便看看黑裙子」），升级为 manager，主 Agent 把三个子 Agent 当工具，并行调用再合成。
  • 关键设计（挑两三个）：工具调用模型决策、代码约束，身份由代码注入，写操作执行前 interrupt 挂起、人工审批后恢复，挡住越权和重复执行；窗口外增量摘要加向量、关键词双路召回，FAQ 混合检索加 LLM 重排；同一套工具封装为 MCP Server 供外部 Agent 复用。
  • 结果：单元、链路、端到端三层 10 个评测集共 760 条，通过率 98%（如 FAQ 检索 147/150，单路向量 134/150）；单轮 P99 约 5.7 秒，SSE 推送进度；前缀缓存命中率 85%，每轮约半美分。

  • 数字只报 760 条、98%、P99、半美分，细分数字等追问。

1 模型基础与调用

1.1 LLM 是个什么样的组件，什么时候该用？

通用做法

  • 概率性：同一输入不保证同一输出，有错误率，不能像函数那样靠单测证明正确，只能靠评测集量错误率。
  • 慢且贵：一次调用几百毫秒到几秒，按 token 计费；多调一次就多一段延迟和一笔钱。
  • 无状态：每次调用从零读上下文，记忆、历史、工具结果都要代码重新喂。
  • 输入输出都是自然语言：既是优点（能处理规则写不完的输入）也是麻烦（输出要先变成程序能用的东西，见 1.2）。

由此一条原则：能不用就不用。能用 if / for 写完的流程就写代码；只有规则枚举不完、或输入是非结构化文本时，才把那一步交给模型（展开见 3.1、5.1）。

Maya 里

  • 模型只在五处出场：主 agent 决定调哪些领域并汇总、Fashion 转检索条件、Account 定查哪几个接口、FAQ 读片段作答、Summarizer 压缩历史。
  • 计数、放宽、澄清这些分叉全是代码。
1.2 模型输出是自然语言，怎么变成程序能用的东西？

通用做法

  • 中间每一步决策都走结构化输出，只有最终给用户看的文案出自然语言。
  • 机制：pydantic 模型转 JSON schema 随请求发出，服务端 strict 模式在解码阶段就约束成合法 JSON，枚举只能取定义过的值；返回后 pydantic 再校验一遍转成对象。
  • 分工：prompt 管「怎么判断」，schema 管「长什么样」。schema 不能替代 prompt，它只保证形状合法，不保证选得对。

Maya 里

  • FAQ、Summarizer 用 with_structured_output；主 agent 用工具调用分派子 agent；Fashion 用提交工具交结果，参数就是检索条件的 schema，代码校验后还能拒收；Account 的最终回复是给用户看的，出纯文本。
  • pydantic 校验器保证 search 和 outcome 一致；校验不过就是异常，chat.py 变成 error 帧，流不断。

2 Prompt 工程与指令

2.1 system prompt 由哪几块组成？

通用做法

块放什么原则
角色与目标你是谁、这次要完成什么一两句，决定模型的默认行为
规则判断标准、边界、禁止项、允许的取值写在「合适的高度」：不把复杂逻辑硬编码进 prompt，也不笼统到默认模型懂你的业务；分 section 写
few-shot（可选）典型样本zero-shot 起步，评测出误判再加；少而典型，不堆边界

正文只有这三块。另外三样走别的通道，不进 system prompt：

  • 工具：bind_tools 绑成请求的 tools 字段，名字、参数、说明都在工具定义上；正文最多写一句什么时候用。
  • 输出形状：with_structured_output 把 schema 绑给模型，正文不写格式契约（见 1.2）。
  • 用户输入、历史、检索结果、工具结果：按轮 append 成 user / tool 消息，不进 system。

摆放顺序只有一条：每轮不变的在前，每轮变的在后（prompt caching 按前缀命中，前面改一个字后面全失效）。

Maya 里

  • 主 agent：角色一句；三个子 agent 各管什么、什么时候并行调、怎么汇总是规则。
  • Fashion：角色一句；规则是搜单品还是整套、何时查天气、何时澄清，以及 search 各字段怎么填（must / should / mustNot 语义、boost 分档、词表取值）。一千多 token，每轮不变。
  • Account：角色一句；规则是只说工具返回的事实。工具走 bind_tools，正文不列清单。
2.2 prompt 怎么迭代？

通用做法

  • 评测集先行：没有评测集就无法判断改好了还是改坏了。zero-shot 起步，只写任务和判断标准，跑评测看错在哪。
  • 按错误补，规则优先于示例：误判样本变成一条规则或一个 few-shot，一条条加，每加一条回归。示例少而典型，覆盖边界不覆盖常见；评测句本身不进 prompt。
  • prompt 当代码管：进版本库，改动走 PR，评测不过不合并；换模型、改采样参数同样过评测。
  • 量大了换路：分类任务例子堆多了又长又慢，有标注数据后换小模型微调或 embedding 分类器。

Maya 里：照此做。prompt 都 zero-shot 起步，第一轮评测抓到「what goes with wide leg jeans」把 Jeans 放进了 must，补一条「问搭配 X 时 X 不进 must」再回归。

3 工具调用

原则（出处见末尾）
  1. 固定流程代码调，开放流程模型调。路径能用 if / for 写完的是 workflow；调哪个、调几次取决于上一步结果的才交给模型。[Anthropic, LangGraph]
  2. 工具的描述和参数签名是模型看到的全部。描述写查什么、什么时候用；参数形状让模型难填错，少而不重叠；身份类参数不暴露。[Anthropic]
  3. 工具调用失败不抛异常，压成一句话当工具结果回给模型。说清是超时、参数不对还是服务没响应，不塞整个栈；模型看到后决定换参数重调还是直接作答。[12-factor, Anthropic]

出处：Anthropic · Building effective agents；LangGraph · Workflows and agents；12-factor agents；Anthropic · Handle tool calls（is_error）

3.1 工具谁来调：代码还是模型？

通用做法

  • 代码调：不会漏调多调，出口一个 schema 钉死，一趟模型加一次 HTTP，换假函数就能测。代价是路径要提前枚举，新工具要改代码。
  • 模型调：路径开放，加工具只加描述不改流程。代价是可能该调不调、重复调、结果不够用也硬编答案，要步数上限和评测兜底；至少两趟往返；测试要模拟整个对话。

Maya 里

  • 代码调：Fashion 提交检索时的计数，每次提交必数，0 件退回让模型放宽；FAQ 的向量检索，每问必检索再作答，模型不决定查不查。
  • 模型调：Fashion 的天气，要不要查、查哪里由问题定；Account 的订阅、订单、收据，一句话可能查一个也可能查三个，组合由问题定；图片识别配订单，先识图还是先查单由上一步结果定。
3.2 工具怎么定义，哪些参数能让模型给？

通用做法

  • 一个工具一个函数：docstring 是给模型看的描述，写查什么、什么时候用，不写实现；参数签名转成 JSON schema。
  • 身份、权限、租户这类参数不让模型填：从 state 注入，schema 里不出现，模型编不了别人的 id。

Maya 里：工具是 clients 函数的薄包装，返回 JSON 字符串；user_id 标 InjectedToolArg，由 tools 节点从 state 注入。

3.3 工具调用失败分几种，各怎么处理？

通用做法

情况处理
工程偶发：超时、429、5xx指数退避加 jitter 重试，只重试幂等调用；重试耗尽回模型一句固定说明，让它说查不到，不编
模型用错：工具名不存在、参数不对错误压成一条工具结果回灌，模型改参数或换工具重调；限轮数

Maya 里

  • 工程偶发：LLM 用 OpenAI SDK 自带重试；core 在 _request 收口用 tenacity，最多 3 次，退避 0.2 秒起、上限 2 秒，单次超时 3 秒（接口全是读，可放心重试）。耗尽返回 None，Account 工具回固定句 CORE_UNAVAILABLE，评测断言模型不编。
  • 模型用错：工具名不存在、工具内异常都压成一句 ToolMessage 回灌，MAX_TOOL_ROUNDS 限轮。

4 MCP 与 Skills

原则（出处见末尾）
  1. MCP 是 AI 应用连接外部系统的标准协议，远程 MCP Server 本质是一个自描述的无状态 HTTP 服务。别人接入：配 URL → OAuth 登录 → tools/list 发现工具 → 模型决定调用 → tools/call 执行。[MCP]
  2. 同一批工具要给多个 Agent 或 Host 用，才封装成 MCP Server。单应用进程内的工具直接定义，多一层协议只多一层开销。[MCP]
  3. MCP 管能连上什么，Skill 管拿到工具后按什么步骤做。Skill 平时只占名字和描述，用到才读全文。[Anthropic Skills]

出处：MCP · Architecture overview；MCP · Specification 2026-07-28；MCP · Authorization；MCP · Registry；Anthropic · Equipping agents with Agent Skills；Anthropic · Code execution with MCP

4.1 MCP 是什么，什么时候用？

通用做法

  • 连接 AI 应用和外部系统的开放标准，类比 USB-C：系统按协议实现一次 Server，所有支持 MCP 的应用都能接，M 个应用接 N 个系统从 M×N 套适配变成 M+N。只管双方怎么交换能力，不管应用怎么用模型。
在哪一层解决什么
Function Calling模型 API模型怎么输出一次结构化的工具调用
MCP应用和工具之间工具怎么被发现、连接、跨进程调用
A2AAgent 和 Agent 之间一个 Agent 怎么把任务委派给另一个 Agent
  • MCP 不替代 Function Calling：Server 暴露工具，Host 把工具定义转成 function 交给模型，模型输出调用，Host 再经 MCP 去执行。
  • 什么时候用：工具只给自己的 Agent 用，Function Calling 就够；要给别人的 AI 应用用，或多个 Agent 复用同一套工具，才做成 MCP Server。

Maya 里

  • 图内工具是 LangChain @tool，进程内直接调，不走 MCP。
  • 同一套 Account 工具另起 maya.mcp_server 以 MCP 暴露，函数体直接复用 agents/account.py，Claude Code 等 Host 能直接接入。
4.2 MCP 由哪几部分组成？

通用做法

  • 角色：Host 是 AI 应用本身，模型在这里；Client 是 Host 里的连接组件，一个 Server 对应一个；Server 是对外提供能力的程序。
  • 分层：数据层是 JSON-RPC 2.0，定义能力发现和原语；传输层有 stdio（Host 拉起的本地子进程）和 Streamable HTTP（远程），认证也在这一层。换传输不动数据层。
原语谁控制用途
Tools模型模型决定调的函数，最常用
Resources应用URI 标识的只读数据，应用决定放不放进上下文
Prompts用户用户主动选用的模板，比如斜杠命令
ElicitationServer 发起执行中途向用户追问或确认
  • 版本按日期：2025-11-25 及以前先 initialize 握手协商版本和能力，连接有状态，Server 可以在调用中途向 Client 发请求；2026-07-28 起请求无状态、每个请求自带版本和能力，Server 要追问就返回 InputRequiredResult，Client 带着回答重发同一个调用；Sampling（Server 借 Host 的模型）同版废弃，Server 要模型直接调厂商 API。
  • 核心之外是可选扩展：Tasks（长任务异步执行）、Skills over MCP、MCP Apps（对话里渲染交互 UI）。

Maya 里：只暴露 Tools，elicitation 用于写操作确认；MCP Python SDK 2.3 的 MCPServer，同一个 Server 在 2025-11-25（握手）和 2026-07-28（无状态）两版协议下都测过，工具列表、调用、确认结果一致。

4.3 MCP Server 本质是什么，别人的 Host 怎么接入？

通用做法

  • 远程 Server 是无状态 HTTP 服务：单一 /mcp 端点收 POST，消息是 JSON-RPC，每个请求自带版本和能力，能直接放负载均衡后面水平扩；认证上是 OAuth 2.1 资源服务器。
  • 和普通 API 的区别不在 AI（Server 里通常没有模型），在接口自描述：工具名、说明、参数 schema 运行时可取，模型读了就会调，不用人写适配代码。
  1. 拿到地址：用户把 URL 配进自己的 Host；公开的 Server 发布到官方 MCP Registry（只存元数据，命名空间经 GitHub 或域名验证），由下游目录收录；按域名自动发现（Server Card）还是实验提案。
  2. 认证：首次请求返回 401，Host 读 /.well-known/oauth-protected-resource 找到授权服务器，走 OAuth（PKCE、resource 参数）让用户登录拿 token；Server 校验 token 的 audience 是自己，不把它转给下游。
  3. 发现：Host 调 tools/list，合并各 Server 的工具交给模型。
  4. 调用：模型选工具和参数，Host 发 tools/call。

Maya 里

  • stdio 形态用 claude mcp add 接进 Claude Code。
  • 远程形态：Streamable HTTP 暴露 /mcp，user_id 的 resolver 改成从 access token 解析，工具签名不动。
4.4 MCP 下身份和高风险操作怎么管？

通用做法

  • 身份不进工具参数：stdio 下由 Host 启动 Server 时注入；远程用 OAuth 2.1，Server 是资源服务器，从 access token 解析用户；不把用户 token 原样转给下游（token passthrough），防 confused deputy。
  • annotations（readOnlyHint、destructiveHint、idempotentHint）只是提示：Host 可据此决定弹不弹审批，规范要求不可信 Server 的 annotations 按不可信处理，Server 也不能指望 Host 一定拦。
  • 写操作由 Server 自己确认：发 elicitation，用户拒绝就不写，Client 不支持 elicitation 就拒绝执行。
  • Host 侧：调用工具前要用户同意；第三方 Server 先审再接；工具描述和返回值都可能夹带注入。

Maya 里

  • user_id 用 SDK 的 Resolve 在服务端注入，工具的 inputSchema 里没有它，和图内 InjectedToolArg 是同一个约束；stdio 下取自启动环境 MAYA_USER_ID，换远程只改 resolver，工具签名不动。
  • pause_subscription 标 destructiveHint、idempotentHint，同时用 Resolve 加 Elicit 发确认：拒绝回 DECLINED 不写；Client 没声明 elicitation 能力时调用直接报错，不执行。
  • 测试时后端换假函数，覆盖确认、拒绝、不支持确认、未登录四种情况，后端只在确认后被写一次。
4.5 接的工具多了，上下文装不下怎么办？

通用做法

  • 两处占上下文：工具定义启动时全量预加载；每次调用的中间结果都要过一遍模型。
  • 解法由轻到重：按场景只暴露子集；用 search_tools 按需取工具定义；让模型写代码调 MCP，大数据在执行环境里过滤，只把结果给模型（Anthropic 的例子 150k token 降到 2k）。

Maya 里：主 agent 只看到三个子 agent 工具，每个子 agent 只挂自己那几个工具，不存在这个问题。

4.6 Skill 是什么，和 MCP、prompt 有什么区别？

通用做法

  • Skill 是一个文件夹：SKILL.md（frontmatter 里 name、description，正文是指令），加可选的脚本和参考文件。

5 Agent 范式与控制流

原则（出处见末尾）
  1. workflow 是代码定路径，agent 是模型定路径。agent 加延迟和成本、放大错误；单 agent 做满，工具重叠或 prompt 分支过多时才拆多 agent。[Anthropic, OpenAI]
  2. 循环永远是代码在跑。模型每步只决定做什么，再来一圈、执行工具、回灌结果都是代码。[hello-agents, LangChain]
  3. 步数要有上限，超限走确定的出口。recursion_limit 是最后一道，不是控制流。[LangGraph, OpenAI]
  4. 节点是 checkpoint 和重放的单位。恢复从节点开头重放，副作用要放在节点里；interrupt 只能落在节点边界。[LangGraph]

出处：Anthropic · Building effective agents；hello-agents · 第四章；LangGraph · Workflows and agents；LangGraph · Durable execution；OpenAI · A practical guide to building agents；Anthropic · How we built our multi-agent research system；Anthropic · Effective context engineering for AI agents；LangChain · Multi-agent；LangGraph · Checkpointers；OpenAI Agents SDK · Multi-agent

5.1 workflow 和 agent 怎么分，各有哪些模式？

通用做法

  • 分界线是谁决定下一步：workflow 的路径由代码预先写死，模型只在节点里干活；agent 由模型在循环里根据工具结果决定下一步和何时结束。
  • 怎么选：先用最简单的。步骤能预先写清、要求稳定，用 workflow；步骤数事先定不下来，才用 agent。agent 成本更高、错误会累积，要设轮数上限、靠评测兜住。
  • workflow 的五种模式（Anthropic 的分法）：
模式做法
prompt chaining拆成固定几步，上一步输出喂下一步，中间可插代码检查
routing先分类，再分到不同的处理流程
parallelization多个调用同时跑再汇总，分切片和投票两种
orchestrator-workers模型动态拆出子任务派给 worker，再合并结果
evaluator-optimizer一个生成、一个评估，循环修改直到通过
  • agent 的三种范式：
范式做法适合
ReAct想一步做一步，每步看工具结果再决定下一步（见 5.2）步骤少、下一步依赖上一步结果
Plan-and-Execute先让模型列出完整计划，再逐步执行，执行中发现不对就重新规划步骤多的长任务：规划只调一次强模型，执行可换小模型，也不容易中途跑偏
Reflection先产出，再由模型自评或外部反馈评审，按意见修改；Reflexion 还把失败教训写成文字留给下次尝试质量要求高、评审标准写得出来的输出。和 evaluator-optimizer 是同一个思路
  • 多 agent 编排：按信号逐级加复杂度。单 agent 起步；领域之间 prompt、工具互相干扰，且每个请求只属于一个领域，拆成 routing（一次分类，代码分给专职 agent）；请求常跨多个领域，升到 manager（也叫 agents as tools、supervisor：主 agent 把子 agent 当工具调用，汇总后自己回复）。handoff 是另一条路：某个领域需要跨轮在岗的长流程时用。

Maya 里

  • 主 agent 是 manager：Fashion、Account、FAQ 三个子 agent 是它的工具，一句话涉及几个领域就并行调几个，再汇总成一句回复。Fashion 的检索条件由代码直接变成按钮，不经主 agent 转述；只调了一个子 agent 时直接透传，省掉汇总调用。
  • 子 agent：FAQ 是 prompt chaining，检索、rerank、作答三步固定；Fashion、Account 是 ReAct，查不查天气、搜单品还是整套、查哪几个接口都由模型定，出口由代码把关。
  • 按信号逐级演进：单 agent 起步；Fashion 的规则和词表变重、开始误调账户工具，按领域拆成 routing，prompt 和评测按领域隔离；之后跨领域问题变多（「下次扣费是哪天，顺便看看黑裙子」），routing 只能进一个领域，升到 manager。
5.2 ReAct 是什么，由哪几部分组成？

通用做法

  • 定义：推理和行动交替的循环。Thought 决定下一步，Action 调工具，Observation 把结果追加回上下文，直到模型不再要动作。
  • 组成：四部分，原论文用文本实现，现在用函数调用实现：
组成原论文函数调用版
Thought模型输出的文本推理模型内化，不公开
Action文本，正则切出动作和参数类型化的 tool_call，不用解析
Observation执行结果拼成文本每个 tool_call 一条 ToolMessage，按 id 配对
出口输出 Finish；超过 max_steps 强停没有 tool_calls 就结束；轮数上限兜底
  • 推理回传：每步是一次新调用，上一步的推理项要回传，模型才能接着想；只在同一轮工具循环里必须带。要用 Responses 接口，chat completions 不返回推理项（存储时传 id，不存储时传密文）。

Maya 里

  • Account：一条消息可并行要多个工具（「下次扣费和箱里有什么」一轮查两个）；要几轮由模型定，没有 tool_calls 就结束，轮数用完不绑工具，强制作答。
  • Fashion：出口是提交工具，模型用它交检索结果，代码计数有货才结束；0 件作为 Observation 退回，模型自己放宽。
5.3 循环怎么停？

通用做法

  • 正常出口：模型不再要工具，或给出约定的结构化输出。
  • 兜底出口：轮数上限。到了不抛异常，走确定路径：不绑工具强制作答，或返回固定澄清。
  • 重复检测：同一工具同样参数连调几次就中断，防止在上限内空转。
  • 框架上限：LangGraph 的 recursion_limit、OpenAI Agents SDK 的 max_turns（默认 10）。LangGraph 老版本默认 25 步，1.x 改成 10007，基本等于不设防，要按图自己配。超限说明出口写漏了，是 bug 不是流程。

Maya 里

  • Fashion：工具调用最多 4 轮（查天气、提交、两次放宽），用完还没收下检索就回固定文案转澄清。
  • Account：MAX_TOOL_ROUNDS = 3，用完后不绑工具，最多四次模型调用、七步，用不着 recursion_limit。
5.4 什么时候用 interrupt？

通用做法

  • 机制：第一次调 interrupt() 抛异常，图存档后退出；恢复时传 Command(resume=值)，被中断的节点从头重跑，interrupt() 直接返回该值。
  • 何时用：写操作前要人批准、改参数或拒绝，处理的是存档里冻结的那次 tool_call，终态加下一轮做不到。澄清、登录引导这类能用终态收口的不用。
  • 落地要点：中断前的代码要能重跑；只恢复本人的、仍在等确认的那一轮；结果不确定时读回状态；工具按风险分级（只读还是写、能否撤销、是否涉钱），高风险的先预览代价再确认。

Maya 里

  • 机制：Account 的 tools 节点执行写工具前 interrupt，前端出确认按钮，点击带回 threadId，图从断点执行。
  • 何时用：只有暂停、取消订阅这类写操作停下确认，澄清和登录引导用终态。
  • 落地要点：写工具登记在一张表里（工具名 → 确认语）；取消订阅先调预览，把会失去的 bonus credits 写进确认语；失败时读回订阅状态再回复。
5.5 为什么用 manager，不用多意图路由？

通用做法

  • 多意图路由（multi-intent routing）：分类器识别多个意图，为每个意图生成子查询，并行扇出给对应 agent 后合成。局限是一次性分发，子任务在分类时已确定，不支持多跳串行调用。
  • manager（agents as tools / orchestrator-workers）：主 agent 在循环中动态分解任务、委派子 agent、合成结果；子任务不预先定义，可依据中间结果追加调用。代价是多一次模型调用。

Maya 里：跨领域请求中存在多跳依赖，如「我订阅暂停了吗？暂停了怎么恢复」，需先查账户状态，再依据结果检索 FAQ，一次性分发无法处理，因此升级为 manager。

5.6 主 agent 怎么分解和委派任务？

通用做法

  • 任务委派：每个子任务明确目标、输出格式、可用工具和任务边界，描述含糊会导致重复劳动或遗漏。
  • 上下文隔离（context isolation）：子 agent 在干净的上下文窗口中只处理自己的子任务，不继承主对话全部历史。
  • 身份注入：身份与权限参数由代码注入，不暴露给模型。

Maya 里

  • 三个子 agent 封装为工具，参数为主 agent 改写后的独立子查询（指代已消解）。
  • 领域状态按需附加，如 Fashion 附上一轮检索条件；user_id 由 state 注入。
  • 每个领域每轮最多调用一次、最多两轮：相互独立的子任务同轮并行，有依赖的放到下一轮。
5.7 并行怎么执行，部分失败怎么处理？

通用做法

  • 扇出/扇入（fan-out / fan-in）：一次输出多个 tool_call 并发执行，每路独立超时，总延迟取决于最慢的一路。
  • 部分失败与降级：单路失败时，将失败信息作为该路结果返回，其余路照常合成，不拖垮整轮。

Maya 里

  • 用 LangGraph Send 将每个子任务分发到独立的子图节点，同一超步（super-step）内并行执行，结果经 reducer 合并。
  • 不在单个节点内 gather：checkpoint 按超步保存，同一超步中已成功节点的写入作为 pending writes 持久化，Account 因人工审批中断后恢复时，已完成的 Fashion 分支不会重跑。
  • 单路超时返回「该领域暂不可用」，先回答可回答的部分，不编造。
5.8 结果怎么合成，额外成本怎么控？

通用做法

  • 结果合成（synthesis）：子 agent 返回浓缩结果，由主 agent 合成最终回复。
  • 避免转述损耗：结构化产物写入外部状态，只向主 agent 回传轻量引用，减少信息损耗和 token 开销。

Maya 里

  • Fashion 检索条件由代码直接渲染为按钮，主 agent 只收到一句摘要；Account、FAQ 的事实在合成时保持不变。
  • 只调用一个子 agent 时直接透传，跳过合成调用：单领域仍为 2 次 LLM 调用，仅跨领域请求多一次。
  • 评测：分派结果（调用了哪些子 agent、子查询是否完整）单独评测，各领域原有评测集同时回归，确认单领域不退化。

6 记忆与上下文工程

原则（出处见末尾）
  1. 上下文是有限资源。窗口越满召回越差，目标是能达成任务的最小高信号 token 集。[Anthropic]
  2. 自己掌握上下文窗口。历史存在自己手里，进模型的每一段都是自己拼的，不交给框架或供应商。[12-factor]
  3. 短期记忆按会话重放，长期记忆按需检索。两者存储和取法都不同，不混在一张表里。[LangGraph, hello-agents]
  4. 窗口外的历史靠压缩和召回，不靠加大窗口。摘要保事实、相似召回保相关、结构化笔记保进度。[Anthropic]
  5. 历史按访问模式建模。按会话取最近 N 轮、按会话追加，就是分区键加排序键。[系统设计通则]

出处：Anthropic · Effective context engineering for AI agents；12-factor agents（Own your context window）；LangGraph · Memory；hello-agents · 第八、九章

6.1 一轮的 prompt 由哪几层组成？

通用做法：按在 prompt 里的位置从上到下，也是从稳定到易变。

层管什么从哪来、怎么更新怎么进 prompt
System角色、规则、few-shot（可选）代码常量，每轮一样system 消息，缓存前缀
画像（长期记忆）跨会话的稳定属性：尺码、风格、过敏按用户存，模型从对话里抽或离线算整份或命中的几条，放在历史之前
摘要本会话窗口外的事实掉出窗口的轮次攒够就调模型增量合并一段概要，一条 user

  • 除 System 外全是数据，按权威层级放 user 不放 system。
  • 摘要和召回互补不替代：摘要稳住「说过的约束」这类和当前问题措辞不像的事实，召回找「上次聊的那条裙子」这类有具体词的旧轮。
  • LangGraph 里摘要、召回、窗口属于 checkpointer（thread 内的 state），画像属于 Store（跨 thread 的命名空间）。

Maya 里：HistoryContext.as_messages 按这个顺序拼：摘要和召回合成一条 user，窗口逐轮重放，三个 agent 共用；画像每轮从 Context Hub 拉。窗口 60 token 的评测：只有窗口 9/30，开摘要和召回 30/30。

6.2 摘要怎么做？

通用做法

  • 调模型，增量式：旧摘要加新掉出窗口的轮次 → 新摘要，不重新总结全部历史。结构化输出钉形状，prompt 规定只留事实（偏好、尺码、约束、搜过什么和结果）、丢寒暄和已推翻的、长度上限。
  • 触发按 token 不按轮数：掉出窗口且未进摘要的轮次累计超过阈值才调一次。LangChain 的 SummaryBufferMemory、langmem 的 SummarizationNode、Anthropic 的 compaction 都这样。
  • 其他压缩手段：结构化笔记（长任务把进度写到上下文外的持久化存储）、子 agent（专门任务在干净上下文里做，只返回精炼结果）。

Maya 里：summaries 表一会话一条，covers_until 是游标；轮末「掉出窗口且未进摘要」的轮次超过 1000 token（窗口预算的四分之一）调一次，150 词上限；失败不推进游标，下一轮重试。八轮手测看到摘要两次滚动，S 码、羊毛过敏、不要荧光色、预算逐条并入。

6.3 召回怎么做？混合检索与 RRF

通用做法

  • 按本轮输入从会话的全部历史里找相关的旧轮，两路：向量一路管语义（改写、同义），对精确词几乎没有分辨力，「不要羊毛」和「要羊毛」向量几乎一样；关键词一路（倒排索引加 BM25 或 ts_rank）管品牌、型号、数字、否定，但「返货」和「退货」对不上。两路各补对方的盲区。
  • 两路各取 top-k，RRF（Reciprocal Rank Fusion）合并：一个结果在某一路排第 r 位记 1/(k+r) 分，k 取 60，几路出现加几份，按总分取前 k。只看名次不看分数，因为余弦距离和关键词分数量纲不同；k=60 压平前几名的差距，让两路叠加胜过单路的微小名次差。
  • 例子：向量路 [m1, m4, m0]，关键词路 [m0, m2]。m0 得 1/63 + 1/61 ≈ 0.032，m1 只有 1/61 ≈ 0.016，m0 反超第一：关键词命中就能把向量排后面的结果捞回来。
  • 局限：RRF 不知道名次之间差多少；没有阈值时总会凑满 k 条，prompt 里要写「可能相关」让模型自己判；两路返回条数要对称。
  • 换成 DynamoDB 加 OpenSearch 时同一套逻辑搬到引擎里：turns 写 DynamoDB，Streams 或 zero-ETL 同步到 OpenSearch 的一个索引，文档里 user_text、reply 做 text 字段，embedding 做 knn_vector 字段（HNSW），session_id 做 keyword 字段。查询一条请求：hybrid 查询里放两个子查询，match（BM25）加 knn，外层 filter session_id，用 search pipeline 的 normalization-processor 做 RRF 或分数归一化，引擎直接返回融合后的 top-k。向量仍由客户端算好写入，或接 neural 插件让引擎算。应用层从「两条 SQL 加 Python 融合」变成「一条请求」，recall 的签名不变。

Maya 里：两路都在 PostgreSQL，向量用 pgvector 的 <=> 余弦距离，关键词用生成列 tsv（to_tsvector 分词去停用词还原词干）加 gin 索引；各取 2k，Python 里 RRF 后去掉窗口里已有的取 3；会话还没说过话时跳过。FAQ 检索复用同一套 retrieval.py。

6.4 窗口怎么截、历史怎么重放？

通用做法

  • 按 token 预算从最新往前取整轮，不截半轮；用 tokenizer 数，不用字符数。
  • 重放成 Human / AI 消息放在本轮之前，不拼成一段文本：模型按角色理解对话，追加不改写也保住缓存前缀。
  • 不同节点看到的历史可以不一样：需要上一轮结构化结果的节点，把结果附在那轮的 AI 消息后面。

Maya 里

  • 预算 4000 token，tiktoken 计数；窗口预算、摘要阈值、召回条数三个旋钮进 Settings，评测时改环境变量跑对比。
  • 三种形态：主 agent 纯文本重放，判「make it blue」交给 Fashion；Fashion 重放时附 [criteria used: …]，prompt 加一条「追问在上一轮条件上改，无关请求从头来」；Account 把历史放在子图 messages 最前面。
6.5 历史消息存什么、怎么建模？

通用做法

  • 自己存，不用供应商的 thread 或 previous_response_id：状态锁在供应商手里，换模型即丢，也做不了查询和裁剪。
  • 一行一轮，不是一行一条消息：窗口按轮截、评测按轮算、追问要上一轮的结果，轮才是历史的单位。
  • 只存对话事实：用户原话、回复、意图、结构化结果。工具消息、推理块、进度不存，下一轮重新来。没产出回复的轮次不存，那是 trace 的事。
  • 主键是会话加时间，其余是普通字段：访问模式只有「按会话取最近 N 轮、按会话追加」，这就是分区键加排序键的形状。

Maya 里：turns(session_id, created_at, message_id, user_text, reply, intent, search jsonb)，主键 (session_id, created_at)。库挂了读当没有历史、写只记 warning，最多等 2 秒，历史是增强不是前提。

6.6 会话怎么定义？

通用做法

  • 会话键由服务端验证过的身份决定：登录用户用 userId，匿名用设备 id，一个人一个会话，上下文长度靠窗口和摘要控制。要做多会话时由后端建会话下发 id，前端只回传。
  • 客户端传来的 id 只能用来选，不能用来证明身份。会话 id 从客户端来时服务端每次查归属，不属于当前用户就拒绝；漏掉就是 OWASP API Top 10 第一条 BOLA。id 要不可猜，但不可猜不能替代归属检查。

Maya 里：照此做。userId 由 cookie 去 core 换来；匿名用请求头里的随机设备 id，游客历史不含账户数据。前端的页面级 sessionId 不存。

6.7 存储现在为什么这样，什么时候换？

通用做法

  • 历史的访问模式是「按会话取最近 N 轮、按会话追加」，教科书答案是 KV 库的分区键加排序键；检索要向量加关键词混合，教科书答案是搜索引擎。完整体是 DynamoDB 存、Streams 做 CDC、OpenSearch 索引，AWS 有 zero-ETL 集成。
  • 完整体的代价：最终一致（写入到可搜差几百毫秒到几秒）、同步链路要运维（断了、失败、重建索引）、两份 schema 要同步演进。量没到之前这些都是净成本。
  • 关键词这一路 PostgreSQL 全文检索和 ES 的差距：ts_rank 只看词频和位置，BM25 有长度归一和逆文档频率；查询语法（minimum_should_match、短语、模糊、同义词）、原生混合检索、多语言分词 ES 都强。量小时差距靠 RRF 和向量路补得回来。
  • 切换信号：写入到万级每秒或单表过亿、语料到十万段以上、要多语言分词、评测显示关键词一路的排序拖后腿。换的时候访问模式不变，两路取 top-k 再融合只是合成一条请求。

Maya 里：一个 PostgreSQL 顶三件，历史、向量、全文同库，事务一致、零同步、一处 schema，本地 docker 一行起；表按 KV 的形状建（主键 session_id 加 created_at），迁 DynamoDB 不改访问模式。OpenSearch 的向量同样是客户端算好写进 knn_vector 字段，差别只在它默认建 HNSW 索引；它的 neural 插件可以服务端算，我们的 embed 函数不用动。

6.8 多轮和长上下文怎么评？

通用做法：历史由样本直接给定，只评最后一句。不跑前几轮：省模型调用、不碰库，评的就是「给定这段历史，最后一句做对没有」。断言意图是否接上、结构化结果改得对不对、追问的工具和事实。

Maya 里

  • maya-multiturn 50 条，历史给在窗口里，覆盖换颜色、换品类、撤销条件、指代（the second one）、新请求从头来、意图切换、短追问、Account 追问。49/50。
  • maya-longcontext 30 条，走真实链路（写临时会话、压缩、读上下文、跑图、删会话），早期一轮说了约束，后面六七轮无关对话把它挤出窗口。窗口 60 token 时只有窗口 9/30（早期说的排除项 0/8 带回），开摘要和召回 30/30；先用 150 跑时早期轮次根本没掉出窗口，对比无效，先确认实验条件触发了要测的机制。

7 RAG

原则（出处见末尾）
  1. 召回要宽，排序要准。便宜的检索先把范围缩到几十条，贵的模型只在候选里判断。[Huyen, Anthropic]
  2. 向量和关键词各补盲区。语义靠向量，专名、数字、否定靠关键词，融合后再排。[Anthropic Contextual Retrieval]
  3. 只按检索到的内容作答，答不了就拒答。出处可追溯，知识库外的问题不用常识补。[OpenAI, RAGAS]
  4. 检索和生成分开评。答错了要分得清是没找到还是找到了没用对。[RAGAS, Hamel]

出处：Anthropic · Contextual Retrieval；Chip Huyen · AI Engineering 第六章；RAGAS · Metrics；Hamel Husain · Your AI Product Needs Evals

7.1 RAG 由哪几段组成？

通用做法：离线建库，在线检索加生成，按数据流向从左到右。

段管什么常见做法Maya

索引每块存成可检索的形式向量索引加倒排索引pgvector 加 tsvector，同一张表

7.2 怎么切块？

通用做法

  • 先按结构切（标题、问答对、段落），一块讲一件事；太长才按 token 切，常见 200 到 800，带 10% 到 20% 重叠。
  • 块太小语义不完整，太大一块混几件事、向量被平均；固定长度硬切会把一个答案劈成两半。
  • 块带元数据（编号、分类、来源、更新时间），用于过滤、出处和增量更新。

Maya 里：FAQ 天然是问答对，一条一块，按编号 upsert。

7.3 embedding 当黑盒用，要知道什么？

通用做法

  • 文本映射成固定长度向量，语义越近余弦越大。擅长同义改写，不擅长专名、数字、否定，所以要配关键词。
  • 选模型看 MTEB 效果、维度（越大越准越贵）、上下文长度、语言。
  • 纪律：索引和查询同一个模型，换模型全量重建；算一次存一次；失败降级到关键词一路。

Maya 里：text-embedding-3-small，写入和查询共用一个句柄。

7.4 关键词一路怎么匹配？

通用做法

  • 默认 OR：问题里出现任一个词就算候选，BM25 排序。BM25 有 idf，到处都有的词（find、work）权重低，罕见词（wool、allergic）权重高，所以 OR 不会被泛词带偏。
  • 要收紧用 minimum_should_match（如四个词至少命中三个），纯 AND 只用在必须精确匹配的字段上，比如品牌名。

Maya 里：FAQ 用 OR，36 个问法只用关键词时 AND 找对 13 个、OR 找对 27 个。历史召回用 AND（PostgreSQL 的 ts_rank 没有 idf，短文本加 OR 会让泛词结果挤掉相关的那轮，用更严的匹配补；迁到 OpenSearch 后改回 OR）。

7.5 为什么要 rerank？

通用做法

  • 检索是粗排，只看像不像，看不出段落有没有回答问题；重排让读过原文的模型判断。粗排多取（要 k 条取 2k 以上），精排只在候选里排。
  • 两种重排器：cross-encoder（bge-reranker、Cohere Rerank）快且便宜；LLM 重排更准，多一次调用。
  • 重排只改顺序不改集合，失败退回粗排顺序。

Maya 里：LLM 重排，混合检索取 10 条、排完取前 5。150 条问法前 3 命中：单路向量 134/150，混合 129/150，加 rerank 147/150。口语问法和 FAQ 原文关键词重合少，关键词一路把融合排序拉偏，重排拉回来；没过的 3 条是候选 10 条里就没有，问题在召回。

7.6 怎么防幻觉、怎么查忠实度？

通用做法：忠实度（faithfulness / groundedness）指回答每句话都能在给定段落里找到依据。三道防线：

防线手段
生成前：约束段落放 user 不放 system；prompt 规定只按段落答、答不了就拒答；要求报出处
生成时：guardrail代码规则（出处编号必须在给定段落里）；高风险场景再加模型检查，判不忠实就重写或拒答
生成后：评测离线跑评测集，线上抽样 trace；指标是事实子串和 faithfulness
  • 出处只证明找对了段落，不证明照着说了，忠实度要靠模型判。
  • faithfulness 的标准做法（RAGAS）：先把回答拆成原子陈述，再逐条判断能否从段落推出，得分是有依据的比例。便宜的替代是 NLI 小模型。judge 要先拿人工标注校准。

Maya 里：结构化输出带 sources，代码只保留真的给过模型的编号；评测查事实子串、出处、知识库外拒答，60 条（15 条该拒答）56/60。

7.7 RAG 怎么评？

通用做法：分层评，答错了才知道错在哪一段。

层指标
检索：正确段落进没进前 khit@k、MRR
引用：依据的是不是对的段落期望出处覆盖率
答案：说得对不对、有没有编事实子串、faithfulness（见 7.6）
拒答：知识库外有没有硬答拒答率

Maya 里：检索和回答两个数据集。检索层不调对话模型，适合大量问法做对比实验。

7.8 检索由代码调还是模型调？

通用做法

  • 普通 RAG：每问都检索，代码调，不会该查不查。
  • agentic RAG：检索做成工具，模型决定查不查、查几次、换词再查；适合多跳问题，多一趟往返。
  • 中间态是 query rewrite：检索前用历史把省略句改写完整。

Maya 里：FAQ 一问一查，代码调（判断标准见 3.1）。

7.9 用托管、pgvector 还是搜索引擎？

通用做法

  • 托管（OpenAI FileSearch、Bedrock 知识库）：切块、召回、排序都在对方，快但不可调不可评。
  • pgvector：和业务数据同库，全链路可控，适合十万段以内。
  • OpenSearch / ES：BM25、混合检索、分词器原生，适合语料大、多语言，多一套组件和同步链路。

Maya 里：pgvector，和历史同库（切换信号见 6.7）。

8 评测与可观测

原则（出处见末尾）
  1. 评测驱动开发，尽早开始。20 到 50 条源自真实失败的样本就能起步；没有评测集的 prompt 调优是凭感觉。[Anthropic, OpenAI]
  2. 条数由覆盖决定。每个重要流程和已知失败都要有样本，回归集通常长到 100 条以上；样本越少，能分辨的差距越大。[Hamel, Anthropic]
  3. 评结果不评路径。不把 agent 的步骤顺序钉死，否则惩罚合理但不同的解法。[Anthropic]

出处：Anthropic · Demystifying evals for AI agents；OpenAI · Evaluation best practices；Hamel Husain · Your AI Product Needs Evals；Hamel Husain · How many examples do I need for an eval?；Anthropic · Adding Error Bars to Evals；LangSmith · Evaluation concepts

8.2 样本从哪来、怎么维护？

通用做法

  • 起步手写，正负都要：该做的和不该做的都测，只测「该搜」会把模型推向什么都搜。边界句单独分组，它们才是迭代的抓手。
  • 上线后从 trace 捞：用户点踩、输出被 schema 拒、人工抽检发现的，进标注队列变成样本。
  • 防过拟合：评测句不原样进 prompt 当示例。

Maya 里：手写起步，每个数据集带反例（该澄清不该搜、知识库外该拒答、不该调工具）和 hard 分组。样本真源在 LangSmith 数据集，git 里的 jsonl 只用来在新环境重建。

8.3 样本要多少条，怎么扩、怎么保证质量？

通用做法

  • 多少条：起步 20 到 50 条；回归集按覆盖长到 100 条以上。条数少只能看出大退步：15 条错 1 条就差 6.7 分，要分辨 3 个点的差距大约要上千条，所以每次改动多跑几遍，并和改动前的代码对照。
  • 怎么扩：先列覆盖维度（每个意图、每条知识、每个工具、每种失败），再按变体写：同义改写、口语短句、和原文没有关键词重合的场景描述、多条件组合、边界歧义；正反例都要，难样本单独分组，约占两成。上线后以真实 trace 和用户反馈为主。
  • 保证质量：标签要有依据（词表、假数据、知识原文、prompt 里的定义）；自动检查查重、取值合法、分布；跑完逐条看没过的，先判标签错还是系统错，标签错改标签，系统错保留。

Maya 里

  • 10 个数据集从 203 条扩到 760 条：Router、FAQ 检索各 150，Fashion 条件 100，Account 80，FAQ 回答 60，Fashion 行为、终态、多轮各 50，Account 写操作 40，长上下文 30。
  • 维度举例：37 条 FAQ 每条至少 3 种问法；Router 三类意图各 50，重点补「问政策」和「查自己的账户」的边界（how long can I pause for 是 faq，pause my subscription 是 account）。
  • 标签自动校验：Fashion 条件对照 vocab.py 词表，Account 的事实对照假数据，FAQ 的事实对照 faq.md 原文。
  • 失败反查：改了 4 条过严的标签（比如要求答出假数据里没有的扣费金额）；剩下 14 条都是系统错，保留，比如召回没捞到、排除条件写成了偏好、知识库外说完不知道又补引用。总体 746/760。
8.4 评测器怎么判？

通用做法：按「这个字段错了后果多大」选比法，同一条输出不同字段可以不同比法。

比法什么时候用
精确相等多一点少一点都算错，如硬过滤条件
覆盖漏了算错、多了不算，如软偏好、必须调的工具、必须出现的事实
形状端到端只看终态和序列，不看措辞
模型判（LLM judge）代码判不了的语气、是否答到点上、两版哪个好；用成对比较或通过与否，先理由后结论，先和人工标注校准

Maya 里：全部代码评测器，可复现、零成本。例：Fashion 的 must 精确相等（多放一个 Color 结果就只剩那个颜色），should 只查覆盖；单品还是整套、该不该查天气用假数据单独评。

8.5 怎么用评测驱动迭代？

通用做法

  • 样本固定，两次实验跑同一批才可比；每次实验标记改了什么，才能归因。
  • 单次分数不可信：模型是概率性的，多跑几次看 pass^k，0% 通过多半是样本或评测器有 bug。
  • 对比实验先确认实验条件真的触发了要测的机制，否则对比无效。

Maya 里

  • 实验名用前缀标改动；对比实验靠环境变量切模式（检索单路与混合、窗口预算、开关摘要和召回），不改代码。
  • 长上下文的对比把窗口压到 60 token，早期轮次才真正掉出窗口：只有窗口 9/30，开摘要和召回 30/30。
  • 改完同一评测跑多遍，再用改动前的代码跑一遍对照；对照也挂的样本算波动，不归因于改动。
8.6 trace 记什么？

通用做法

  • 每一步的输入输出、模型和参数、token 用量、延迟、工具调用和返回、错误；按一轮串成一棵树，能从用户投诉一路下钻到哪次调用。
  • 敏感数据脱敏或只记哈希，按比例采样，设留存期。

Maya 里：LangSmith 自动 trace，配了 key 就开；每个节点、子图、模型调用、工具调用都是 trace 里的一个节点。FAQ 额外打一行检索命中和模型引用的编号，两者的差就是检索噪音。

9.2 prompt 注入怎么防？

通用做法

  • 直接注入来自用户输入，间接注入藏在工具结果、检索段落、网页里，后者更危险，因为用户看不到。
  • 没有一招防住，靠叠加：指令只放 system，外部内容放 user 或 tool，没有指令效力；工具最小权限、读写分开、高危要人确认；输出按 schema 校验；输入层加注入检测分类器。
  • 评测集里放注入样本，看模型会不会照做。

Maya 里：检索段落和用户问题放同一条 user，工具结果是 tool 消息，system 只放规则；user_id 由代码注入，被诱导也只能动当前用户自己的数据；写操作必须用户点确认（见 5.4）。

9.3 幻觉怎么防？

通用做法

  • 缩小判断面：枚举、schema、词表，模型只选不编。
  • 事实只从工具和检索来，说不上来允许「不知道」。

Maya 里：Account 只报工具返回的事实，core 不可用时如实说查不到，写操作结果不确定时读回状态再说；FAQ 见 7.6。

9.4 依赖挂了怎么办？

通用做法

  • 区分核心依赖和增强依赖：核心挂了明确报错，增强挂了降级继续。
  • 每个外部调用设超时；单次工具失败怎么处理见 3.3。
  • 流式响应中途出错发 error 事件再正常收尾，不直接断连。

Maya 里：只有模型是核心依赖，其余都降级。

10 服务底座与生产工程

原则（出处见末尾）
  1. 并发解决 IO 等待，并行解决 CPU。LLM 应用大部分时间在等模型和网络，异步合适；CPU 密集靠多进程。[FastAPI]
  2. 事件循环上不跑阻塞代码。一段 1 秒的同步调用让所有连接一起卡 1 秒；阻塞的交给线程池。[Python]
  3. 流式要端到端不攒：服务端每帧即发，代理不缓冲，长等待发心跳。[MDN, nginx]
  4. 一轮是契约单位。一轮的所有事件共用一个消息 id，开始、进度、正文、错误、结束都挂在它上面。
  5. 成本按 token 算，不按请求算。先省掉不必要的调用，再谈换小模型。[Huyen]

出处：Python · Developing with asyncio；FastAPI · Concurrency and async / await；MDN · Using server-sent events；nginx · ngx_http_proxy_module；Chip Huyen · AI Engineering 第九、十章

10.1 Python Web 栈怎么选？

通用做法：协议、框架、服务器三层，同步一套、异步一套。

同步异步
协议WSGI：app(environ, start_response)，一次调用一个请求，返回即结束ASGI：async app(scope, receive, send)，一个连接可多次收发，期间能让出控制权
框架Flask：一个请求占一个线程，SSE 连接占死线程FastAPI：一个事件循环挂几千连接，pydantic 自动校验
服务器gunicorn：fork 多进程兼进程管理uvicorn：多进程用 --workers，或交给容器编排
适合简单 CRUD长等待、流式推送、高并发 IO

Maya 里：FastAPI 加 uvicorn，一个容器一个进程，进程守护和扩容交给 ECS Fargate。请求校验和模型的结构化输出用同一套 pydantic，类型从入口贯通到图内。

10.2 进程、线程、协程，并发靠哪个？

通用做法

层解决什么代价
进程用多核（GIL 让一个进程同时只有一个线程跑字节码）内存按份复制，不共享状态
线程把同步阻塞代码挪出事件循环受 GIL 约束不能并行算
协程IO 等待时切换，一个线程挂成千个连接只对 IO 有效，一次同步阻塞让全部连接一起卡
  • 协程只在 await 处切换，两个 await 之间不会被打断，大多不用锁。
  • 最常见的线上事故：在 async def 里调了同步 IO（requests、同步数据库驱动）。修法是换异步客户端，或 asyncio.to_thread。

Maya 里：所有 IO 一律异步：httpx 异步客户端、psycopg 异步连接池、节点全是 async def、模型走 ainvoke。

10.3 LLM 流式输出怎么实现？

通用做法

  • 三层接力：模型 SDK 返回 async iterator；服务端 async generator 把每块包成 SSE 事件 yield 出去；StreamingResponse 边产边发。
  • await 向内等上游给下一块，yield 向外交给下游，两头都不攒。
  • 必须是 async generator：普通 generator 里不能 await，普通 async 函数只能 return 一次。

Maya 里：图用 astream 同时听两路：custom 是节点写的进度，原样交出；values 只留最后一份 state，包成结束事件。api 层把事件逐个映射成 SSE 帧，不碰 LangGraph 的接口。

10.4 为什么用 SSE 不用 WebSocket？

通用做法

  • SSE 是普通 HTTP 长响应，单向，CDN、网关、鉴权中间件原样通过，浏览器原生重连。WebSocket 双向，要网关支持协议升级，重连自己做。
  • 对话是「用户发一句，服务端推一段」，单向够用；要双向实时（语音、打断生成）才上 WebSocket。
  • 原生 EventSource 只能 GET；要 POST 带 body 就用 fetch 读流，重连自己做。

Maya 里：SSE，POST 带 JSON body，前端用 fetch 读流。

10.5 多步 agent 的中间状态要不要推给前端？

通用做法：要。路由、调工具、检索、生成每步几秒，用户盯着空白会以为挂了。用独立的进度事件，和正文事件分开，前端按类型渲染，不进消息历史。

Maya 里：每个耗时步骤前发一帧 processing，文案统一一句 Thinking；子图里的进度也能穿到主图（subgraphs=True）。

10.6 反向代理后面流式不生效或被掐断，怎么排查？

通用做法

  • 一次性返回：代理默认缓冲上游响应（nginx proxy_buffering on）。代理侧关缓冲，或响应头 X-Accel-Buffering: no；再确认 gzip 没对 text/event-stream 生效，压缩也会攒块。
  • 一分钟左右断开：nginx proxy_read_timeout 默认 60 秒，算的是两次读之间的间隔。调长超时，或定期发心跳（冒号开头的注释行，或进度事件）。

Maya 里：响应头带 X-Accel-Buffering: no 和 Cache-Control: no-cache，每步发进度帧。

10.7 用户中途关页面、模型中途报错，怎么办？

通用做法

  • generator 由消费方推动：客户端断开后服务器停止迭代，generator 停在上一个 yield，后面的代码不再执行。落库、埋点不能写在最后一帧之后，要放 finally 或后台任务；上游模型调用要跟着取消，否则照样计费。
  • 中途报错不直接断连：发一个 error 事件再正常收尾。一轮的事件共用同一个消息 id，前端据此决定保留半段还是回滚。

Maya 里：图内异常变 error 帧，end 帧照发，流不断；落库在图跑完之后，没跑完的轮次不存，历史里只有完整的轮。

10.8 成本和延迟怎么控？

通用做法：按收益从大到小。

  • 省掉不必要的调用：路径固定的用代码不用模型，能跳过的步骤跳过。
  • 控输入 token：窗口按 token 预算截，旧内容压摘要，只检索需要的段落。
  • 吃缓存：稳定内容放前缀，命中 prompt caching 读价约一折。
  • 按任务选模型：路由、分类、重排这类简单判断用小模型，生成用大模型；常见请求走缓存。
  • 压感知延迟：流式和进度事件让首字节尽早到；独立的调用并行。

Maya 里

  • 省调用：Fashion 计数和 FAQ 检索由代码调，不多一趟模型往返；会话还没说过话时跳过召回；rerank 只用在 FAQ。
  • 控 token：窗口 4000 token 预算，摘要攒够 1000 token 才压一次。
  • 吃缓存：system 只放固定的规则和词表，做缓存前缀。

附 多模态输入

  • 按任务选模型：对话和主 agent 用 gpt-5.6-terra；看图给意见用便宜的 gpt-5.6-luna（detail: low）；多物件检测用 Gemini 2.5 flash，定位框更准；召回不用大模型，用时尚领域的 CLIP 图像向量做 kNN。
  • 意图分叉交给 agent：问「好不好看、怎么搭」调看图工具；要找同款直接调检测工具，不先看一遍图，省一次调用。
  • 图片和坐标不进对话上下文：只有识图模型看图，它出的检测框缓存在代码侧；对话模型只看到编号列表 {idx, categoryCode, description}，挑出要保留的编号，最终结果由代码按编号重建。省 token，对话模型也改不了坐标。
  • 两段式，选件是终态不是 interrupt：对话里检测出物件、在图上画出可点的框，本轮结束；用户点框后由前端裁剪，经 core 调召回接口，不再回到 agent。
