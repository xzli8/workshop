0 总览

两分钟版本

这个系统是美团医药 C 端的 BFF 层，聚合几十个领域服务给前端。我接手时是硬编码，我带 5 个人分三步重构。第一步把聚合逻辑拆成可复用的批式 Unit，接口内置超时、强弱依赖和降级，用分层并行引擎加配置化编排，先解决开发效率，这一步允许不是最优解。第二步发现分层的 barrier 拖长了延迟，把调度换成 DAG，每个 Unit 只等自己的前驱、前驱完成就触发，失败沿边传播，TP99 降了三成。第三步发现引擎再快也解决不了前后端耦合，因为响应形状仍在设计期由配置固定，于是引入 GraphQL schema 作为契约，把决定权交给前端请求期；取数调度不换，查询分析把选中字段翻译成 Unit 子图交给 DAG 引擎跑，fetcher 从结果仓读，没选的字段对应的 Unit 不执行。整个过程用流量对比灰度迁移，零停机。三步分别对应 BFF 的聚合、编排、整形三个职责。

1 阶段 0：硬编码 BFF

1.1 问题

每个页面一个接口，接口内部各自组织并行调用、各自处理容错、各自拼装。两段代码都是合格工程师写的，问题全在两份之间（单元名和业务细节是示意，替换为真实的）：

// StoreDetailService
CompletableFuture<StoreDTO> storeF = supplyAsync(() -> storeRpc.getById(storeId), pool);
CompletableFuture<UserCtx>  userF  = supplyAsync(() -> userRpc.getCtx(userId), pool);

CompletableFuture<Delivery> deliveryF = storeF.thenCombine(userF, (s, u) -> {
    Delivery d = deliveryRpc.estimate(s.getLocation(), u.getLocation());
    if (u.isMember()) d.setFee(memberDiscount(d.getFee()));      // 会员减免规则写在这里
    return d;
});
CompletableFuture<List<Promo>> promoF = storeF.thenCombine(userF, (s, u) -> {
    try { return promoRpc.listByStore(storeId, u.getMemberLevel()); }
    catch (Exception e) { return emptyList(); }                   // 弱依赖降级，就地 try/catch
});
CompletableFuture<List<Sku>> skuF = supplyAsync(() -> productRpc.listByStore(storeId), pool);
CompletableFuture<Map<Long, Stock>> stockF = skuF.thenApply(skus -> stockRpc.batchGet(ids(skus)));

allOf(deliveryF, promoF, stockF).get(800, MILLISECONDS);         // 整个接口一个超时
return assemble(storeF.join(), deliveryF.join(), promoF.join(), skuF.join(), stockF.join());

// StoreListService
List<StoreDTO> stores = storeRpc.batchGet(storeIds);
UserCtx u = userRpc.getCtx(userId);
Map<Long, Delivery> ds = deliveryRpc.batchEstimate(locations(stores), u.getLocation());
                                                                  // 批量了，但忘了会员减免
Map<Long, List<Promo>> ps = promoRpc.batchList(storeIds, u.getMemberLevel());
                                                                  // 没有 try/catch，活动服务抖动列表页整页 500
return stores.stream().map(s -> assembleCard(s, ds.get(s.getId()), ps.get(s.getId()))).toList();
  • 根因。代码里的毛病单看都能靠"仔细"避免，但它们是同一个根因的症状：聚合逻辑以页面为组织单位，页面之下没有可复用的单元。同一段规则、同一个下游的容错和超时、同一组依赖的调度，每个页面各有一份，正确性靠每个人在每处都仔细。
    • 症状一：漂移。规则、降级、超时各有 N 份，N 是页面数，改一处漏一处（e.g.: 会员减免、活动降级只在详情页有 etc.）。
    • 症状二：调度手工推导。一个 thenCombine 同时表达业务逻辑、依赖关系、并行策略，并行结构由开发者从依赖手推，推得好坏看人，改一个依赖就要动结构，每个页面各推一遍。
    • 症状三：新页面成本是全量。加一个页面，同一批调用再写一遍，第三份漂移开始（e.g.: 加购物车页，配送费、活动、库存的调用都要再写一遍）。
  • 结论。要消掉的是"一个页面一份实现"，改成"一个逻辑一份实现"：规则、降级、超时、依赖声明随单元只写一处，单元带调度元数据，并行结构由引擎从声明推导。

1.2 方案

方案选型

方案是什么优点缺点
抽公共方法【不选】把重复的规则、降级、超时抽成公共方法或工具类，页面接口继续各自编排 future改动最小，不停业务，随手就能做只解决规则复用，解决不了调度：同步方法表达不了"依赖 A、B 的输出，可与 C 并行，超时 200ms，弱依赖失败给空列表"，编排仍在方法外手写、每页一份；症状二、三原样保留
一次重写到最终形态【不选】直接按目标架构（批式 Unit + DAG 引擎 + GraphQL 契约）重写整层，一次切换只迁一次，没有中间形态DAG 引擎要做节点级触发、失败沿边传播、子图跳过、deadline 下推，周期长；GraphQL 要前端团队配合，不是后端单方面能推；长时间没有可上线的收益，风险集中在一次切换
三步演进【选定】Unit 划分和依赖梳理做一次，分层引擎先上线止血，再换 DAG 引擎，最后引入 GraphQL，每步流量对比灰度每步有独立收益，分层几天能上；两代引擎读同一份 dependsOn 声明，前置工作不重做；风险分散，业务迭代不停分层引擎是已知的非最优解，注定被替换；三次迁移、三次对比验证的工作量

三步走 + 流量对比迁移

短期
棘手问题攻坚。目标是低成本快速止血，允许不是最优解。
中期
通用能力建设。优化上一步的已知缺陷，构建当前最优解。
长期
能力上限探索。继续优化架构，探索系统边界。
迁移
流量对比：老服务收到请求后同时转发一份给新服务，对比两边的返回结果，不一致就记日志（时间戳这类非确定字段比对前排除或归一化）。线上真实流量做验证，用户始终拿老服务的结果，新服务有问题不影响用户。日志里的不一致收敛到零后再切流（可随时回切）。

2 阶段 1：Unit 化 + 分层并行引擎

2.1 问题

硬编码方式下，聚合逻辑以页面为组织单位，页面之下没有可复用的单元，会导致漂移、调度手工推导、新页面成本是全量这三个问题。

2.2 方案

把一个页面接口拆成三层：Unit 承载取数逻辑和调度元数据，页面配置只是一份 Unit 清单，引擎从声明推导执行结构并统一执行横切逻辑。硬编码里混在一起的四样东西各归一层：业务逻辑和容错进 Unit，依赖变成 Unit 上的声明，页面变成配置，并行结构由引擎推导。

Unit
一个逻辑一份实现。取数逻辑加调度元数据（依赖、超时、强弱、降级值）只写一处。
页面配置
一个页面一份清单，列出要输出的 Unit，不写依赖、不写顺序。
引擎
加载配置时从 dependsOn 声明推导出图并校验，运行时按图并行执行，超时、降级、线程池、埋点统一在这里做。

Unit：取数逻辑加调度元数据

Unit 是批量输入输出（e.g.: 列表页传 20 个 storeId、详情页传 1 个 etc.），相同的取数逻辑加调度元数据（依赖、超时、强弱、降级值）只写一处。

interface Unit<K, V> {
    Set<K> inputKeys(RequestContext ctx);     // 推导本次要传给 fetch 的输入 key：来自请求参数或上游结果，空集则不执行
    Map<K, V> fetch(Set<K> keys, RequestContext ctx);
    Set<Class<? extends Unit>> dependsOn();   // 依赖声明
    Duration timeout();                        // 单元级超时
    boolean isStrong();                        // 强弱依赖
    V fallback(K key);                         // 弱依赖失败时的降级值
}
Unit输入输出依赖强弱
StoreBasestoreIds名称、logo、评分、经纬度无强
UserCtxuserId位置、会员等级无强
OpenStatusstoreIds营业中 / 休息中 / 已打烊StoreBase强

SkuListstoreId分类和商品列表无强
StockskuIds库存SkuList强

页面配置：只列 Unit 清单

store_list:    [StoreBase, UserCtx, OpenStatus, DeliveryEstimate, PromoTags]
store_detail:  [StoreBase, UserCtx, OpenStatus, DeliveryEstimate, PromoTags, SkuList, Stock, FinalPrice]
cart_page:     [UserCtx, Stock, FinalPrice]

配置和依赖是两层东西：依赖归 Unit，清单归页面，补齐和校验归引擎。

  • 依赖写在 Unit 上。dependsOn 是 Unit 的静态属性，和页面无关。
  • 页面配置只是清单。只列最终要输出的 Unit，不写依赖、不写中间 Unit（e.g.: cart_page 只写 [UserCtx, Stock, FinalPrice]）。
  • 引擎补齐并校验。加载配置时对清单里每个 Unit 的 dependsOn 做传递闭包，补上中间依赖（e.g.: 给 cart_page 补进 SkuList），同时校验环和未注册的 Unit。
  • 复用由此成立。一个 Unit 只有一份实现，改一次所有引用它的页面同时生效（e.g.: OpenStatus 的"临时休息"逻辑改一次，三个页面一起变）。

引擎：从声明推导执行结构

配置展开后是一张以 Unit 为节点、dependsOn 为边的图。这一阶段的引擎按层消费它：Kahn 算法逐轮摘入度为零的节点，每轮一层，同层并行、层间串行；摘不完就是有环，环检测顺带就有了。层号不手写，它是依赖推出来的，手写就是把依赖抄第二遍。

Layer 1:  StoreBase   UserCtx   SkuList                 ← 互不依赖，并行
Layer 2:  OpenStatus  DeliveryEstimate  PromoTags  Stock
Layer 3:  FinalPrice

这张图不属于某一代引擎。分层引擎给每个节点算"从入口到它的最长路径长度"，长度相同的放一层；阶段 2 的 DAG 引擎给每个节点记未完成前驱数，前驱每完成一个减一，减到零立刻触发。两代引擎读同一张图，只是消费方式不同，所以换引擎时 Unit 代码和页面配置都不用动。

失败处理属于 Unit，不属于调度器

拆成 Unit 的那一刻，原来写在方法里的 try/catch 没地方放了，容错必须变成 Unit 的声明、由引擎统一执行。所以这些能力是随 Unit 一起出现的，定义在接口上，后面换引擎也不动：

  • 单元级超时，而不是整个接口一个超时。
  • 强弱依赖：弱依赖失败给降级值继续跑，强依赖失败整个请求失败。这是业务属性（e.g.: 库存是强的，推荐是弱的）。
  • 降级值：弱依赖失败时返回什么。
  • 舱壁隔离：Unit 声明所属下游，引擎按下游建线程池，一个下游慢不拖死别的下游。
  • 依赖校验：加载配置时检测环、检测未注册的 Unit。

调度器只负责"什么时候跑谁"，失败了怎么办由 Unit 自己说。分层和 DAG 两代引擎改变的是失败的传播范围，不是失败策略本身。

2.3 效果

开发迭代效率提升约 30%，口径是需求平均交付周期缩短约 30%。稳定性上，弱依赖故障由引擎统一降级，不再拖垮整页，数字见第 5 节追问 7。

2.4 遗留：层是 barrier

第 2 层要等第 1 层全部完成才能开始。一个慢 Unit 拖住整层，总延迟是各层最慢之和，而不是关键路径之和。

面试追问

逻辑单元具体是什么？举个例子。
OpenStatus 或 DeliveryEstimate。列表页和详情页原来各有一份实现，逻辑漂移出过线上不一致；抽成 Unit 后配置引用，一份实现。顺手带出 Unit 是批式接口。
分层怎么算的？
Kahn 算法逐轮摘入度为零的节点，每轮一层：没有依赖的是第 1 层，只依赖第 1 层的是第 2 层，以此类推。摘不完就是有环，配置加载失败。
一个 Unit 挂了怎么办？
看强弱：弱依赖返回降级值，本层照常收口；强依赖失败请求整体失败。超时按 Unit 配置，线程池按下游隔离。

3 阶段 2：DAG 调度

3.1 问题

分层 barrier 造成无谓等待。同样的下游、同样的机器，纯靠调度顺序有 30% 以上的延迟空间。

3.2 方案

方案选型

要换的是一个进程内、请求级的取数调度引擎：一次请求扇出十几到几十个下游 RPC，总预算几百毫秒，引擎自身开销要在毫秒以下，请求结束状态即丢。选型只比这一类，跨进程的工作流引擎（Conductor、Airflow 一类）解决的是持久化、重试和跨机分配，粒度是秒到小时，不在比较范围内。

方案是什么优点缺点
LiteFlow【不选】2020 年开源的组件式规则引擎。业务写成组件，流程用表达式显式编排：THEN 串行、WHEN 并行、SWITCH/IF/FOR 分支循环，规则可热更新，组件间不传参，靠每请求一个共享上下文读写成熟、社区大；规则热更新和多脚本适合业务规则频繁变化的场景；表达式可读并行结构由开发者手写，不是从依赖声明推导，改一个依赖要动表达式；WHEN 是 fork-join，所有分支完成才进下一步，等价于分层加 barrier，只能到阶段 1 的形态；共享上下文就是黑板，数据线程安全由使用方负责，隐式依赖无法校验；没有按边的强弱依赖，节点级超时 v2.11（2023-08）才提供，且语义是停止等待而非 deadline 下推；定位是规则引擎，取数调度不是它的问题域
京东 asyncTool【不选】2020 年公开的多线程编排框架，出自京东主 App 后台。每个任务包成 WorkerWrapper，代码里用 builder 声明 depend/next；节点完成后触发后继，must 区分强弱依赖；失败或超时返回默认值，依赖失败快速失败节点级触发、无 barrier，强弱依赖和默认值降级的思路与阶段 2 一致；无锁、轻量，京东生产验证超时只有全组一个，没有节点级超时和 deadline 沿边下推；线程池只有一个且默认无界，做不了按下游舱壁隔离；编排在代码里每请求现场拼装，没有配置化、传递闭包和环校验；结果按字符串 id 从 Map 取，依赖未执行时为 null，没有类型化输入契约，也没有批式抽象；它是 CompletableFuture 上的薄封装，缺的这几件都是调度器内部行为，外面补不上
阿里 compileflow【不选】2020 年开源的 BPM 流程引擎，淘宝 TBBPM 的演进，流程用 TBBPM/BPMN 2.0 描述，编译成 Java 代码执行，纯内存无状态面向交易、履约类业务流程建模成熟，有可视化设计器，编译执行开销低解决的是业务流程编排，节点是流程步骤，不是数据依赖驱动的取数调度；没有批式单元、强弱依赖、deadline 这些概念，用它要在流程节点里再手写一层并行取数
自研 DAG 引擎【选定】Unit 是"一批 key 到一批 value"的批式取数单元，接口上声明 dependsOn、强弱依赖、超时、降级、所属下游；引擎从声明做传递闭包和环校验，事件驱动 Kahn 按节点触发，失败沿边传播，deadline 下推，按下游建线程池依赖声明和引擎解耦，分层与 DAG 两代引擎读同一张图，可开关切换；失败语义、deadline、舱壁是调度器内部行为，与 Unit 契约一致；批式抽象为阶段 3 的查询子图直接复用维护成本和 bus factor 在自己手里；需要配套节点级 trace、契约测试和文档才能让后来者接手

选型依据。引擎核心是事件驱动 Kahn 加一个 remaining 计数和 CAS 状态机，几百行。工作量在 Unit 契约、失败语义、deadline 下推和按下游的舱壁，这几件是触发那一刻要做的决定，属于调度器内部，无论选哪个现成件都得改它内核。契约层用现成件：阶段 3 的 GraphQL 用 graphql-java，DataLoader 评估过，否决理由见 4.2。原则是标准化的那一层用标准件，贴业务语义的那一层自己控。

节点级触发

依赖关系直接建成有向无环图，每个 Unit 只等自己的前驱完成就立刻执行，不再等整层。dependsOn 声明和页面配置都不变，换的只是引擎消费图的方式（第 2 节）。配置格式在这一阶段升级的是页面级的部分：允许页面覆盖某个 Unit 的强弱和超时（活动标签在列表页是弱依赖，在活动落地页是强依赖），以及按条件决定某个 Unit 是否纳入本次执行（未登录不跑会员价）。延迟从"各层最慢之和"降到"关键路径之和"。

从 Unit 集合到执行

引擎的输入是一组 Unit（阶段 2 来自页面配置，阶段 3 来自查询分析），分三步。

补依赖。工作队列：弹出一个 Unit，把它 dependsOn 里不在集合中的加入队列，直到队列空，得到传递闭包。未注册的 Unit 在这一步抛出。

建图。节点是 Unit，边是 dependsOn，前驱指向后继，每个节点算入度，入度为零的是根。环检测不在请求期做：dependsOn 是静态的，进程启动时对全部注册 Unit 跑一遍 Kahn，有环直接启动失败，请求期取的子图不可能有环。建图是一次 O(节点 + 边) 的计数，结果可以缓存，每个请求只实例化一份状态。

跑图。每个节点一份请求级状态：state 是 PENDING → RUNNING → DONE | FAILED | SKIPPED，用 CAS 迁移；remaining 是未完成前驱数，初值等于入度。

start(plan):
    for node in roots: trigger(node)

trigger(node):
    if !CAS(node.state, PENDING → RUNNING) return          // 已被跳过或已触发
    keys = node.unit.inputKeys(ctx)
    if keys.isEmpty(): complete(node, emptyMap); return    // 上游为空、谓词过滤掉：不发 RPC
    timeout = min(node.unit.timeout, deadline - now)
    if timeout <= 0: fail(node, TimeoutException); return
    pool(node.unit.downstream).submit(() -> node.unit.fetch(keys, ctx))
        .orTimeout(timeout)
        .whenComplete((v, e) -> e == null ? complete(node, v) : fail(node, e))

complete(node, value):
    ctx.putResult(node.unit, value)                        // 写一次
    node.state = DONE
    for succ in node.successors:
        if succ.remaining.decrementAndGet() == 0: trigger(succ)
    checkFinished()

fail(node, e):
    if node.unit.isStrong(): node.state = FAILED; skipSubtree(node)
    else: complete(node, fallbackFor(keys))                // 弱依赖：降级值当正常结果

skipSubtree(node):
    for succ in node.successors:
        if CAS(succ.state, PENDING → SKIPPED): ctx.putResult(succ.unit, emptyMap); skipSubtree(succ)
        // remaining 照常减，否则整图卡住
    checkFinished()

checkFinished():
    未完成节点计数归零，或 deadline 到 → finish()，结果仓里有多少返回多少，迟到的 RPC 结果丢弃
  • 触发条件是"我的前驱全完成"，remaining 减到零那一刻立刻 trigger。这不是拓扑排序，排序产出线性序列，按序列跑就串行了；这是事件驱动的 Kahn 算法，谁入度归零谁跑，同时归零的并行跑。分层引擎是按轮次跑 Kahn，DAG 引擎是按事件跑 Kahn，同一个算法，粒度从轮细到节点。
  • inputKeys 在触发时算，前驱结果此时已就位。返回空集直接完成，"上游为空不发 RPC"和"谓词过滤"落地在这一行。
  • 被跳过的节点也写空结果，否则后继和装配器读不到值。
  • 没有调度线程。fetch 提交到该 Unit 所属下游的线程池，回调在完成线程上执行，trigger 后继也在这个线程上。

节点状态机与 CAS

每个节点一个 AtomicReference<State>，五个状态，合法迁移四条，终态不回头：

PENDING ──trigger──► RUNNING ──fetch 成功──► DONE
   │                    └────fetch 失败/超时──► FAILED（强依赖）或 DONE（弱依赖，带降级值）
   └──skipSubtree──► SKIPPED

三处竞争决定了不能用普通赋值。trigger 对 skip：节点 A 的一个前驱刚把 A 的 remaining 减到零准备 trigger，同时另一分支强依赖失败正在 skipSubtree 要把 A 标成 SKIPPED，两个线程都想改 A，谁先 CAS 成功谁生效，另一个直接返回；没有 CAS 就可能先标 SKIPPED 又被覆盖成 RUNNING。重复 trigger：remaining 的 decrementAndGet 保证只有一个线程看到零，trigger 仍以 CAS 为准，一个节点最多发一次 fetch。完成对 deadline：deadline 到了 finish 收尾后，晚到的 fetch 回调还会调 complete，CAS(RUNNING → DONE) 失败就说明请求已收尾，结果丢弃。

enum State { PENDING, RUNNING, DONE, FAILED, SKIPPED }

final class Node {
    final Unit<?, ?> unit;
    final AtomicReference<State> state = new AtomicReference<>(State.PENDING);
    final AtomicInteger remaining;                 // 初值 = 入度
    final List<Node> successors;

    boolean tryStart()  { return state.compareAndSet(State.PENDING, State.RUNNING); }
    boolean trySkip()   { return state.compareAndSet(State.PENDING, State.SKIPPED); }
    boolean tryFinish(State terminal) {            // DONE 或 FAILED
        return state.compareAndSet(State.RUNNING, terminal);
    }
}

void onPredecessorDone(Node n) {
    if (n.remaining.decrementAndGet() == 0 && n.tryStart()) run(n);
}

void skipSubtree(Node n) {
    for (Node s : n.successors) {
        if (s.trySkip()) { results.put(s.unit, Map.of()); skipSubtree(s); }
        s.remaining.decrementAndGet();             // 照常减，避免整图卡住
    }
}

remaining 和 state 是两个原子量，不需要一把锁包住：remaining 归零只决定"要不要尝试启动"，最终裁决在 state 的 CAS 上。整图完成用一个未终态节点计数，每进入一个终态减一，归零即 finish；deadline 到时也 finish，后到的回调全部在 CAS 上失败。

跑完之后，阶段 2 由页面装配器读结果拼响应；阶段 3 由 GraphQL 执行器读结果仓整形，见 4.2。

备选与取舍

保留分层引擎，按分支拆成多条独立的分层流水线，最后汇总。否决理由：只去掉了跨分支的等待，每条链内部仍是层加 barrier，最慢的 Unit 还是决定整层何时结束；而要正确拆分支，先得算出哪些 Unit 属于同一条链，这一步就是在建 DAG，图建好了再折回分层跑，等于走一半停下。

失败沿边传播

DAG 没有发明失败处理，它把阶段 1 的策略沿图的边重新实现了一遍，粒度从"层"细到"边"，并多了两件分层模型不需要的事：取消和 deadline 传播。

分层并行DAG
强依赖失败整个请求终止只取消它的下游子图，兄弟分支继续，最后拼部分结果或整体失败
弱依赖失败本层照常收口给降级值，后继照常执行
超时预算每层一个固定值请求级 deadline 下推：Unit 实际超时 = min(自身配置, 剩余预算)
取消层结束即结束强依赖失败时下游子图整体跳过，不再发起 RPC；在途 RPC 不硬杀

deadline 下推与子图取消

分层模型只需要"每层一个超时"，DAG 把超时和取消都做到了节点粒度，具体是三件事。

请求级 deadline 下推。请求进入时按页面预算（如详情页 800ms）算出一个绝对截止时间放进 Context。每个 Unit 执行前先算剩余预算，剩余为零直接走降级、不发 RPC；否则用"自身配置超时"和"剩余预算"里较小的那个作为本次 RPC 的超时。这样各层超时不会相加超过页面预算，上游已经放弃的分支下游也不会白跑。

long remaining = ctx.deadlineNanos - System.nanoTime();
if (remaining <= 0) return fallbackOf(unit);              // 预算耗尽：直接降级，不发 RPC
long timeout   = Math.min(unit.timeoutNanos, remaining);  // per-call 超时，而不是配置里的固定值
return rpcClient.callAsync(req, timeout);

Dubbo 通过 RpcContext 附件传单次超时；Thrift 同步客户端按超时分档持有多个 client 实例，或用异步客户端。gRPC 的 Context deadline 天然自动向下游传，面试可以拿它做类比。

子图取消。每个节点是一个状态机：PENDING、RUNNING、DONE、FAILED、SKIPPED。强依赖节点 FAILED 时，沿出边把所有后继 CAS 到 SKIPPED，被跳过的节点在触发检查时直接用降级值完成，不再发起 RPC；兄弟分支不受影响。CAS 保证"被跳过"与"正常完成"互斥。客户端断开时在 Servlet 异步回调 onError 和 onTimeout 里把整个请求标成取消，后续节点看到标记同样不再发 RPC。

在途 RPC 不硬杀。这里有个常见误解：CompletableFuture 的 cancel(true) 不会中断底层任务，只是把 future 标成取消、让后面的 thenApply 链收到 CancellationException。真要停掉在途 RPC 得拿到线程池返回的 FutureTask 去中断阻塞 IO，或者依赖异步客户端自带的 cancel。评估后没做：RPC 通常几十毫秒就返回，收益小；中断线程池线程有状态风险；线程池已经按下游隔离，爆炸半径本来就有界。让在途结果"到了没人要"是更稳的选择。

3.3 效果

核心接口 TP99 平均降低 30-40%。数字来自节点级 trace：每个节点记录开始、结束、耗时、状态，整条请求输出甘特图式的时间轴，切换前后对比关键路径长度得到收益。

报 TP99 而不是平均，因为 barrier 是"取最大值"：每层耗时等于该层最慢的 Unit，而最慢的是当次恰好抖动的那个，抖动被逐层累加到接口尾部，barrier 放大的是长尾。DAG 拆掉 barrier 后一个 Unit 抖动只拖慢自己的后继，压缩的正是长尾，所以 TP99 降幅大、平均降幅小。

3.4 遗留：形状在设计期固定

引擎已经很快，但响应形状在设计期就固定在配置里，每个端乘每个页面就是一份配置。Web 和 App 要不同字段是两份，加一个端再加一套，改一个字段就要发一次版。形状由构建方在设计期决定，使用方在请求期没有选择权，这个结构不管谁来维护都一样。

面试追问

DAG 怎么处理失败？
先说一句"失败策略在阶段 1 拆 Unit 时就定义在接口上了，DAG 改变的是传播范围"，再讲上面那张表。
强依赖失败后，已经在跑的下游 RPC 真的取消了吗？
没有硬杀，也不该硬杀。取消的是"还没启动"的子图：后继节点 CAS 到 SKIPPED，不再发 RPC。已在途的 RPC 让它自然返回后丢弃。原因见上文：cancel(true) 停不掉底层任务，中断线程池线程有风险，RPC 本身几十毫秒就回，线程池按下游隔离已经限住了资源占用。deadline 下推保证了在途 RPC 的等待时间不会超过请求剩余预算。
怎么调试一条 DAG 请求？
每个节点记录开始、结束、耗时、状态，整条请求输出一张甘特图式的 trace，能一眼看到关键路径在哪，也是 TP99 收益的量化依据。
怎么保证配置改了不出事？
加载时校验环和未注册 Unit，校验不过配置不生效；配置版本化可回滚；流量对比不只用于服务迁移，配置变更也走一遍新旧对比再切。

4 阶段 3：GraphQL 契约

4.1 问题

痛点不是谁拥有这一层，换团队维护成本只是转移。痛点是响应形状在设计期固定在配置里，每端每页一份，改形状就要发版。GraphQL 把形状的决定权挪到请求期，一份 schema 服务所有端，只有数据能力变化才发版。

4.2 方案：GraphQL schema 作为契约

GraphQL 不是替代 BFF，它就是 BFF 的一种形态。三个阶段都是 BFF：硬编码的、DAG 编排的、schema 驱动的。

Schema、DataFetcher 和 Unit 的分工

三者分工：Schema 描述形状，不管数据从哪来；Unit 是取数能力，不管谁要；DataFetcher（规范和 JS 生态叫 resolver）是胶水，每个字段一个函数，签名是"(父对象, 参数, 上下文) → 字段值"。

type Store {
  id: ID!
  name: String!            # 来自 StoreBase，平凡字段，默认 fetcher 从父对象读
  rating: Float!
  openStatus: OpenStatus!  # → Unit OpenStatus
  delivery: Delivery!      # → Unit DeliveryEstimate
  promoTags: [Promo!]!     # → Unit PromoTags，弱依赖
  skus(category: ID): [Sku!]!  # → Unit SkuList
}
type Sku { id: ID!  name: String!  stock: Int!  finalPrice: Price! }   # stock → Stock，finalPrice → FinalPrice
type Query {
  store(id: ID!): Store            # → StoreBase
  stores(ids: [ID!]!): [Store!]!   # → StoreBase，批量
}

页面配置文件消失了，列表页和详情页的差别变成两条查询：

# 列表页
{ stores(ids: [...]) { name rating openStatus delivery { fee eta } promoTags { label } } }
# 详情页
{ store(id: 1) { name rating openStatus delivery { fee eta }
                 promoTags { label } skus { name stock finalPrice { display } } } }

列表页没选 skus，SkuList、Stock、FinalPrice 三个 Unit 根本不会跑。哪些 Unit 执行由前端选的字段决定，这就是"决定权前置到请求期"的具体含义。

字段和 Unit 的绑定在 graphql-java 里叫 RuntimeWiring，每个非平凡字段配一个 fetcher。阶段 1 的配置是"页面 → Unit 列表"，阶段 3 换成"字段 → Unit"，粒度从页面细到字段，这张映射表是 4.2 查询分析的输入。

schema 管形状，DAG 管取数

为什么不让 GraphQL 执行器调度取数

最直接的接法是每个 fetcher 里调对应 Unit 的 fetch。执行器逐字段调用，50 个 Sku 的 stock 字段就是 50 次 Stock.fetch，各传一个 key，N+1 立刻出现。Unit 本来就是批式的，缺的只是"攒 key 的时机控制"。

GraphQL 生态的标准答案是 DataLoader：fetcher 只把 key 放进桶、返回 future，桶满时一次批量调用。Unit 接口 Set<K> → Map<K,V> 和 DataLoader 的批加载函数形状一致，每个 Unit 可以零改造注册成一个 DataLoader。问题在谁决定桶何时发。Java 没有事件循环，DataLoader 自己从不主动发批，graphql-java 用 FieldLevelTracking 决定：把字段树按深度切 level，某层所有 fetcher 都被调过一次就 dispatch 一次。这带来三个后果：

level 1   Query.store                        → StoreBase
          ─── 层末 dispatch ───►
level 2   Store.openStatus / delivery / skus  → 三个 Unit 并行
          ─── 层末 dispatch ───►                 ← Stock 要等 DeliveryEstimate 返回，尽管它只依赖 SkuList
level 3   Sku.stock × 50                      → Stock 一次批量
  • barrier 回来了。往返轮数等于字段树深度，每层耗时等于该层最慢的 Unit。这和阶段 1 的分层 barrier 是同一个东西，层的划分依据从"依赖深度"换成了"字段树深度"。阶段 2 拆掉的东西被重新装回去。
  • 链式调用会悬挂。一个 fetcher 先 load A 再用 A 的结果 load B，第二个 load 发生在本层 dispatch 之后，计数器只听"fetcher 被调用"这一种事件，再没有任何事件触发第二次 dispatch。下面还有层就多一轮往返，是叶子就悬挂到超时。
  • 跨分支依赖表达不了。FinalPrice 需要 SkuList 的输出（父）和 PromoTags 的输出（叔叔分支）。字段树是父到子的单向结构，fetcher 只拿得到 source，拿不到另一支的结果，只能再 load 一次并赌请求内缓存命中。

三条都指向同一个结论：字段树不是好的调度结构，阶段 2 的 DAG 才是。DAG 没有 barrier、依赖边天然表达跨分支、失败传播和 deadline 都是现成的。所以不让 GraphQL 执行器调度取数。

备选与取舍

沿用 graphql-java 的层级计数加 DataLoader，把 dispatch 触发逻辑修掉。这条路评估到了方案层面：悬挂的根因是计数器只听"fetcher 被调用"一种事件，修法有三种，ticker 定时盲发、按上一轮结果动态算预期数多轮 dispatch、跟踪在途回调的静止检测，我们拟定的是静止检测，细节见本节末追问"为什么不直接用 DataLoader"。否决理由：它只修悬挂这一条，barrier 和跨分支依赖是字段树这个调度结构本身的问题，修不掉。修完之后往返数仍等于字段树深度，性能退回分层阶段的水平，阶段 2 的收益全部吐回去。

查询分析怎么做

按 schema 类型走 AST 加查表，不看数据，所以便宜且可缓存。

映射表和 fetcher 同源。注册 fetcher 时顺手登记字段坐标到 Unit 的映射，两者不会漂移；平凡字段（name、rating）不注册，默认从父对象读。

// unitField()：向映射表登记 (Store.delivery → DeliveryEstimateUnit)，并返回一个从结果仓读值的 fetcher

五步。

1. 变量代入    把 variables 按 schema 类型强制转换，代进字段参数和 @include / @skip
2. 展开        选定 operation，内联所有 fragment spread；@skip 为真的分支丢掉
3. 带类型遍历  从 Query 类型出发递归 selection set，每个字段得到坐标 (父类型, 字段名)
              查映射表：命中 → 加入 Unit 集合，并记下该字段的参数；未命中 → 平凡字段，跳过
              union / interface：按 fragment 的 ... on Type 以各具体类型继续遍历
              同一坐标多次出现（递归嵌套、别名）：递归嵌套每层一个节点，别名合并参数进同一节点
4. 补依赖      沿 dependsOn 传递闭包，未注册校验（第 3 节的那段代码）
5. 输出 Plan   { Unit 集合, 参数绑定 }，交给 DAG 引擎

第 3 步按类型走而不是按实例走：Store.skus 下的 Sku.stock 在 AST 里只出现一次，StockUnit 只登记一次，50 个 sku 的 key 由 StockUnit 的 inputKeys 在运行期从 SkuList 的输出推。分析复杂度只和查询文本大小有关，和数据量无关，所以能按 hash 缓存。

前端参数怎么落到 Unit。参数挂在字段上，随字段坐标一起收集进 RequestEnv 的参数表，key 是字段路径。根字段参数变成根 Unit 的初始 key：store(id: 1) 收集为 Query.store.id，StoreBaseUnit 的 inputKeys 读它返回 {1}。嵌套字段参数变成 Unit 的过滤条件：skus(category: "drug") 收集为 Store.skus.category，SkuListUnit 的 inputKeys 从前驱拿 storeId、从 env 拿 category，组成复合 key (storeId, category)，K 可以是任何值对象。变量在第 1 步已代入，到这里都是字面值。别名 a: skus(category: "drug") 和 b: skus(category: "food") 映射到同一个 SkuListUnit，不拆节点，两组参数都记下，inputKeys 产出两个复合 key 一次批量发出，fetcher 按各自字段路径取对应 key。

这个设计归成两点：取数怎么跑，哪些不用跑。

  • 取数还是阶段 2 那套，只加了入口和出口。DAG 引擎、失败传播、deadline 下推、子图跳过、节点级 trace 原样不动，往返数等于子图关键路径而不是字段树深度。入口是查询分析，一次 selection set 遍历加查表，把选中字段翻译成 Unit 子图。出口是结果仓 Results，请求生命周期内的内存 map，fetcher 拿父对象 id 去里面取值，没有 IO。结果仓同时定下了 Unit 之间传数据的规则：按生产者索引，key 是 Unit 类型，值类型由 Unit<K,V> 泛型定；引擎在 fetch 返回后写入一次，值不可变；下游只能读 dependsOn 里声明过的前驱，读未声明的抛异常。请求环境（userId、设备、locale、deadline、traceId）单独放只读的 RequestEnv，Unit 不能写。这是 GraphQL 父到子传参的推广：输入来源受限、有类型，但允许多个父，跨分支依赖就是多一条边。Unit 的取数逻辑不动，读输入的方式统一替换成从结果仓按前驱读，接口最终形态： 
    interface Unit<K, V> {
    Set<K> inputKeys(RequestEnv env, Results in);         // 推导本次要传给 fetch 的输入 key：来自请求参数或前驱结果
    Map<K, V> fetch(Set<K> keys, RequestEnv env, Results in);
    Set<Class<? extends Unit>> dependsOn();
    Duration timeout();  boolean isStrong();  V fallback(K key);
}
// in.of(SkuListUnit.class) → Map<Long, List<Sku>>，SkuListUnit 不在 dependsOn 里则抛异常
    结果仓是两层 map，外层 key 是生产者 Unit 的类型，内层就是该 Unit 批式输出的 Map<K,V>。详情页跑完后： 
    Results
├─ StoreBaseUnit  → { 1 → Store{name, rating, ...} }
├─ SkuListUnit    → { 1 → [Sku 101, Sku 102, ...] }          key 是 storeId
├─ StockUnit      → { 101 → Stock{...}, 102 → Stock{...} }   key 是 skuId
└─ FinalPriceUnit → { 101 → Price{...}, 102 → Price{...} }

下游 Unit 读：in.of(SkuListUnit.class).get(storeId)          前提 SkuListUnit ∈ dependsOn
fetcher 读：   results.of(StockUnit.class).get(sku.getId())   Sku.stock 字段，父对象是 Sku
    of 的签名 <K,V> Map<K,V> of(Class<? extends Unit<K,V>> producer) 用泛型带出内层类型，取出来就是 Map<Long, Stock>，不用强转。同一个 Unit 类在查询里多路径出现（递归嵌套）时按节点存，节点由字段路径标识，fetcher 按自己的路径读。
  • 不需要的不执行，开销摊掉。三层裁剪：前端没选的字段，查询分析在执行前排除，SkuList 及其后继不进列表页的子图；上游结果为空的，key 沿边传递，Stock 拿到空 key 集合不发 RPC；按数据内容取舍的，写在 Unit 的 inputKeys 里，按类型路由（搜索结果里商家 id 给 StoreBase、商品 id 给 ProductBase）、谓词过滤（药店才进 PrescriptionInfo）、多上游联合判断，子图只要求候选 Unit 能事先枚举，谁真正执行由数据决定。查询里的嵌套深度是显式写出的，规范禁止 fragment 循环引用，所以子图总能在执行前确定，原生执行的惰性求值没有多覆盖的情况。每请求的分析开销靠缓存：graphql-java 的 PreparsedDocumentProvider 按查询文本 hash 缓存 parse 和 validate 结果，查询分析的输出挂同一个 key；变量只影响 @include 和 @skip，缓存的是带条件节点的子图模板，请求期按变量裁一次。线上查询就几十条，稳态下三步都不花 CPU。

4.4 遗留：GraphQL 的代价

  • N+1：Unit 天然批式、由 DAG 按批调度，不存在。
  • 每请求 parse + validate + 查询分析：多几毫秒 CPU。按查询 hash 缓存三步的结果，见 4.2。再加 persisted query：前端构建期把查询注册到服务端换 hash，线上只传 hash 和变量，省掉查询文本的传输，保证缓存必命中，同时充当查询白名单。
  • 恶意深层查询：前端能选字段就能写深度嵌套。加了查询深度和复杂度上限，超限在 validate 阶段直接拒绝；线上只放行已注册查询，未注册查询只在测试环境允许。
  • HTTP 缓存失效：POST 请求不走 HTTP 缓存，需要应用层缓存或 GET + persisted query。
  • schema 治理：字段由谁拥有、废弃字段怎么下线、breaking change 怎么审。三件事都落在已有的两个机制上：字段到 Unit 的映射，和 persisted query 注册库。
    • 字段归属跟着 Unit 走。每个字段注册时必须绑定一个 Unit（4.2 的 unitField()），字段的 owner 就是 Unit 的 owner，不另设一套归属表。schema 文件按业务域拆（商品、价格、营销、门店、评价），进 git，每个域文件配 CODEOWNERS，改字段必须该域后端审批。形状由前端提，字段由后端定义：前端在查询里选什么是自由的，往 schema 里加什么不是。
    • 废弃字段按引用计数下线。线上只放行已注册查询，所以每个字段有哪些查询在用、这些查询属于哪些端和哪些客户端版本，注册库里是精确的，不用猜。流程三步：字段标 @deprecated(reason)，工具链在前端构建期对引用该字段的查询报 warning；注册库里引用该字段的查询归零，或引用它的客户端版本占比低于阈值且已停止维护，才允许删；删字段是一次 schema 变更，走下面的评审。不做 schema 版本号，GraphQL 的约定就是单一 schema 持续演进，版本靠字段级废弃而不是 v1/v2。
    • breaking change 由 CI 用注册库判定。合并 schema 变更前 CI 做两件事。一是 schema diff 分级：加字段、加可选参数、加枚举值是安全的；删字段、改字段类型、输出字段 nullable 改 non-null 之外的方向、输入加必填参数是破坏性的，直接拦。二是拿注册库里所有仍在线的查询对新 schema 跑一遍 validate，任何一条不通过就是破坏性变更，不看分级表也能拦。第二条是主判据：一个变更是否 breaking，定义就是有没有线上查询会失效，注册库让这个定义可以机械执行。破坏性变更要走废弃流程，不能直接合并。

面试追问

GraphQL 不就是另一种 BFF 吗？
是。它是 schema 驱动的 BFF，替代的是"后端按页面手写接口"这种形态，不是替代 BFF 这一层。
GraphQL 和第二阶段的 DAG 引擎是什么关系？
GraphQL 拿走的是"谁决定形状"，取数调度没换。查询分析把选中的字段翻译成 Unit 子图交给 DAG 引擎跑，fetcher 从结果仓读。Unit、依赖、失败传播、deadline 全是阶段 2 的。
为什么不直接用 DataLoader？评估过怎么修它吗？

三条，见 4.2：层级 dispatch 是 barrier 再现；链式 load 会悬挂；字段树表达不了跨分支依赖。悬挂那条我们评估到了方案层面，被追问时按下面讲。

悬挂的根因。Java 没有事件循环，DataLoader 自己不发批，graphql-java 按字段树层级计数，某层 fetcher 都调过一次就 dispatch 一次。链式 load 的第二个 load 发生在 dispatch 之后，计数器只听"fetcher 被调用"一种事件，再没有事件触发第二次。下面还有层就多一轮往返，是叶子就悬挂到超时。

三种修法。共同前提是层级 dispatch 只发一次的机制不动，改的是"什么时候再发一次"。

ticker 定时
官方做法		预期数动态化静止检测
思路每隔几毫秒检查一次，有 pending key 就 dispatch。JS 版 DataLoader 按事件循环 tick 批处理、graphql-java 的 ScheduledDataLoaderRegistry 都是这个思路识别链有几步，每层 dispatch 多轮；每轮的预期 load 数按上一轮返回的数据量算，凑齐就发不预测数量，跟踪在途的 fetcher 回调数；归零且有 pending key 时 dispatch
再发一次的依据时间计数到达预期没有任何回调在跑
往返数不确定，取决于 tick 间隔与 RPC 耗时的关系恰好等于链长恰好等于链长
批质量可能碎：tick 到了但 key 还没到齐满批满批
链长未知或动态天然支持不支持，必须能算出预期天然支持
条件性不发 load、异常天然支持预期算多了凑不齐，需改为按阶段完成计数天然支持

我们拟定的是静止检测。只维护一个"在途"计数，记已被触发、正在执行、尚未完成的回调。规则三条：在途为零且某个桶非空则 dispatch；批返回唤醒回调在途加一，回调结束减一，回调期间发的新 load 让桶再次非空；在途为零且所有桶为空则本层结束。

50 个 fetcher 调完 → 在途 0，promo 桶 50 个 key → dispatch #1
批返回 → 50 个回调被触发 → 在途 50
每个回调执行 priceLoader.load(...) 后结束 → 在途逐个 -1
在途归 0，price 桶 50 个 key → dispatch #2
批返回 → 没有更多回调 → 在途 0，桶全空 → 本层结束

全程没有 N 和 batchSize，因为它不预测。名字来自分布式终止检测。三个细节决定漏不漏：事件来自包装类型，fetcher 返回框架的 ChainedFuture，thenCompose、thenApply 包一层在此登记和注销，不碰 JDK 内部；登记先于注销，回调里再挂新 hop 时新 hop 的加一必须在当前回调的减一之前，否则瞬时归零误触发；归零只触发一次，多个回调线程同时减一，用 CAS 保证只有一个线程 dispatch。兜底是层级超时：某层在超时内没静止，强制 dispatchAll，再按弱依赖降级或整体失败，防的是漏包装。

为什么最终没走。它只修悬挂。修完之后每层还是等最慢的 Unit，往返数还是字段树深度，跨分支还是要再 load 一次赌缓存。barrier 和跨分支是字段树这个调度结构的问题，换调度结构才能解，所以取数交回 DAG。这个方案的价值是让我们确认"DataLoader 路线的上限就是分层阶段的性能"，否决得有依据。

union 和 interface 按运行时类型选 Unit，子图执行前怎么确定？
能预取，三步。查询里的 fragment（... on Store、... on Product）已经声明了客户端关心的类型，查询分析把这几个类型对应的 Unit 都放进子图，客户端没写 fragment 的类型不进。父 Unit（如搜索）的输出每条带类型标记。key 沿边传递时按标记路由，商家 id 进 StoreBase、商品 id 进 ProductBase。这就是 StoreBase 和 ProductBase 各自的 key 推导：从搜索结果里按类型标记筛出自己的 id。前提是父 Unit 输出带类型，搜索、推荐这类混合列表的下游本来就返回类型字段。
"药店才查处方信息"这种按数据内容决定要不要查的，怎么预取？
在 PrescriptionInfo 的 key 推导里做：从上游商家结果里筛出药店 id 作为输入，非药店不进，输入为空则不发 RPC。key 推导是任意代码，多个上游联合判断也写在这里。候选 Unit 进子图，数据决定谁真正执行。
评论楼中楼这种递归结构，子图执行前怎么确定？
GraphQL 查询表达不了不定深度：规范禁止 fragment 循环引用，每一层嵌套都要在查询文本里显式写出，replies { replies { replies } } 就是三层。查询分析走 AST 时 Comment.replies 出现几次深度就是几，每次出现登记一个节点，同一个 Unit 类在不同路径上是不同节点，第二层的 inputKeys 从第一层的输出推 key，两个节点之间是普通的边。递归节点需要另一分支的数据，也是多一条边。查询深度上限顺手封住了递归的成本。所以子图总能事先确定，不存在需要惰性取数的字段。
前端团队怎么配合的？schema 谁定？
schema 两边共同评审，字段归属后端（一个字段对应哪个 Unit 的哪个输出），查询归前端。前端按页面写查询，构建期注册成 persisted query 拿 hash，线上只放行已注册查询，注册流程就是前后端的接口评审流程。先用一个核心页面做试点，前端拿到"改字段不用等后端发版"的收益后，剩下页面是前端主动排期切的。
阶段 3 的流量对比怎么做？老接口和 GraphQL 返回形状都不一样
不比响应体，比结果仓。老服务和新服务跑的是同一批 Unit，老服务把每个 Unit 的输出也按 Unit 落一份，转发请求后对比两边每个 Unit 的 Map<K,V>，与响应形状无关。GraphQL 整形层是纯内存的确定性变换，结果仓一致响应就一致，只在试点页面用查询回放做一次端到端校验。
GraphQL 阶段性能有没有变差？
持平。取数仍是 DAG，关键路径不变。多出来的 parse、validate、查询分析按查询 hash 缓存，线上查询几十条，稳态命中率接近 100%。剩下的是一次 selection set 内存遍历和 fetcher 的内存读，微秒级。上线时用流量对比同时比了返回内容和耗时。

1. 5k QPS 用 50 台机器，单机 100 QPS，够吗？为什么是 5 个 set？

4. 过程中遇到过什么问题？怎么解决的？

问题：上下文黑板退化，暴露成 DAG 阶段的偶发 null。阶段 1 的 Unit 通过一个共享的 RequestContext 交换数据：引擎把每个 Unit 的输出放进 ctx，Unit 自己从 ctx 取上游结果。Unit 多了以后 ctx 变成黑板，有人往里塞派生值（会员标记、折扣率），有人读了上游的值却没在 dependsOn 里声明。分层阶段这个错被 barrier 掩盖，前面的层全跑完才进下一层，读到的总有值。换成 DAG 之后触发粒度细到节点，没声明的依赖不再被等待，线上出现只在特定时序下复现的偶发 null。根因一句话：ctx 里的真实依赖多于 dependsOn 声明的依赖，DAG 的边不再等于真实依赖。

止血。阶段 2 当时补齐缺失的 dependsOn，加一条 code review 规则：读 ctx 必须有对应声明。能止住，但靠人。

结构性解决，在阶段 3。引入 GraphQL 时要给 fetcher 一个读 Unit 结果的地方，这逼着回答"Unit 输出的权威存放处是什么"。GraphQL 父到子传参给了方向：输入来源受限且有类型。于是把 ctx 拆成两样东西。请求环境放只读的 RequestEnv，字段数是常量，Unit 不能写。Unit 输出放按生产者索引的结果仓，引擎写一次、值不可变，下游只能读 dependsOn 里声明的前驱，读未声明的直接抛异常。dependsOn 仍然是人写的，机制改变的是写漏之后的后果：从依赖时序、只在线上特定负载下复现的偶发 null，变成和时序无关、测试环境跑一遍必现的异常。多声明不报错，只损失并行度，引擎记录每个 Unit 实际读过的前驱和 dependsOn 对比，声明了没读的打 warning。仓的大小等于子图的 Unit 数，请求结束即丢，不再膨胀。一条纪律：凡是要被两个 Unit 用的数据，就是某个 Unit 的输出，不是上下文字段。

被追"为什么阶段 2 不直接这么改"，答当时优先级是止血，结构改动要动所有 Unit 的读输入方式，放到阶段 3 和 fetcher 的需求一起做，一次机械替换。

5. 上线过程中出过什么线上问题？怎么处理的？

切 DAG 灰度时把下游打限流。阶段 2 切换按 set 灰度，先切一个 set 承接 20% 流量。切完当天高峰，库存 Unit 错误率上升，错误码是下游限流。节点级 trace 直接指到这个 Unit，几分钟内把该 set 的引擎开关切回分层，两代引擎读同一张图，切换不用发版，影响止在 20% 流量的十几分钟。根因：分层引擎里同一下游的几个 Unit 分散在不同层，被 barrier 隔开串行执行；DAG 让它们同时就绪，对该下游的瞬时并发翻倍。按下游建的线程池当时是按分层的并发峰值设的，下游按调用方配的限流阈值也是。barrier 一直在隐含地做流量整形，拆掉它等于给下游加压。处理：舱壁的线程池大小改成按下游给的容量设，语义从"隔离"变成"隔离加限流"；和主要下游逐个重新协商阈值；灰度节奏改成一个 set 观察一个完整高峰再切下一个。上线前多了一步：DAG 切换前用分层阶段的 trace 算每个下游在 DAG 下的理论峰值并发，和下游确认。

流量对比期抓到历史分叉。阶段 1 逐页切流时，对比日志里有一类不一致收不到零：同一段逻辑的几份复制品早已行为不同，优惠价为零时一处返回 0、一处不返回字段，缺货商品一处过滤掉、一处保留并打标。Unit 化后只能有一种行为，对比日志把这些分叉全部暴露出来。处理不是改代码，是逐条拉产品和前端判定以哪份为准，前端按判定结果改渲染，再切流。这一步耗时超过预期，也是"复用等于复制"最直接的证据：复制品的分叉在合并之前没有人知道它存在。

8. GraphQL 阶段为什么没有性能提升？
因为没有空间。BFF 每个端本来就是定制接口，阶段 2 已经跑在关键路径上，GraphQL 换的是形状由谁决定，不是取数怎么跑。这一阶段的目标是解耦，性能约束是不变差，见 4.3。
9. 如果重来一次会怎么做？
两条。阶段 1 就把 Unit 输出按生产者索引、按依赖读，不给黑板留口子，隐藏依赖那次线上问题就不会有。前端更早拉进来：阶段 3 最长的一条是前端逐页改查询，schema 设计如果从第二个月就一起做，第五个月能切的页面会多一倍。
