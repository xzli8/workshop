Maya 重构设计

0 Agent 工程与传统工程

根因（root cause）

Agent 工程与传统工程的全部差异，来自把 LLM 放进了控制流：一个概率性的、以自然语言为接口的、慢而贵且上下文有限的组件，开始决定程序的下一步。（概率性、自然语言接口、资源属性是 LLM 的性质，「放进控制流」是架构选择。不放进控制流只是「用了 LLM 的应用」，放进去才是 agent。）

传统工程对「组件」有四个隐含假设，LLM 逐条打破：

传统工程agent 工程如何处理（业界调研结果）常用实现
确定性
同输入同输出，坏 case 一定可复现		概率性
同输入不同输出，坏 case 不一定复现		无法杜绝，只能记录和约束
  • 全量 trace 记录每步输入输出
  • 评测集加 pass^k 门禁，报可靠性不报单次成功率
  • 缩窄决策点、结构化输出压方差
  • trace 与评测平台：LangSmith、Langfuse、OpenTelemetry GenAI 约定
  • 评测器：LLM-as-judge、DeepEval、Ragas
  • 评测跑在 CI 里
强类型接口
结构由 schema 保证，指令与数据分离		自然语言接口
结构靠约定，指令与数据同一通道，任何位置输出 EOS 都合法		在边界上把软结构变成硬结构
  • 边界处一次解析成类型，工具调用当结构化输出由代码校验执行
  • 分层 guardrail 叠在鉴权之上
  • prompt 当版本化配置，变更过评测
  • 结构化输出：pydantic + 模型侧 structured outputs、instructor
  • guardrail：Guardrails AI、NeMo Guardrails、厂商 moderation API
  • prompt 版本化：LangSmith Prompt Hub 或 git
廉价无界
调用快、便宜、资源不设上限		资源属性
调用慢、按 token 计费、上下文窗口有限		把上下文和调用当预算管
  • 上下文工程：只放高信号 token，记忆分层，压缩与按需检索
  • 流式输出
  • 按任务大小选模型
  • 超时按失败类型定策略
  • 记忆与检索：LangGraph checkpointer / Store，向量库（OpenSearch、pgvector）
  • token 计数与压缩：tiktoken、摘要节点
  • 模型抽象与路由：LangChain 模型接口、LiteLLM
  • 流式：SSE
控制流归代码
组件只返回结果，不决定下一步		输出决定控制流
输出决定下一步做什么、调哪个工具、何时停（架构选择，不是 LLM 性质）		循环归代码，模型只判断意图
  • 显式边与步数上限
  • 每步 checkpoint，可暂停可恢复，节点幂等
  • 执行状态与业务状态单源
  • LangGraph：StateGraph、条件边、recursion_limit、checkpointer、interrupt
  • 同类：OpenAI Agents SDK 的 run loop
  • 持久化工作流引擎：Temporal

概率性、自然语言接口、资源属性三者相互独立；输出决定控制流由前两者叠加放大：自然语言接口让「不调工具、直接 EOS」成为合法输出，概率性让它偶发。

1 Maya

1.1 角色定位

Maya 是 BNTO 的多模态导购 agent，支持用户用自然语言/图片搜索相关服装饰品等潮牌搭配，问账户、订单、FAQ 等相关问题。

2.1.1 边界划分

相邻系统Maya 负责对方负责交互
前端接收一轮对话请求，流式返回结构化消息；历史消息的查询与管理发起请求、渲染消息、处理点击前端经网关调 Maya，SSE 消息契约不变

  • 弹窗与问卷判定：原在 bnto-ai 内判定并持有频控锁，现划归 Context Hub；前端展示回调直接打 Context Hub，不经 Maya。

职责数据源输出边界

  • 鉴权、consent 和画像拉取在 Router 之前的入口节点完成，一轮一次。
  • 天气按路由拉取，作为 Fashion 的一个场景（独立天气入口保留，直达 Fashion，不经 Router）。

  • 历史消息存储
    • 短期：PostgreSQL + pgvector 同库。当前量级追加写无瓶颈，按用户过滤后候选集很小，同库做向量查询不需要 CDC。
    • 长期：写入量上来后，日志迁到追加型日志存储（日志追加负载，宽表或带排序键的 KV 模型），经 CDC 同步到向量索引（搜索负载，倒排加向量索引）。
      • options：追加型日志存储
        方案优点缺点
        DynamoDB【选定】（B-tree + WAL）分区键 session、排序键时间（顺序读和分页是原生模式）；TTL 内建；Streams 即 CDC；托管零运维和厂商绑定
        Cassandra / HBase（LSM-tree）宽表加时间聚簇的模型完全匹配，消息与日志系统的经典选择；写吞吐高；开源可迁出自管集群运维重，HBase 还要拖 Hadoop 与 ZooKeeper；CDC 要另搭
      • options：向量索引
        方案优点缺点
        OpenSearch【选定】按用户过滤后 kNN 加 BM25 混合检索原生支持，用户提品牌名、品类词时关键词比向量准；增量写、按文档删方便；托管版有比纯向量库重；相关性调参要投入
        独立向量库（Milvus、Qdrant、Pinecone 一类）大规模 ANN 性能强，向量专用功能全召回限定在单用户历史内，候选集小，ANN 规模用不上；无原生全文混合；多一个系统
        Vespa混合检索能力最强，向量、全文、结构化过滤一体极重，学习和运维成本高；对单用户小候选集是杀鸡用牛刀
      • conclusion：DynamoDB 存日志，Streams 作 CDC，OpenSearch 做向量索引。
      • tradeoff
        • 托管换锁定：DynamoDB 与 OpenSearch 都用 AWS 托管版，换来零运维和内建的 CDC、TTL，付出和厂商绑定。Maya 本就跑在 AWS 上，可接受。
        • 分开换复杂度：日志与索引分成两个系统各取所长，付出一条 CDC 链路和两套运维。
        • 混合检索换重量：OpenSearch 比纯向量库重、相关性要调参，换来过滤后的向量加关键词混合检索。
  • FAQ 知识库检索
    • 短期：沿用 OpenAI FileSearch，不动，减少本次工作量。
    • 长期：需要按版本失效、评测召回或混合检索时，切到自建 OpenSearch，与历史召回同引擎。
    • options
      方案优点缺点
      OpenAI FileSearch（现状）【短期】托管，零工程；可强制调用，支持属性过滤和文件引用检索发生在供应商侧，命中什么、怎么排序看不到也调不了；只能评最终回答，评不了召回；没有关键词混合；版本失效靠切换向量库或属性过滤，口径管理在供应商边界内
      PostgreSQL + pgvector【不选】与历史消息同库，索引和检索代码复用；过滤与版本是普通列没有原生全文；历史召回长期已定 OpenSearch，知识库再走一条线会多一套索引
      自建 OpenSearch【长期】检索过程全部可见可评；过滤后向量加关键词混合；按版本字段过滤与失效；出处是文档自己的字段；与历史召回同引擎切块、建索引、评测全部自己做；比托管方案多一套运维
    • conclusion：短期沿用 FileSearch，长期视情况切自建 OpenSearch。
    • tradeoff
      • 省工程量换可控延后：沿用 FileSearch 本次零工程，付出的是召回不可见不可评、版本靠供应商机制，这些问题暴露时再切。
      • 切换成本可控：自建的切块、索引、评测和历史召回共用一套，届时边际成本小。

2.2 重构方案

2.2.1 编排

方案选型
方案是什么优点缺点
代码优先的手写循环（现状）【不选】openai-agents SDK 的形态：一个 run loop，模型通过 handoff 和工具调用决定下一步零改动，写法直接控制流在循环体内，终态靠模型自觉，每种终态要单独兜底
持久化工作流引擎（Temporal 类）【不选】面向长时任务的可靠执行：持久化、重试、超时执行可靠性强不提供结构化输出、流式和工具循环的约束；对几秒一轮的对话是多余的重量
LangGraph【选定】把一轮对话写成显式状态图：节点、条件边、子图，自带 checkpoint、interrupt、步数上限、流式控制流在边上不在模型输出里，终态由出口节点保证；Maya 的流程边界有限、画得出来引入新依赖，节点、状态、边全部要重写
对话状态图
  • 循环归代码，模型只判断意图
    • Router 是一次结构化输出：意图枚举，多步时带顺序；走哪条边由代码映射，不解析自由文本。
    • agent 子图内部是工具循环，模型每步只输出结构化决定：调哪个工具、给出结果、还是需要澄清；条件边按字段判定。
    • 首批 Fashion 文本路径的实际实现是节点内代码循环：计数由代码调，模型不决定调不调，只给条件；模型决定调哪个工具留给路径开放的子图（图片、FAQ）。取舍见 3.5.1 与 3.3.2。
    • 工具调用是结构化输出，参数经 schema 校验后由代码执行；工具报错压缩成一条结果写回 state，不把 stack trace 喂给模型。
  • 终态由结构保证
    • 每个子图只有一个出口节点，出口有 schema：Fashion 出检索条件或澄清问题，Account 出结构化事实，FAQ 出带出处的回答。
    • 模型输出不满足出口 schema 时进不了终态：有步数余量就回循环，没有就走澄清出口。模型无法以 EOS 结束一轮。
    • 现状的流末兜底（wait cue、overlay）不再存在：它们兜的是「模型停在半路」，图里没有这条路径。
  • 步数上限与弹窗
    • 每个子图设 recursion_limit；超限进固定的兜底出口（澄清或失败文案），不向用户抛异常。
    • consent 与问卷弹窗是本轮的一个终态：入口节点按 Context Hub 的判定直接出弹窗，本轮结束；用户处理后的下一条消息作为新一轮进入口重新判定（受约束「前端契约不变」；约束解除时改为 interrupt 加恢复接口，本轮原地续跑）。
  • 流式与 SSE 适配
    • 图以 stream 方式运行，三类事件：节点更新（进度）、token（文本流式）、自定义事件（结构化消息）。
    • SSE 适配层在图外，把事件映射到现有消息类型；消息送达时写消息表（受约束「前端契约不变」；约束解除时按终态类型重新定义消息 schema，适配层消失）。

方案是什么优点缺点

3.1 运行时与并发

纪律（出处见末尾）
  1. 事件循环单线程，同一时刻只跑一个 Task，只在 await 处切换。几乎所有 asyncio 对象不是线程安全的，跨线程要用 call_soon_threadsafe / run_coroutine_threadsafe。[Python]
  2. 不要在事件循环上跑阻塞代码。一段 1 秒的 CPU 计算让所有并发 Task 和 IO 一起延迟 1 秒；阻塞的东西交给 executor（asyncio.to_thread）。[Python]
  3. FastAPI 的选择规则：库支持 await 用 async def；库是阻塞的用普通 def，框架放线程池；纯计算用 async def；不确定用 def。[FastAPI]
  4. 并发解决 IO 等待，并行解决 CPU。Web 应用大部分时间在等 IO，异步合适；CPU 密集靠多进程。[FastAPI]
  5. 多进程用 uvicorn --workers，内置进程管理器会重启异常退出的子进程；gunicorn 的 uvicorn.workers 已标记弃用。[uvicorn]
  6. 调试开 PYTHONASYNCIODEBUG=1：记录超过 100ms 的回调，从错误线程调非线程安全 API 直接抛异常；「coroutine was never awaited」警告是忘了 await。[Python]

出处：Python · Developing with asyncio；FastAPI · Concurrency and async / await；uvicorn · Deployment

3.1.1 WSGI 和 ASGI 是什么？

两个都是 Python 的 Web 协议，规定「服务器怎么把 HTTP 请求交给应用、应用怎么把响应交回去」。它们只是接口约定，不是软件。

WSGIASGI
全称Web Server Gateway InterfaceAsynchronous Server Gateway Interface
年代2003（PEP 333 / 3333）2018
接口app(environ, start_response)，同步调用，返回即结束async app(scope, receive, send)，协程，receive / send 可反复调用
能做什么一问一答的 HTTPHTTP、SSE、WebSocket、长连接

区别的根源是接口形态：WSGI 一次调用一个请求，中途不能让出控制权；ASGI 的 receive 和 send 是两个协程，一个连接上可以分多次收发，连接期间还能让出控制权去处理别的连接。

3.1.2 Flask 和 FastAPI 怎么比？

两个都是框架，是写业务代码的地方。Flask 说 WSGI，FastAPI 说 ASGI。

维度FlaskFastAPI
并发模型一个请求占一个线程，等 IO 时线程空转一个事件循环，等 IO 时切去处理别的请求
流式响应能做，但一个 SSE 连接占死一个线程原生，一个事件循环（一个线程）可挂几千个 SSE 连接
参数校验手动取 request.json、自己判空声明 pydantic 模型，自动校验，错了返回 422
类型弱全类型标注，自动生成 OpenAPI 文档
适合简单 CRUD、内部工具高并发 IO、长等待（调 LLM）、流式推送

3.1.4 进程、线程、协程，并发到底靠哪个？

三层各管一件事，一个 Python 服务里可能同时存在。

层单位解决什么代价
进程gunicorn worker / uvicorn --workers / 容器副本利用多核。GIL 限制一个进程同时只有一个线程执行 Python 字节码，多核只能靠多进程内存按份复制，进程间不共享状态
线程线程池把同步阻塞代码挪出事件循环，让它不卡住别人线程切换有开销，受 GIL 约束不能并行算
协程事件循环上的 async defIO 等待时切换。一个线程同时挂成千个连接只对 IO 等待有效；循环上出现一次同步阻塞，所有连接一起卡

协程的运行方式：事件循环是一个死循环，看哪些 IO 就绪（底层 epoll / kqueue），把对应协程从上次 await 处恢复，跑到下一个 await 再挂起。切换只发生在 await 处，是协作式的；线程是操作系统抢占式切换。所以两个 await 之间的代码不会被打断，大多数场景不用锁。

追问常见的两条：

  • 异步能加速 CPU 密集任务吗？不能。协程是单线程切换，CPU 活还是要多进程。
  • 在 async def 里调了同步 IO（requests、同步数据库驱动）会怎样？事件循环停下来等它返回，这个进程里所有正在服务的连接全部卡住。这是异步框架最常见的线上事故。修法是换异步客户端，或显式 asyncio.to_thread() 包到线程池。

3.2 流式输出

纪律（出处见末尾）
  1. SSE 协议就四个字段：event / data / id / retry，text/event-stream，UTF-8，空行分帧；冒号开头的行是注释，用来做心跳。[MDN]
  2. 原生 EventSource 只能 GET，自动重连并带 Last-Event-ID；要 POST 带 body 就用 fetch 读流，重连自己做。[MDN]
  3. HTTP/1.1 下每个域名的 SSE 连接上限 6 个，跨标签页共享；HTTP/2 默认 100。[MDN]
  4. 服务端每帧写完即 flush，响应头 Cache-Control: no-cache，并检测客户端是否已断开。[MDN]
  5. 反向代理默认缓冲上游响应（nginx proxy_buffering on）。关法两种：配置 off，或响应头 X-Accel-Buffering: no，后者可被 proxy_ignore_headers 屏蔽，配置更可靠。[nginx]
  6. proxy_read_timeout 默认 60 秒，是两次读之间的超时，不是整个响应的。模型思考超过一分钟没吐帧，连接就被代理掐断，所以长等待要发心跳。[nginx]
  7. 响应后的收尾用 BackgroundTasks：响应返回之后执行、同进程、不持久化不重试；要可靠就上任务队列。[FastAPI]

出处：MDN · Using server-sent events；nginx · ngx_http_proxy_module；FastAPI · Background Tasks

3.2.1 LLM 流式输出到前端是怎么实现的？

三层接力：模型 SDK 返回一个 async iterator；服务端用 async generator 把每个 chunk 包成 SSE 事件 yield 出去；StreamingResponse 边产边发。

async def run_turn(turn, req):
    yield turn.start()
    async for chunk in graph.astream(...):   # 每轮内部 await 一个 token
        yield turn.text(chunk)               # 到一块吐一块
    yield turn.end()

两个关键字各管一个方向：await 向内等上游（LLM、HTTP、数据库）给下一块；yield 向外把这一块交给下游（服务器写 socket）。generator 是夹在中间的一根管子，两头都不攒。

为什么必须是 async generator：普通 generator 里不能 await，等 LLM 只能同步阻塞，整个事件循环卡住；普通 async def 只能 return 一次，前端要等整段生成完才看到第一个字。

3.2.2 为什么用 SSE 不用 WebSocket？
SSEWebSocket
方向服务端到客户端单向双向
协议普通 HTTP 长响应，text/event-streamHTTP 升级后的独立协议
基建CDN、网关、鉴权中间件原样通过需要网关支持升级，部分 CDN 不透传
重连浏览器原生，带 Last-Event-ID自己实现
请求方式原生 EventSource 只支持 GET；用 fetch 读流可以 POST 带 body连接建立后任意收发

对话产品是「用户发一句，服务端推一段」，单向够用，SSE 更省事。需要双向实时（语音、打断生成）再上 WebSocket。

3.2.3 用户中途关掉页面，后端会怎样？

这题考的是：generator 由消费方推动。服务器每 async for 一次，函数体才往前跑一段。客户端断开后服务器停止迭代，generator 停在上一个 yield 处，后面的代码不再执行。

由此两条纪律：落库、埋点这类收尾逻辑不能写在 end 事件之后，要放 try/finally 或 BackgroundTask；上游的 LLM 调用要跟着取消，否则模型还在生成，token 照样计费。

3.2.4 多步 Agent 的中间状态要不要推给前端？

要。先路由、再调工具、再生成，每步可能几秒，用户盯着空白会以为挂了。用独立的 processing 事件推进度，和正文的 chat_message 分开，前端按事件类型渲染，不混进消息历史。

3.2.5 反向代理后面流式不生效，怎么排查？

Nginx 之类的反向代理默认缓冲上游响应，攒够一块才转发，流式就变成一次性返回。两个修法：代理侧关 proxy_buffering；或应用侧响应头加 X-Accel-Buffering: no，Nginx 看到就对这个响应不缓冲。顺带加 Cache-Control: no-cache，并确认 gzip 没对 text/event-stream 生效，压缩也会攒块。另一个常见症状是流到一分钟左右被掐断：nginx 的 proxy_read_timeout 默认 60 秒，算的是两次读之间的间隔，模型长时间不吐帧就超时，解法是调长超时或每隔几十秒发一行冒号开头的心跳注释。

3.2.6 流式中途模型报错，前端已经收到一半内容，怎么处理？

服务端不能直接断连，要发一个 error 事件再正常收尾。关键是一轮的所有事件共用同一个 messageId，前端据此知道出错的是哪条消息，自己决定保留已收到的半段还是回滚。这是把「一轮」作为契约单位的原因：错误处理依赖轮的身份，不能每个事件各发各的。

3.3 Maya 选型

3.3.1 Maya 选什么，依据是什么？

选 FastAPI + uvicorn，一个容器一个进程，全异步。

  • 场景决定协议。一轮对话要等 LLM 几秒到几十秒，期间持续向前端推 SSE。这是 IO 等待加长连接，ASGI 的协程模型正好对上。同步模型下一个连接占死一个线程，并发撑不起。
  • 边界决定框架。设计里每个外部数据源一个 pydantic 边界模块、每个 LLM 节点一个输出 schema（2.2.3），FastAPI 的请求校验和 LangGraph 的结构化输出用的是同一套 pydantic，入口到图内部类型一路贯通。
  • 部署决定服务器。跑在 ECS Fargate 上，进程守护和水平扩展由平台做：挂了平台重启，要并发就加副本。gunicorn 的多进程和守护功能是多余的一层，去掉。
  • 一条纪律。所有 IO 一律异步：HTTP 用 httpx.AsyncClient，LangGraph 节点写 async def，模型调用走 ainvoke / astream。确实要跑同步库或 CPU 活时，显式 asyncio.to_thread()。不允许在 async def 里直接调同步 IO。
3.3.2 子图里的循环放图上还是节点里？
原则（出处见末尾）
  1. 两种写法都是官方写法。Graph API 用条件边把节点连成环；Functional API 用普通 while 循环加 @task。[LangGraph]
  2. 节点（或 task）是 checkpoint 和重放的单位。恢复不是从中断的那一行继续，而是从节点开头重放；所以副作用和非确定操作要放在节点或 task 里，恢复时直接取持久化的结果不重跑；一个节点里多个副作用各包一个 task。[LangGraph]
  3. 步数要有上限。recursion_limit 默认 25 超步，超限抛 GraphRecursionError；一圈 ReAct 占两步。[LangGraph]
  4. 声明式图和代码优先各有代价。图清晰可视，但流程一复杂就笨重；代码优先灵活，但循环不可见。框架是抽象层，用它要理解底层。[OpenAI, Anthropic]
  5. interrupt 在节点内暂停，state 持久化，同一 thread 恢复后继续。要这个能力，暂停点必须落在节点边界上。[LangGraph]

出处：LangGraph · Workflows and agents；LangGraph · Durable execution；OpenAI · A practical guide to building agents（Declarative vs non-declarative graphs）；Anthropic · Building effective agents（框架一节）

一个「调模型、看结果、不满意再调」的循环，LangGraph 里有两种写法：拆成节点用条件边连成环，或者整个循环写在一个节点的函数体里。

方案是什么优点缺点
图上循环循环的每一步是一个节点，条件边按 state 字段决定回头还是出口；圈数和中间结果存在 state 里，步数上限靠 recursion_limit
  • 循环在图上可见，每圈每步一个 trace 节点
  • 每步落 checkpoint，圈内可以 interrupt 等外部输入再续
  • 圈内各步可以各自换模型、各自重试
  • 循环的私有变量要进全局 state，别的子图也看得见
  • 循环逻辑散在节点和建图两处
  • 超限是 GraphRecursionError，异常做控制流，要在外层接住
节点内循环一个节点函数里 for 或 while，中间结果是局部变量，上限是常量，出口由函数返回值决定
  • 逻辑集中一处，state 不动
  • 上限和退出条件是普通代码，不靠异常
  • 单元测试只要替换循环里调的函数
  • 图上看不到环，trace 里是一个节点内的多次调用
  • 圈内不能 checkpoint 或 interrupt，节点一旦开始只能跑完；失败恢复时整个节点从头重放，圈内已完成的模型调用会重来
  • 圈内各步共享同一个节点的配置和重试策略

判断标准：循环中途需不需要停下来等外部输入或从断点恢复。需要就上图，图是为了可暂停可恢复而存在的；不需要，节点内循环更短更好测。

Maya 的 Fashion 计数循环选节点内。上限 2，分叉只看一个整数，圈内没有要问用户的步骤，不需要断点恢复，图上循环的优点一个都用不上，缺点却实打实：state 要多两个只有 Fashion 用的字段，上限要靠接异常。

什么时候切回图上：循环体里出现要 interrupt 的步骤（在同一轮里暂停、等用户回答后从断点继续，已拒条件还在。澄清不是这种：它结束本轮，用户的回答是下一轮的新请求，重新过 Router）、需要按步 checkpoint 恢复、或者圈数多到要逐圈看 trace。迁移成本可控：把 for 拆成两个节点，中间变量搬进 state，加一条条件边。

3.4 Prompt 工程

3.4.1 Prompt 工程现在业界怎么做？

已经从「写一篇好 prompt」收敛成一条流水线，核心是用评测驱动迭代，不靠感觉：

  1. 格式交给 schema。输出结构用结构化输出钉死，prompt 里不写「只返回 JSON」「不要解释」这类话。
  2. 从最短开始。先 zero-shot，只写任务和判断标准，跑评测集看错在哪。
  3. 按错误补。误判样本变成 few-shot 例子或边界规则，一条条加，每加一条回归一次。
  4. prompt 当代码管。进版本库，改动走 PR，评测不过不合并。大了放 prompts/ 目录或 prompt hub 做版本与对比。
  5. 量大了换路。分类类任务 few-shot 堆多了又长又慢，有标注数据后换小模型微调或 embedding 分类器。
3.4.2 结构化输出和 prompt 怎么分工？

结构化输出管「长什么样」，prompt 管「怎么判断」。

以 pydantic 模型调 with_structured_output(Model) 为例：模型类转成 JSON schema 随请求发给 OpenAI，服务端开 strict 模式，输出在解码阶段就被约束成合法 JSON，枚举字段只能取定义过的值；返回后 pydantic 再校验一遍转成对象。模型没有机会输出别的东西，所以 prompt 里格式相关的内容全部删掉，长度通常减一半以上。

追问「schema 能不能替代 prompt」：不能。schema 只保证形状合法，不保证选得对。三个意图选哪个，仍然要靠 prompt 里的定义和例子。

3.4.3 few-shot 什么时候加、加什么？

few-shot 是调优手段，不是起点。一开始凭想象写的例子往往不是真正的难点。正确顺序是 zero-shot 先跑评测集，把误判的句子拿出来当例子，例如「what's in my box」被判成 fashion，就把它作为 account 的例子加进去。

加例子的原则：覆盖边界而不是覆盖常见；每类不超过三五条；加了要回归，防止修一个坏一个。

3.4.4 prompt 怎么管理、怎么迭代？
阶段放哪怎么改
短、单节点模块常量改代码，走 PR
长、多段拼接prompts/*.md，代码读文件改文件，走 PR，评测门禁
要 A/B、非工程师参与LangSmith / Langfuse 的 prompt hub平台上改版本，trace 里能看到每轮用的哪个版本

不管放哪，底线是没有评测集就没法判断改好了还是改坏了。评测集先于 prompt 优化。

3.4.5 Maya 里怎么用的？
  • Router 是 zero-shot + 结构化输出。输出契约是 RouterOutput(intent: Intent)，枚举三值；prompt 六行，只写三类意图的定义，没有格式说明、没有例子。
  • 每个 LLM 节点一个输出 schema。Router、各子图的输出都是 pydantic 模型，边界在模型侧钉死（2.2.3），图内部不再做字符串解析。
  • prompt 现在是模块常量，子图 prompt 变长后迁到 prompts/ 目录；版本与对比放到 LangSmith 和评测门禁一起做（2.2.4）。
  • few-shot 等评测集。迁移批次里评测骨架先于子图业务，有了误判样本再补例子。
3.4.6 每次调用都要带 system prompt 吗？本轮产生的数据放哪个角色？
原则（出处见末尾）
  1. 调用无状态，每次全量发。prompt caching 缓存的是前缀算出的 KV，不是文本；前缀必须逐字节一致，低于最小长度（常见 1024 token）不缓存。[OpenAI, Anthropic]
  2. 稳定内容前置，动态内容后置，追加不改写。前缀顺序 tools → system → messages，改前面的让后面全失效；改 tools、输出 schema、模型、reasoning 参数也会失效。[Anthropic, OpenAI]
  3. 缓存只省钱不省传输。读约 0.1 倍输入价，写 1.25 倍；命中率要看 usage 里的缓存 token 数。[OpenAI, Anthropic]
  4. 角色有权威层级：platform/system ＞ developer ＞ user ＞ guideline；assistant 和 tool 消息没有权威。[OpenAI Model Spec]
  5. 引用的和不可信的内容是信息，不是指令。工具输出、粘贴的文档、检索结果里的指令一律当数据看。[OpenAI Model Spec]

出处：OpenAI · Prompt caching；Anthropic · Prompt caching；OpenAI · Model Spec（Chain of command）

要。模型调用是无状态的 HTTP 请求，服务端不记得上一次，每次都把全部消息发一遍。客户端缓存的是连接对象，不是对话。模型侧的 prompt caching 按相同前缀命中（OpenAI 对超过 1024 token 的前缀自动做），命中后那段按折扣计费，但只省钱不省传输。

由此得到一条摆放原则：固定的放前面做 system，每轮变的追加在尾部。四个角色各管一类内容：

角色放什么特征
system开发者定的规则：身份、任务、输出形状、允许的取值每轮一样，是缓存前缀
user本轮输入：用户的话，以及这一轮才产生、要让模型看到的事实每轮不同
assistant模型之前的输出，重放对话时才需要可选，不重放就没有
tool模型自己发起的 tool call 的结果必须跟在对应的 tool call 后面，否则被拒

把运行时得到的反馈（工具结果、校验失败、检索为空）回给模型有两种写法：重放，把模型上一次的输出当 assistant 消息放回去，再追加一条 user 说明问题；当数据，不放 assistant，只把上一次输出里有用的部分序列化进一条 user 消息。前者模型看到的是「自己说过的话被打回」，后者更短，也不用把结构化输出再还原成 assistant 消息的格式。只在模型主动调了工具时才用 tool 角色。

Maya 里：词表和输出规则在 system，一千多 token 做固定前缀；用户原话是第一条 user；计数为 0 时的放宽反馈走「当数据」写法，作为第二条 user 追加；代码循环里没有先行 tool call，所以不用 tool 角色。

3.5 工具调用

3.5.1 工具谁来调：代码还是模型？
原则（出处见末尾）
  1. 先定义：workflow 是 LLM 和工具按预定义代码路径编排；agent 是 LLM 动态决定自己的流程和工具使用。[Anthropic, LangGraph]
  2. 先找最简单的方案。很多场景一次调用加检索加示例就够；agent 增加延迟和成本、放大错误，只在需要时用。[Anthropic]
  3. 该上 agent 的三个信号：判断复杂例外多、规则多到难维护、重度依赖非结构化输入。都不满足，确定性方案就够。[OpenAI]
  4. 工具分三类：Data（取信息）、Action（改外部状态）、Orchestration（agent 当工具）。[OpenAI]
  5. 先把单 agent 做满。prompt 分支过多或工具重叠导致选错时才拆多 agent；工具数不是问题，相似才是。[OpenAI]
  6. 模型调工具的循环必须有退出条件：特定结构化输出、无 tool call、错误、最大轮数。[OpenAI]
  7. 工具是给模型用的界面，和 UI 一样要设计：描述带例子和边界、参数防呆。[Anthropic]

出处：Anthropic · Building effective agents；OpenAI · A practical guide to building agents；LangGraph · Workflows and agents

判断标准：固定流程代码调，开放流程模型调（固定流程指路径能提前枚举、用 if 和 for 写完；开放流程指调哪个、调几次取决于上一步的结果，事先写不完）。前者是 workflow，后者才是 agent。

方式是什么优点缺点
代码调模型只给结构化结果，节点按固定流程调 clients 函数，结果进 state 或回填 prompt
  • 流程确定，每次都调，不会漏调或多调
  • 出口一个 schema 就钉死，终态由类型保证
  • happy path 一趟模型加一次 HTTP
  • 把函数换成假的就能测每条路径
  • 路径要提前枚举，分支多了代码写不完
  • 新工具要改节点代码
模型调bind_tools 把工具描述给模型，模型吐 tool call，代码执行后以 ToolMessage 回传，模型再决定下一步
  • 路径开放，模型按上一步结果决定调哪个、调几次
  • 加工具只加描述，不改流程
  • 不确定：可能不调、重复调、看到结果也硬给答案，要靠步数上限兜底
  • 最终回答和 tool call 是两种输出，终态要另加约束
  • 至少两趟模型往返
  • 测试要模拟整个对话，难钉住

Maya 场景下按工具逐个选：

工具谁调理由
商品计数 search_products代码每次都要查，0 件放宽一次再 0 就澄清，分叉只看一个整数
订单 search_orders代码意图是 account 就一定要查，没有可选项
类目、品牌列表代码是静态词表，直接渲染进 prompt，不需要运行时调
products 还是 looks模型选，代码调二选一，选完路径固定。结构化输出多一个枚举值，和 Router 选 intent 同一套路
图片：看图、识别单品、框选模型问什么、框哪几个取决于识别结果，路径开放，枚举不完
FAQ：知识库检索配订单查询模型一个问题可能只查知识库，也可能先查订单再查知识库，顺序由问题定

3.6 评测

原则（出处见末尾）
  1. 评测驱动开发，尽早开始。20 到 50 条源自真实失败的样本就能起步，等得越久越难建。没有评测集的 prompt 调优是凭感觉。[Anthropic, OpenAI]
  2. 指标要任务专属，跟着失败后果走。不用 BLEU 一类通用指标；评结果不评路径，不把 agent 的步骤顺序钉死。[OpenAI, Anthropic]
  3. 不确定性出现在哪，评测就放在哪。工作流里的每次模型调用单独评；agent 再加工具选择和参数抽取；整条链路另评一层。[OpenAI, Hamel L1]
  4. 能用代码判的不用模型判，模型判先和人对齐。代码评测器快、便宜、可复现；LLM judge 用最强模型、成对比较或通过/不通过、先推理再打分，和人工标注核对一致性后再放量。[Anthropic, OpenAI, Hamel]
  5. 正负样本都要有。既测该做的，也测不该做的，否则会单边优化。[Anthropic]
  6. 单次分数不可信。模型是概率性的，多次 trial 看 pass^k；0% 通过多半是样本或评测器有 bug；分数要配合读 transcript。[Anthropic]
  7. 评测集从 trace 长大，持续更新。记录全部日志，错例进样本，线上问题转离线用例；样本分布要反映真实流量；通过率饱和后加难题。[OpenAI, LangSmith, Anthropic]
  8. 永远要看数据。自动评测只是一层，配合生产监控、A/B、用户反馈和定期人工读 transcript，没有一层能兜住全部。[Hamel, Anthropic]

出处：Anthropic · Demystifying evals for AI agents；OpenAI · Evaluation best practices；Hamel Husain · Your AI Product Needs Evals；LangSmith · Evaluation concepts。hello-agents 第十二章侧重 BFCL / GAIA 一类公开基准，对产品评测只有「多指标组合、LLM judge 有偏见需人工校验」两条适用。

3.6.1 怎么知道 prompt 改好了还是改坏了？

靠评测集，它是 LLM 应用的回归测试：一批固定样本，每条有期望输出，每次改动跑一遍比分数。没有评测集的 prompt 调优是凭感觉，改好一个常常改坏另一个而不自知。

两条和传统测试不同的纪律：

  • 样本固定。两次实验跑同一批样本才可比。
  • 单次通过率不可信。模型是概率性的，24/25 可能下一次是 22/25。要跑 k 次看 pass^k，或至少同一数据集多次实验对比；每次实验标记这次改了什么，才能归因。

Maya 里：样本的真源是 LangSmith 上的数据集，实验跑它，新样本加在它上面；git 里的 jsonl 只是首批样本，用来在新环境一键重建。实验名用前缀标记改动（--prefix fewshot）。

3.6.2 评测分几层？
层评什么特点
单元级一个 LLM 节点的结构化输出：分类对不对、字段抽得对不对快、便宜、错了能定位到哪个 prompt
端到端整轮从入口到出口：路由加工具加出口，以用户看到的结果为准慢、贵，但能抓到各层接缝的问题

两层都要有。只有单元级会漏掉接线错误，只有端到端会定位不到原因。

Maya 里：router 和 fashion-criteria 是单元级，target 就是线上的 route() 和 decide()；fashion-terminal 是端到端，target 用 httpx 的 ASGITransport 直接打 FastAPI app，拆回 SSE 帧看最后一条是 button 还是 text。三个 target 都不 mock，评的是真实路径。

3.6.3 指标怎么定？

指标就是评测器怎么打分：拿输出和什么比，比到多严。选哪种看这个字段错了后果多大，同一条输出里不同字段可以用不同比法。常用的三种：

比法什么时候用Maya 的例子
精确相等多一点少一点都算错must 组。must 是硬过滤，多放一个 Color: Red 结果就只剩红色，所以期望 {Category: [Dress]} 就必须一模一样
覆盖漏了算错，多了不算错should 组。should 只影响排序，多加几个 Style 标签不伤害结果，只检查期望的 Occasion 有没有出现
打真实数据对错不在标注里，要去真实系统验证in_stock。条件对不对标注说了算，有没有货只有索引知道，拿条件去 core 数一下，大于 0 才过

评结果不评路径。把 agent 的步骤顺序钉死会惩罚合理但不同的解法。端到端评测因此常常只比形状不比内容：Maya 的终态评测只看最后一帧是 button 还是 text 与期望一致、帧序列 start 开头 end 收尾没有 error，不管 reply 写得好不好，也不管中间有没有放宽重试。

3.6.4 评测器用代码还是用模型？

能用代码判的一律代码判：枚举相等、集合包含、schema 合法、序列形状。确定、免费、不会自己出错。

模型判（LLM-as-judge）留给代码判不了的：回复的语气、有没有答到点上、两版回复哪个更好。judge 自己也是概率性的，用之前要校准：拿一小批人工标注核对它的一致性，不一致就改 judge 的 prompt 或换成成对比较（A 和 B 哪个好）而不是打绝对分。

Maya 里：现在全是代码评测器。reply 的质量还没评，这是下一步要加 judge 的地方。

3.6.5 样本从哪来、怎么维护？
  • 起步手写，正负都要。每类意图几条常规句，再加一组边界句单独分 split，边界句才是 prompt 迭代的抓手。该做的和不该做的都要有样本，只测「该搜」会把模型推向什么都搜。
  • 上线后从 trace 捞。用户点踩的、输出被 schema 拒掉的、人工抽检发现的，进标注队列变成样本。这是评测集长大的正路，手写的只是起点。
  • 防过拟合。评测句不能原样进 prompt 当 few-shot，否则是在考背答案。错例变 few-shot 时换一句同类的。
  • 评测集会腐坏。词表改了、库存变了、业务规则变了，标注就过期。打真实数据的指标尤其如此。谁改规则谁改样本。

Maya 里：三个集都是手写起步，clarify 样本就是「不该搜」的负例，hard split 放边界句（「what goes with wide leg jeans」第一次跑就抓到 must 里放了 Jeans）。还没有线上流量，从 trace 捞是下一阶段。

3.6.6 评测怎么进流程？
阶段做法
