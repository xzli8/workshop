Maya 重构设计

0 Agent 工程与传统工程

根因（root cause）

Agent 工程与传统工程的全部差异，来自把 LLM 放进了控制流：一个概率性的、以自然语言为接口的、慢而贵且上下文有限的组件，开始决定程序的下一步。（概率性、自然语言接口、资源属性是 LLM 的性质，「放进控制流」是架构选择。不放进控制流只是「用了 LLM 的应用」，放进去才是 agent。）

传统工程对「组件」有四个隐含假设，LLM 逐条打破：

传统工程agent 工程如何处理（业界调研结果）常用实现
确定性
同输入同输出，坏 case 一定可复现		概率性
同输入不同输出，坏 case 不一定复现		无法杜绝，只能记录和约束
  • 全量 trace 记录每步输入输出
  • 评测集加 pass^k 门禁，报可靠性不报单次成功率
  • 缩窄决策点、结构化输出压方差
  • trace 与评测平台：LangSmith、Langfuse、OpenTelemetry GenAI 约定
  • 评测器：LLM-as-judge、DeepEval、Ragas
  • 评测跑在 CI 里
强类型接口
结构由 schema 保证，指令与数据分离		自然语言接口
结构靠约定，指令与数据同一通道，任何位置输出 EOS 都合法		在边界上把软结构变成硬结构
  • 边界处一次解析成类型，工具调用当结构化输出由代码校验执行
  • 分层 guardrail 叠在鉴权之上
  • prompt 当版本化配置，变更过评测
  • 结构化输出：pydantic + 模型侧 structured outputs、instructor
  • guardrail：Guardrails AI、NeMo Guardrails、厂商 moderation API
  • prompt 版本化：LangSmith Prompt Hub 或 git
廉价无界
调用快、便宜、资源不设上限		资源属性
调用慢、按 token 计费、上下文窗口有限		把上下文和调用当预算管
  • 上下文工程：只放高信号 token，记忆分层，压缩与按需检索
  • 流式输出
  • 按任务大小选模型
  • 超时按失败类型定策略
  • 记忆与检索：LangGraph checkpointer / Store，向量库（OpenSearch、pgvector）
  • token 计数与压缩：tiktoken、摘要节点
  • 模型抽象与路由：LangChain 模型接口、LiteLLM
  • 流式：SSE
控制流归代码
组件只返回结果，不决定下一步		输出决定控制流
输出决定下一步做什么、调哪个工具、何时停（架构选择，不是 LLM 性质）		循环归代码，模型只判断意图
  • 显式边与步数上限
  • 每步 checkpoint，可暂停可恢复，节点幂等
  • 执行状态与业务状态单源
  • LangGraph：StateGraph、条件边、recursion_limit、checkpointer、interrupt
  • 同类：OpenAI Agents SDK 的 run loop
  • 持久化工作流引擎：Temporal

概率性、自然语言接口、资源属性三者相互独立；输出决定控制流由前两者叠加放大：自然语言接口让「不调工具、直接 EOS」成为合法输出，概率性让它偶发。

1 Maya

1.1 角色定位

Maya 是 BNTO 的 AI 导购助手，支持用户用自然语言/图片搜索相关服装饰品等潮牌搭配，问账户、订单、FAQ 等相关问题。

2.1.1 边界划分

相邻系统Maya 负责对方负责交互
前端接收一轮对话请求，流式返回结构化消息；历史消息的查询与管理发起请求、渲染消息、处理点击前端经网关调 Maya，SSE 消息契约不变

  • 弹窗与问卷判定：原在 bnto-ai 内判定并持有频控锁，现划归 Context Hub；前端展示回调直接打 Context Hub，不经 Maya。

2.1.3 基础设施

项作用Maya 如何依赖选型
模型供应商对话、看图、识图的模型推理同步调用，超时与重试在 Maya 侧OpenAI（对话、看图）、Gemini（识图）
历史消息存储按照 session 存储历史消息用于消息展示和摘要，通过 CDC 同步到索引供向量查询轮初读出作为起点，轮末追加短期 PostgreSQL + pgvector；长期追加型日志存储 + CDC 同步向量索引
RAG 检索FAQ 知识库的检索FAQ 回答时同步调用自建 OpenSearch、pgvector、沿用 OpenAI FileSearch
trace 与评测平台记录每步输入输出；存评测集并跑评测运行时异步上报；CI 拉评测集跑门禁LangSmith、自托管 Langfuse、OpenTelemetry 加自有存储
  • 部署形态：bnto-monorepo 的 apps/maya 可部署单元，自带 Dockerfile 与 deploy.yaml，按部署契约进 ECS，运行时配置走 SSM。
  • 历史消息存储
    • 短期：PostgreSQL + pgvector 同库。当前量级追加写无瓶颈，按用户过滤后候选集很小，同库做向量查询不需要 CDC。
    • 长期：写入量上来后，日志迁到追加型日志存储（日志追加负载，宽表或带排序键的 KV 模型），经 CDC 同步到向量索引（搜索负载，倒排加向量索引）。
      • options：追加型日志存储
        方案优点缺点
        DynamoDB【选定】（B-tree + WAL）分区键 session、排序键时间（顺序读和分页是原生模式）；TTL 内建；Streams 即 CDC；托管零运维和厂商绑定
        Cassandra / HBase（LSM-tree）宽表加时间聚簇的模型完全匹配，消息与日志系统的经典选择；写吞吐高；开源可迁出自管集群运维重，HBase 还要拖 Hadoop 与 ZooKeeper；CDC 要另搭
      • options：向量索引
        方案优点缺点
        OpenSearch【选定】按用户过滤后 kNN 加 BM25 混合检索原生支持，用户提品牌名、品类词时关键词比向量准；增量写、按文档删方便；托管版有比纯向量库重；相关性调参要投入
        独立向量库（Milvus、Qdrant、Pinecone 一类）大规模 ANN 性能强，向量专用功能全召回限定在单用户历史内，候选集小，ANN 规模用不上；无原生全文混合；多一个系统
        Vespa混合检索能力最强，向量、全文、结构化过滤一体极重，学习和运维成本高；对单用户小候选集是杀鸡用牛刀
      • conclusion：DynamoDB 存日志，Streams 作 CDC，OpenSearch 做向量索引。
      • tradeoff
        • 托管换锁定：DynamoDB 与 OpenSearch 都用 AWS 托管版，换来零运维和内建的 CDC、TTL，付出和厂商绑定。Maya 本就跑在 AWS 上，可接受。
        • 分开换复杂度：日志与索引分成两个系统各取所长，付出一条 CDC 链路和两套运维。
        • 混合检索换重量：OpenSearch 比纯向量库重、相关性要调参，换来过滤后的向量加关键词混合检索。

2.2 重构方案

2.2.1 编排

方案选型
方案是什么优点缺点
代码优先的手写循环（现状）【不选】openai-agents SDK 的形态：一个 run loop，模型通过 handoff 和工具调用决定下一步零改动，写法直接控制流在循环体内，终态靠模型自觉，每种终态要单独兜底
持久化工作流引擎（Temporal 类）【不选】面向长时任务的可靠执行：持久化、重试、超时执行可靠性强不提供结构化输出、流式和工具循环的约束；对几秒一轮的对话是多余的重量
LangGraph【选定】把一轮对话写成显式状态图：节点、条件边、子图，自带 checkpoint、interrupt、步数上限、流式控制流在边上不在模型输出里，终态由出口节点保证；Maya 的流程边界有限、画得出来引入新依赖，节点、状态、边全部要重写
对话状态图
  • 循环归代码，模型只判断意图
    • Router 是一次结构化输出：意图枚举，多步时带顺序；走哪条边由代码映射，不解析自由文本。
    • agent 子图内部是工具循环，模型每步只输出结构化决定：调哪个工具、给出结果、还是需要澄清；条件边按字段判定。
    • 工具调用是结构化输出，参数经 schema 校验后由代码执行；工具报错压缩成一条结果写回 state，不把 stack trace 喂给模型。
  • 终态由结构保证
    • 每个子图只有一个出口节点，出口有 schema：Fashion 出检索条件或澄清问题，Account 出结构化事实，FAQ 出带出处的回答。
    • 模型输出不满足出口 schema 时进不了终态：有步数余量就回循环，没有就走澄清出口。模型无法以 EOS 结束一轮。
    • 现状的流末兜底（wait cue、overlay）不再存在：它们兜的是「模型停在半路」，图里没有这条路径。
  • 步数上限与弹窗
    • 每个子图设 recursion_limit；超限进固定的兜底出口（澄清或失败文案），不向用户抛异常。
    • consent 与问卷弹窗是本轮的一个终态：入口节点按 Context Hub 的判定直接出弹窗，本轮结束；用户处理后的下一条消息作为新一轮进入口重新判定（受约束「前端契约不变」；约束解除时改为 interrupt 加恢复接口，本轮原地续跑）。
  • 流式与 SSE 适配
    • 图以 stream 方式运行，三类事件：节点更新（进度）、token（文本流式）、自定义事件（结构化消息）。
    • SSE 适配层在图外，把事件映射到现有消息类型；消息送达时写消息表（受约束「前端契约不变」；约束解除时按终态类型重新定义消息 schema，适配层消失）。

方案选型
方案是什么优点缺点
每轮从 Context Hub 拉历史回放（现状）【不选】对话经 RocketMQ 异步写入 Context Hub，每轮拉最近 20 行清洗后回放进内存 Session零改动两份真源；异步链路静默丢；每轮多一次 hub 往返和清洗；只有倒序取 20 行一个接口，窗口外的历史用不上

方案定义优点缺点
前端定义会话（现状）【不选】sessionId 由前端生成放在 cookie，App 或 Web 重开即换零改动历史页按用户展示、模型记忆按 session 取，Maya 认不出对话框里正在展示的历史

上下文管理
  • 用户本轮输入：用户当前输入的消息（文本/图片等）。
  • 历史消息：按照 session 跨轮持久化存储，每轮追加（展示用的历史接口读同一份存储，不另存）。
    • 窗口内：最近 N 轮原文。
    • 窗口外：摘要是超预算时把更早轮次压缩成的事实概要；相似召回是按当前输入从全部历史中命中的相关旧轮。两者互补。
  • 外部数据源：按需拉取、不落盘。
    • 画像每轮拉。
    • 天气按意图拉。
    • Account 的用户数据按路由拉。
  • system prompt：角色、规则、工具定义（版本化配置，见 边界与契约）。

A 面试追问

系统形态与契约

为什么不做多轮流式会话，而是一次请求一轮？
前端契约先于我存在。一次请求一轮让服务端可以无状态横向扩，代价是历史要显式回放。我的判断是保留请求模型、修历史回放，比改前端契约代价小一个量级。
路由靠模型分类，不怕不稳定吗？
怕，而且实测就是不稳定。处理原则不是消灭不稳定，是让错误路由无害：两边都挂工具，走到哪边都能答。真正要精确路由的只有职能绑定类工具，那是单挂的。

终态保证

rescue 会不会误伤：模型故意不调工具、只是想澄清？
判定条件是 readiness 1.0 且 search_json 完整，模型自己声明了"我要搜了"。这个状态下不调工具没有合理解释。真正的澄清走 A 路径，readiness 不足，不触发。
为什么不直接用 tool_choice="required"？
Fashion Agent 有十几个工具，required 只保证调一个，不保证是搜索；而且澄清轮本来就不该调。选项 ③ 是"检测到 C 再用 required 克隆重跑"，比 ① 多一次模型调用，UX 好一点点，我们的判断是不值。
rescue 率是多少？
升级 terra 前 UAT 全天 5 次真实 rescue，升级后 1 次，且那次是登录态多轮长上下文的跟进轮。计数要精确 grep base_agent - [wait-cue-fallback]，裸 grep 会被 MQ produce 行和历史回显放大三倍。
这是打补丁还是设计？
诚实说是补丁，但它是正确的补丁：把终态责任放到确定性的一侧。长期方案是把终态做成编排图里的一个节点，rescue 消失，见第 2 节。

外部模型调用治理

15 秒怎么定的？
正常识别 7 秒左右，用户能等的上限十几秒，网关 60 秒。15 秒给了两倍正常延迟的余量，又远离网关线。8824 之后 13.8 秒的样本离线很近，备选是缩到 1024 边，一行配置。
为什么服务端缩图而不是让 iOS 对齐 Web 的压缩？
两个都要做，但服务端先做：客户端有版本分布，改了要等用户升级；服务端一次生效覆盖所有端，而且服务端本来就该对输入归一化，不该信任客户端字节。
截断的 JSON 为什么不做 salvage parse？
触发图片在 temp=0 下必然截断、必然失败，救不出结果；salvage 只是把 4 分钟的失败变成 4 分钟的部分结果。先把 4 分钟变成 15 秒才是重点。
tracing 为什么关了？
openai-agents 默认 trace export 把 original_input 连同完整图片 base64 发到 OpenAI tracing 端点，被 length 拒，刷屏 errors.log，还外发了用户图片。这是第 2 节接 LangSmith 时要用 hide_inputs 剥掉的东西。

上下文与记忆

为什么不用 SDK 的持久化 Session 直接落库？
历史已经在 Context Hub 里，是 Java 侧的事实源，历史页也从那读。再落一份就是两个事实源。回放的成本是每轮一次清洗，实测 215 token，可以接受。
历史多长合适？
20 行是 hub 的上限，我用了全部，再用预算截。不是算出来的，是够用且长上下文会抬 path-C，所以没往上加。有评测体系后这是第一个该调的参数。
历史里有 base64 怎么办？
存量行有。注入时的转换永远不内联图片值，只放 URL 占位。这条是在一次误报排查里定下来的：我自己的 smoke 用了旧的字符串形状，绕过了剥 base64 的分支，看起来像回归，其实是载荷形状错了。教训是 smoke 载荷必须用前端契约形状。
结果页追问还是不承接上下文？
对。召回是点击后的同步调用，不是对话轮，模型知道用户传了图、识别出什么，不知道结果页展示了什么、点了哪个框。补齐要前端随追问带结果页上下文，或服务端把点击记进会话。Lee 判定当前不做。

模型升级与验证

没有评测集，怎么敢换模型？
不敢，所以验收标准定得很窄：不是"更好"，是"关键路径不退化"。九探针加 A/B/C 计数就是最小验收集。这也是为什么第 2 节第一步是接观测建评测，下次换模型不该再靠手工探针。
同车上线双变量归因怎么办？
分支内独立 commit，出问题按 commit revert 看指标。当时判断风险可接受：模型变更的探针已经过了，图搜是新功能没有基线可退化。
离题空气泡真的修了吗？
以模型升级结案，17/17 零复现，但没有加服务端空轮兜底。评论里写明了复发时的方案：流末检测整轮无文本回复，补发固定引导文案，仿 wait-cue rescue。

总体

1. 这个项目你是从零做的吗？
不是。两位同事写的第一版，我 5 月接手做生产化。接手比从零更能说明"own production quality"：所有问题都是在真实流量下发现、根因、修复、验证的。
2. 团队多大，你负责什么？
bnto-ai 服务端改造由我独立承担，包括 core 侧配套的三个 Java inner 接口。iOS、Web 各一人对接契约，QA 一人，core 一人确认数据语义。
3. 为什么是 openai-agents SDK 而不是 LangChain？
接手时已定。我的判断是框架不是当前瓶颈，见第 2 节：先观测评测，编排重写放最后且可选。
4. 你最得意的一个决策？
把终态从模型手里拿回来。它让"模型怎么变"和"用户一定能点到结果"解耦，后面换模型、加历史、加工具都没再碰它。
5. 你最想重做的一个决策？
接手第一周就该接 tracing。7 月所有根因都是靠 grep 多 worker 轮转日志加 awk 指纹做的，能做但慢，而且换人做不了。
6. 三次判断错在哪里？
consent 降级的大面积触发预测，前提来自过期注释；8824 第一版假设退化循环，原字节复跑后改为输出过长；base64 进历史的回归告警，是我自己 smoke 载荷形状错了。三次共同教训：拿真实字节和真实请求头，不拿代码注释和自己的探针当证据。
7. 和推荐系统、BFF 的关系？
推荐讲的是定边界再分层，BFF 讲的是编排演进，这个讲的是把不确定的组件放进确定的系统：终态由确定的一侧保证，外部调用有超时与降级，失败响亮，验证有方法。三个项目的共同点是先定契约，再让两侧独立演进。
8. 延迟 6–9 秒能接受吗？
对话场景用户容忍度高于搜索页，首 token 流式先出。大头是模型推理与工具往返，不是我们的代码。能做的是并行（S3 上传已与识别并行）、缩输入（缩边、历史清洗）、少一轮（rescue 不额外调模型）。再往下要 reasoning 档位和工具并行调用，需要评测体系兜着才敢动。

C 两分钟版本

Maya 是 BNTO 的 AI 导购助手，Python 写的，跑在 openai-agents SDK 上，我 5 月接手时能演示但不能运维：按钮偶发不出、图搜偶发永挂、每轮不记得上一轮、照片进不了历史、失败全部静默。我做的第一件事是把终态从模型手里拿回来：模型说"正在搜"却不调工具的比例约三分之一，根因是 prompt 契约要求一次回复两个动作，和模型的补全先验冲突，我在流末加服务端 rescue，检测到孤儿 wait cue 就重跑计数查询补发按钮，用户可见的失败归零，同一模式复用到图搜的 overlay 兜底。第二件是外部模型调用治理：Gemini 对某些图片进入重复循环，一次四分钟、三次重试静默十二分钟，网关六十秒掐流，前端永远转圈；改成十五秒一次、加输出 token 上限，永挂变成十七秒明确失败。九月手机端高清图必超时，根因是模型把背景路人的衣服全数出来，送识别前统一缩边到 1600，延迟从 23 到 44 秒降到 9 到 13 秒。第三件是上下文：每轮无状态的根因是 SDK Session 每请求重建，我从 Context Hub 拉最近二十行历史、清洗到十三分之一的体积回放进 Session；图片消息超 128KB 被 MQ 客户端静默丢弃，改成异步上 S3、历史只存 URL，单轮 SSE 从 275KB 降到 4KB。第四件是模型升级：gpt-4.1 升到 gpt-5.6-terra，SDK 不动，用路径分类和 per-trace 日志指纹验证，全天真实 rescue 从六次降到一次且被兜住，离题空气泡十七次零复现。

D 判断复盘

consent 降级误判
我一度判断 Web 升 UA 版本会把登录用户拉进 consent 静默降级、上线日会大面积触发。Lee 指出上一版 Web 的 UA 早已过门槛，我的前提来自一个过期的 docstring 示例。预测作废，问题降级为"platform 参数接受但未使用"的卫生问题。教训：代码注释里的示例不是线上行为的证据，要看真实请求头。
拦截轮去重被回滚
survey 拦截的图片轮不上 S3 不持久化，我做了并合了 dev，Lee 当天回滚，判断是不该这么改。记着的是接受了的权衡：问卷完成但重发没触发时历史里没有那张图。

E 09-18 规划稿（已由第 2 节取代）

判断：Maya 的痛是"没有眼睛和尺子"，不是编排框架。四步，前三步是主线，第四步可选：

  1. 接观测（约 1 周）：注册 openai-agents 的 LangSmith TracingProcessor；工具、图搜阶段、Context Hub 调用加 traceable；metadata 带 session / user / 端 / 版本 / prompt 版本；hide_inputs 剥 base64 与 PII，关掉 OpenAI tracing 端点。path-C 率从 grep 变成查询。
  2. 评测基线（2–3 周）：从生产 trace 攒五个数据集：路由、工具调用（query 到工具与 searchJson 字段）、终态完整性、离题处理、图片识别。前四个代码 evaluator，回复质量 LLM 裁判。进 CI，改 prompt 或换模型必须过。
  3. Prompt 治理：渲染器拼出的完整 prompt 作为版本化产物入 Hub，trace 带版本；在线抽 5% 打离题与空回复分。
  4. 编排重构（可选）：LangGraph 显式状态图，分类 → 子图 → 工具循环 → 终态节点，按钮与 overlay 由图保证，rescue 消失；checkpointer 替每轮回放历史；同意弹窗与问卷拦截用 interrupt；自定义 stream 经薄适配层映射到现有 SSE 契约，前端不动。按场景灰度，新旧成对评测。
