0 Agent 工程与传统工程

根因（root cause）

Agent 工程与传统工程的全部差异，来自把 LLM 放进了控制流：一个概率性的、以自然语言为接口的、慢而贵且上下文有限的组件，开始决定程序的下一步。（概率性、自然语言接口、资源属性是 LLM 的性质，「放进控制流」是架构选择。不放进控制流只是「用了 LLM 的应用」，放进去才是 agent。）

传统工程对「组件」有四个隐含假设，LLM 逐条打破：

传统工程agent 工程如何处理（业界调研结果）常用实现
确定性
同输入同输出，坏 case 一定可复现		概率性
同输入不同输出，坏 case 不一定复现		无法杜绝，只能记录和约束
  • 全量 trace 记录每步输入输出
  • 评测集加 pass^k 门禁，报可靠性不报单次成功率
  • 缩窄决策点、结构化输出压方差
  • trace 与评测平台：LangSmith、Langfuse、OpenTelemetry GenAI 约定
  • 评测器：LLM-as-judge、DeepEval、Ragas
  • 评测跑在 CI 里
强类型接口
结构由 schema 保证，指令与数据分离		自然语言接口
结构靠约定，指令与数据同一通道，任何位置输出 EOS 都合法		在边界上把软结构变成硬结构
  • 边界处一次解析成类型，工具调用当结构化输出由代码校验执行
  • 分层 guardrail 叠在鉴权之上
  • prompt 当版本化配置，变更过评测
  • 结构化输出：pydantic + 模型侧 structured outputs、instructor
  • guardrail：Guardrails AI、NeMo Guardrails、厂商 moderation API
  • prompt 版本化：LangSmith Prompt Hub 或 git
廉价无界
调用快、便宜、资源不设上限		资源属性
调用慢、按 token 计费、上下文窗口有限		把上下文和调用当预算管
  • 上下文工程：只放高信号 token，记忆分层，压缩与按需检索
  • 流式输出
  • 按任务大小选模型
  • 超时按失败类型定策略
  • 记忆与检索：LangGraph checkpointer / Store，向量库（OpenSearch、pgvector）
  • token 计数与压缩：tiktoken、摘要节点
  • 模型抽象与路由：LangChain 模型接口、LiteLLM
  • 流式：SSE
控制流归代码
组件只返回结果，不决定下一步		输出决定控制流
输出决定下一步做什么、调哪个工具、何时停（架构选择，不是 LLM 性质）		循环归代码，模型只判断意图
  • 显式边与步数上限
  • 每步 checkpoint，可暂停可恢复，节点幂等
  • 执行状态与业务状态单源
  • LangGraph：StateGraph、条件边、recursion_limit、checkpointer、interrupt
  • 同类：OpenAI Agents SDK 的 run loop
  • 持久化工作流引擎：Temporal

概率性、自然语言接口、资源属性三者相互独立；输出决定控制流由前两者叠加放大：自然语言接口让「不调工具、直接 EOS」成为合法输出，概率性让它偶发。

1 Maya

1.1 角色定位

Maya 是 BNTO 的多模态导购 agent，支持用户用自然语言/图片搜索相关服装饰品等潮牌搭配，问账户、订单、FAQ 等相关问题。

2.1.1 边界划分

trace 与评测平台记录每步输入输出；存评测集并跑评测运行时异步上报；CI 拉评测集跑门禁LangSmith、自托管 Langfuse、OpenTelemetry 加自有存储
  • 部署形态：bnto-monorepo 的 apps/maya 可部署单元，自带 Dockerfile 与 deploy.yaml，按部署契约进 ECS，运行时配置走 SSM。
  • 历史消息存储
    • 短期：PostgreSQL + pgvector 同库。当前量级追加写无瓶颈，按用户过滤后候选集很小，同库做向量查询不需要 CDC。
    • 长期：写入量上来后，日志迁到追加型日志存储（日志追加负载，宽表或带排序键的 KV 模型），经 CDC 同步到向量索引（搜索负载，倒排加向量索引）。
      • options：追加型日志存储
        方案优点缺点
        DynamoDB【选定】（B-tree + WAL）分区键 session、排序键时间（顺序读和分页是原生模式）；TTL 内建；Streams 即 CDC；托管零运维和厂商绑定
        Cassandra / HBase（LSM-tree）宽表加时间聚簇的模型完全匹配，消息与日志系统的经典选择；写吞吐高；开源可迁出自管集群运维重，HBase 还要拖 Hadoop 与 ZooKeeper；CDC 要另搭
      • options：向量索引
        方案优点缺点
        OpenSearch【选定】按用户过滤后 kNN 加 BM25 混合检索原生支持，用户提品牌名、品类词时关键词比向量准；增量写、按文档删方便；托管版有比纯向量库重；相关性调参要投入
        独立向量库（Milvus、Qdrant、Pinecone 一类）大规模 ANN 性能强，向量专用功能全召回限定在单用户历史内，候选集小，ANN 规模用不上；无原生全文混合；多一个系统
        Vespa混合检索能力最强，向量、全文、结构化过滤一体极重，学习和运维成本高；对单用户小候选集是杀鸡用牛刀
      • conclusion：DynamoDB 存日志，Streams 作 CDC，OpenSearch 做向量索引。
      • tradeoff
        • 托管换锁定：DynamoDB 与 OpenSearch 都用 AWS 托管版，换来零运维和内建的 CDC、TTL，付出和厂商绑定。Maya 本就跑在 AWS 上，可接受。
        • 分开换复杂度：日志与索引分成两个系统各取所长，付出一条 CDC 链路和两套运维。
        • 混合检索换重量：OpenSearch 比纯向量库重、相关性要调参，换来过滤后的向量加关键词混合检索。
  • FAQ 知识库检索
    • 短期：沿用 OpenAI FileSearch，不动，减少本次工作量。
    • 长期：需要按版本失效、评测召回或混合检索时，切到自建 OpenSearch，与历史召回同引擎。
    • options
      方案优点缺点
      OpenAI FileSearch（现状）【短期】托管，零工程；可强制调用，支持属性过滤和文件引用检索发生在供应商侧，命中什么、怎么排序看不到也调不了；只能评最终回答，评不了召回；没有关键词混合；版本失效靠切换向量库或属性过滤，口径管理在供应商边界内
      PostgreSQL + pgvector【不选】与历史消息同库，索引和检索代码复用；过滤与版本是普通列没有原生全文；历史召回长期已定 OpenSearch，知识库再走一条线会多一套索引
      自建 OpenSearch【长期】检索过程全部可见可评；过滤后向量加关键词混合；按版本字段过滤与失效；出处是文档自己的字段；与历史召回同引擎切块、建索引、评测全部自己做；比托管方案多一套运维
    • conclusion：短期沿用 FileSearch，长期视情况切自建 OpenSearch。
    • tradeoff
      • 省工程量换可控延后：沿用 FileSearch 本次零工程，付出的是召回不可见不可评、版本靠供应商机制，这些问题暴露时再切。
      • 切换成本可控：自建的切块、索引、评测和历史召回共用一套，届时边际成本小。

2.2 重构方案

2.2.1 编排

方案选型
方案是什么优点缺点
代码优先的手写循环（现状）【不选】openai-agents SDK 的形态：一个 run loop，模型通过 handoff 和工具调用决定下一步零改动，写法直接控制流在循环体内，终态靠模型自觉，每种终态要单独兜底
持久化工作流引擎（Temporal 类）【不选】面向长时任务的可靠执行：持久化、重试、超时执行可靠性强不提供结构化输出、流式和工具循环的约束；对几秒一轮的对话是多余的重量
LangGraph【选定】把一轮对话写成显式状态图：节点、条件边、子图，自带 checkpoint、interrupt、步数上限、流式控制流在边上不在模型输出里，终态由出口节点保证；Maya 的流程边界有限、画得出来引入新依赖，节点、状态、边全部要重写
对话状态图
  • 循环归代码，模型只判断意图
    • Router 是一次结构化输出：意图枚举，多步时带顺序；走哪条边由代码映射，不解析自由文本。
    • agent 子图内部是工具循环，模型每步只输出结构化决定：调哪个工具、给出结果、还是需要澄清；条件边按字段判定。
    • 工具调用是结构化输出，参数经 schema 校验后由代码执行；工具报错压缩成一条结果写回 state，不把 stack trace 喂给模型。
  • 终态由结构保证
    • 每个子图只有一个出口节点，出口有 schema：Fashion 出检索条件或澄清问题，Account 出结构化事实，FAQ 出带出处的回答。
    • 模型输出不满足出口 schema 时进不了终态：有步数余量就回循环，没有就走澄清出口。模型无法以 EOS 结束一轮。
    • 现状的流末兜底（wait cue、overlay）不再存在：它们兜的是「模型停在半路」，图里没有这条路径。
  • 步数上限与弹窗
    • 每个子图设 recursion_limit；超限进固定的兜底出口（澄清或失败文案），不向用户抛异常。
    • consent 与问卷弹窗是本轮的一个终态：入口节点按 Context Hub 的判定直接出弹窗，本轮结束；用户处理后的下一条消息作为新一轮进入口重新判定（受约束「前端契约不变」；约束解除时改为 interrupt 加恢复接口，本轮原地续跑）。
  • 流式与 SSE 适配
    • 图以 stream 方式运行，三类事件：节点更新（进度）、token（文本流式）、自定义事件（结构化消息）。
    • SSE 适配层在图外，把事件映射到现有消息类型；消息送达时写消息表（受约束「前端契约不变」；约束解除时按终态类型重新定义消息 schema，适配层消失）。

方案选型
方案是什么优点缺点
每轮从 Context Hub 拉历史回放（现状）【不选】对话经 RocketMQ 异步写入 Context Hub，每轮拉最近 20 行清洗后回放进内存 Session零改动两份真源；异步链路静默丢；每轮多一次 hub 往返和清洗；只有倒序取 20 行一个接口，窗口外的历史用不上

会话定义
方案定义优点缺点
前端定义会话（现状）【不选】sessionId 由前端生成放在 cookie，App 或 Web 重开即换零改动历史页按用户展示、模型记忆按 session 取，Maya 认不出对话框里正在展示的历史

上下文管理
  • 用户本轮输入：用户当前输入的消息（文本/图片等）。
  • 历史消息：按照 session 跨轮持久化存储，每轮追加（展示用的历史接口读同一份存储，不另存）。
    • 窗口内：最近 N 轮原文。
    • 窗口外：摘要是超预算时把更早轮次压缩成的事实概要；相似召回是按当前输入从全部历史中命中的相关旧轮。两者互补。
      • 相似召回以一轮为索引单位，按用户过滤后做向量加关键词的混合检索，召回质量用离线评测集做门禁。
  • 外部数据源：按需拉取、不落盘。
    • 画像每轮拉。
    • 天气、用户数据、知识库按路由拉：Router 判出对应意图后才取（天气的独立入口不经 Router，直接取）。
  • system prompt：角色、规则、工具定义（版本化配置，见 边界与契约）。

2.2.3 边界与契约

方案选型
方案是什么优点缺点
后处理修 JSON（现状）【不选】模型输出自由文本，代码在其中切出 JSON 块，缺括号补括号、尾逗号去掉、嵌套字符串再解一层，全部失败则当普通回复不依赖模型能力方向反了：用代码猜模型想表达的结构，猜对靠运气，猜错静默跳过；嵌套对象常以转义字符串出现要再解一层；解析失败不是异常，是一条 warning
外挂解析重试库（instructor 一类）在模型调用外包一层：按 pydantic schema 校验，失败把错误回灌给模型重试不依赖模型侧的约束能力，schema 即契约多一层依赖，每次失败多一次模型调用；和 LangChain 的结构化输出接口重复
模型侧结构化输出【选定】每个 LLM 节点声明一个 pydantic schema，模型按 schema 约束生成（OpenAI structured outputs，经 LangChain 的 with_structured_output 调用），输出直接是类型化对象输出要么是合法对象，要么是异常，没有中间态；嵌套天然是对象；schema 就是节点的出口契约，和 2.2.1 的出口校验是同一件事依赖供应商支持；约束生成对少数复杂 schema 可能降低回复质量，需评测验证

2.2.4 观测与评测

方案选型
  • 短期：LangSmith，LangGraph 原生集成，trace、评测集、评测器一体，零运维。
  • 长期：trace 量上来后费用成为问题时，切自托管 Langfuse，trace 格式兼容，评测集可导出迁移。
方案优点缺点
LangSmith【短期】LangGraph 原生上报，节点级 trace 零配置；trace、数据集、评测器、成对对比一个平台；SaaS 零运维按 trace 量付费，流量上来后成本可观
自托管 Langfuse【长期】开源，功能对标 LangSmith；LangChain 回调一行接入自己运维一套服务和存储；评测器生态弱于 LangSmith
OpenTelemetry GenAI 约定 + 自有存储【不选】标准化，不绑平台；可并入现有 Grafana 一类的观测栈只有 trace 没有评测：数据集、打分器、成对对比全部自建；LangGraph 节点级语义要自己打点

指标数兜底触发的日志行当终态缺失率终态缺失率、延迟、成本从 trace 查询
评测集无，验证靠手工六个集从生产 trace 筛样例加人工标注：路由、工具调用、终态完整性、离题、图片识别、FAQ 准确性

prompt文件加 Redis 覆盖，无版本版本化配置，版本随 trace 上报，是评测能归因的前提
