Job Scheduler

题外话：通用法则（从这道题提炼）
建模
  • 定义和实例分开：Job 是定义，Execution 是一次执行；状态、重试、幂等键都挂在实例上。
  • 按时间触发的数据，按时间分桶做分区键，读取时只扫"当前桶 + 下一个桶"。
精度和持久分层
  • DB 负责持久（低频扫描一个时间窗口），延迟队列负责精度（到点才可见）。
  • DB 是唯一数据源；队列、缓存里的东西丢了，都要能从 DB 补回（reconciler）。
可靠性
  • at-least-once + 幂等，不追求 exactly-once。
  • 状态迁移用条件写，带 attempt / epoch 做 fencing，挡住过期 worker 的回写。
  • 失败先分类：不可重试的直接失败，可重试的指数退避 + 抖动，超过次数进 DLQ。
读写分离
  • 高频写的主表不挂查询索引；查询通过 change feed 异步同步到专门的查询表，查询侧故障不影响主链路。
1

功能需求

核心

  • 提交任务：立即执行、指定时间执行、周期执行（cron，比如每天 10:00）。
  • 查询任务状态：我提交的任务、某次执行的结果。

范围外

  • 取消、改期。
  • 任务之间的依赖（DAG / workflow）。
2

非功能需求与估算

核心

  • 准时：计划时间后 2s 内开始执行。
  • 吞吐：峰值 10k 次执行/s。
  • 可靠：至少执行一次（at-least-once），已提交的任务不丢。
  • 可用性优先于一致性：调度和执行链路高可用；状态查询可以最终一致（延迟几秒）。
  • 隔离：一个任务慢或失败，不影响其他任务。

估算

  • 执行记录：10k/s ≈ 每天 8.6 亿条 × 200B ≈ 170GB/天。单机 DB 扛不住，要分区，并设 TTL 或归档。
  • 并发：平均执行 2s × 10k/s ≈ 2 万个并发执行槽，决定 Worker 集群的规模，必须能自动扩缩容。
  • 核心难点：准时（秒级精度）+ 高吞吐 + 不丢不重（at-least-once 下的幂等）。
3

核心实体与 API

  • Task：可复用的任务类型（比如"发邮件"），对应一个 handler。
  • Job：Task + 调度规则 + 参数，用户提交的就是它。
  • Execution：Job 的一次具体执行，周期任务会有很多条。状态和重试都挂在 Execution 上。
  • User：任务的提交者。
POST /jobs
  body: { task_id, schedule: { type: IMMEDIATE | DATE | CRON, expression }, parameters }
  → { job_id }

GET /jobs                                     → 当前用户创建的 Job
GET /executions?status=FAILED&start=..&end=..  → 当前用户的执行记录（状态查询主要用这个）
GET /jobs/{job_id}/executions                 → 某个 Job 的每次执行：时间、状态、attempt、错误

user_id 都从 token 取，不放在 body 或 path 里
4

高层设计

Client ──► API Gateway ─┬─► Job Write Service ──► DB（Jobs + Executions）
                        │        └─ 当前窗口内的任务直接投递 ──────────────┐
                        └─► Job Query Service ──► Execution 查询表         │
                                                       ▲ change feed       │
DB ──► Watcher × N（每 5 分钟扫未来 5 分钟）──► 延迟队列（Service Bus）◄─────┘
                                                   ──► Workers（AKS + KEDA）──► 回写 DB
                                                   └─► DLQ
Reconciler：扫描已到期但长时间未进入终态的 Execution，重新投递

① 提交：Job 和 Execution 分两张表

  • 写入 Jobs，同时写入第一条 Execution（PENDING）。
  • Jobs 用 job_id 当 PK：高频访问是 Watcher 和 Worker 按 job_id 点查；job_id 随机，写入均匀。"列出我的 Job"走 user_id 的 GSI。
  • Executions 按时间分桶：调度层只查"当前小时和下一小时这两个桶里、时间 ≤ 某值"的记录，不扫全表。
  • Execution 冗余存 task_id 和参数，Worker 执行时不用再查 Jobs。
表结构
Jobs
  PK  job_id
  user_id, task_id, schedule, parameters
  GSI user_id                                 -- 列出我的 Job

Executions（调度用）
  PK  time_bucket#shard                       -- 执行时间按小时取整 + hash(job_id) % N
  SK  execution_time#job_id
  status: PENDING | QUEUED | RUNNING | SUCCEEDED | FAILED
  attempt, user_id, task_id, parameters

Execution 查询表（状态查询用，change feed 异步写入）
  PK  user_id#k                               -- 大租户拆成 k 片
  SK  execution_time

② 执行：Watcher → 队列 → Worker

  • 最简版：Watcher 每隔几秒查一次已到期的 PENDING 记录 → 投进队列 → Worker 执行 → 回写状态。
  • 问题：轮询间隔决定准时精度，高频轮询压垮 DB → 引出深入部分的两层调度。

③ 查询：读写拆成两个服务

  • Job Write Service：依赖 DB 和队列，必须持久化成功才返回。
  • Job Query Service：只读查询表，可以最终一致。
  • 各自按自己的 QPS 独立扩缩容，故障互相隔离。
5

深入

2s 内准时执行

方案做法问题
差：轮询 DBWorker 每秒查一次到期任务DB 压力大，精度仍受轮询间隔限制
较好：Redis sorted setscore = execution_time；Watcher 预加载未来几分钟；Lua 原子取出到期任务要高可用、能从 DB 重建；ack、重投、DLQ 都要自己实现
好：两层调度（选这个）Watcher 每 5 分钟扫未来 5 分钟，按 execution_time − now 设延迟投进延迟队列，到点才可见准时性还依赖 Worker 余量
  • 延迟队列：Service Bus scheduled message（ScheduledEnqueueTimeUtc）；SQS 用 DelaySeconds，最长 15 分钟，所以扫描窗口要小于 15 分钟。
  • 新提交的任务：落在当前窗口内的，由 Job Write Service 直接投队列，不等下一轮扫描。
  • Worker 通过长轮询或长连接等待，消息一到期就被取走。
  • 监控"计划时间 → 实际开始"的延迟。
题外话：MQ 的延迟能力
MQ单条任意延迟取消ack / 重投 / DLQ说明
Service Bus支持支持（和激活有竞态）自带到点才入队，投递时间受负载影响
SQS≤ 15 分钟不支持自带FIFO 队列不支持单条延迟
RocketMQ 5.x支持（时间轮）有限自带4.x 只有 18 个固定级别
Pulsar支持（deliverAt）不支持自带只在 Shared 订阅下生效
Kafka不支持不支持只有 offset只追加、按 offset 顺序读，未到期消息会队头阻塞
  • Kafka 的时间轮在 broker 内部，用来管理 produce 等待副本确认、fetch 长轮询这类延迟操作，不对用户提供延迟消息。变通做法：按固定延迟分 topic，队头没到期就 pause 分区；或者消费者自己维护时间轮。
  • 时间轮和堆：时间轮插入和取消 O(1)，堆是 O(log n)；适合定时器多、大量会被取消、精度到一个 tick 就够的场景。Kafka 的 DelayQueue（堆）只存非空的槽，用来推进时间轮。
Redis sorted set 方案
  • ZADD due:{shard} <exec_time> <execution_id>；Lua 原子执行"取出到期的 + 删除"；取消和改期直接 ZREM / ZADD。
  • 主从复制是异步的，故障切换会丢最近的写入 → DB 是数据源，丢失的任务靠 reconciler 补回。
  • 一个 zset 只落在一个节点上 → 按 shard 拆成多个 key。
  • 没有 ack / visibility timeout → 用 processing zset（score = 租约到期时间）自己实现。
  • 适用场景：频繁取消或改期、超过 15 分钟的任意延迟、按优先级或租户自定义取出顺序。

扩展到 10k/s

  • Executions 写热点：同一小时的写入全部落在同一个 time_bucket 分区上 → 改成 time_bucket#shard，Watcher 并行查 N 个分片。
  • 状态查询移出主写链路：Executions 不挂 user_id 的 GSI（每次状态更新都会写放大，GSI 写不过来时还会反压主表）；状态变更通过 change feed（Cosmos DB）/ Streams（DynamoDB）异步写入查询表。
  • Watcher 横向扩展：每个实例按租约持有一部分 shard（etcd / ZooKeeper / DB 条件写），实例挂了，租约过期后由其他实例接管。
  • 队列：Service Bus 开分区，或按 shard 拆成多个队列。
  • Worker：AKS + KEDA 按队列积压扩缩容。
    • 保留最小副本数作为常驻余量，不缩到 0。
    • 副本数 = max(当前积压 ÷ 单 Pod 目标值, Watcher 给出的未来 5 分钟到期数 ÷ 单 Pod 目标值)，提前应对整点峰值。
    • 缩容时优雅退出：停止拉取，跑完当前任务再 ack；没跑完的靠重新投递和幂等兜底。
    • 短任务可以用 serverless（Azure Functions）；长任务用容器 + 心跳。

至少执行一次

失败场景处理
任务报错先分类：参数错误不重试；可重试错误指数退避 + 抖动，超过最大次数进 DLQ
Worker 崩溃没 ack 的消息在 visibility timeout / lock duration 后重新可见，由其他 Worker 取走；超过 MaxDeliveryCount 进 DLQ
长任务被误判超时心跳续期 lock
过期 Worker 回写条件写带 epoch（fencing），被拒绝
重复消息记录已经是终态就直接 ack，不再执行
Watcher 扫描后、投递前崩溃投递后条件更新为 QUEUED；reconciler 扫描"已到期但长时间未进入终态"的记录并重新投递
  • 幂等键：execution_id，下游按它去重。
  • 状态迁移：PENDING → QUEUED → RUNNING → SUCCEEDED / FAILED，每一步都是条件写。
  • 立即执行的任务可以用 transactional outbox：Execution 和待投递记录写在同一个事务里。

周期任务

  • 不预先生成所有未来的 Execution，只保留"下一次"；当前这次投递或完成时，按 cron 表达式算出下一次并写入。
  • 时区和夏令时：按用户原始时区计算，存储用 UTC。
  • 停机后错过的执行：补跑还是跳过由 Job 配置决定；补跑时限速，避免压垮下游。

多租户公平性（可选）

  • 按租户限制并发，防止一个大客户占满所有 Worker。
  • 高优先级任务用单独的队列。

面试讲述顺序

  1. 需求与估算：难点是准时 + 高吞吐 + 不丢不重。
  2. 主线：Job / Execution 分表 → Watcher 轮询 → 队列 → Worker。
  3. 深入：两层调度 → 分片和查询表 → at-least-once 和幂等 → 周期任务 → 多租户。
