Ticketmaster

1

功能需求

核心

  • 用户查看演出。
  • 用户搜索演出。
  • 用户订票。

范围外

  • 用户订票历史。
  • 后台创建演出。
  • 动态定价。
2

非功能需求

核心

  • 搜索和浏览优先可用，订票优先一致：绝不双卖。
  • 规模：单场热门演出 1000 万并发用户。
  • 搜索延迟：500 ms 内。
  • 读多写少：读写比约 100:1。

落到答题框架的三个点

  • CAP：同一系统两种取舍，搜索和演出详情要 A，预留和支付转正要 C。
  • 延迟：搜索 500 ms 内，座位图要实时变化。
  • 规模：1000 万并发是同时在线，不是每秒请求。真正的写压力在预留，预留次数远大于成交，这个差距决定预留写入不能直接打数据库。
3

核心实体

  • Event：日期、描述、类型、演出者。Performer：名字、简介。Venue：地址、容量、座位图。
  • Ticket：eventId、座位、价格、状态 available / reserved / booked。库存。
  • Booking：userId、ticketIds、总价、状态 in_progress / confirmed。订单。
  • 为什么 Ticket 和 Booking 分开：票是库存，订单是一次购买行为。一单买多张票，总价和支付流水是订单级属性；bookingId 是支付的句柄和幂等键；一张票可能被尝试购买很多次，放弃的记录要留在订单里不能覆盖掉。
4

API

  • GET /events/:eventId → Event、Venue、Performer、Ticket[]。
  • GET /events/search?keyword&start&end&page → Event[]。
  • POST /bookings/:eventId，body 带 ticketIds → bookingId。用户 id 从认证取。
5

高层设计

客户端 ──► API Gateway ──┬─► Event Service ──► Redis 缓存 ──► PostgreSQL（Event / Venue / Performer / Ticket）
                          ├─► Search Service ──► Elasticsearch（CDC 从 PostgreSQL 同步）
                          └─► Booking Service ──► 预留层 ──► PostgreSQL（Ticket / Booking）──► Stripe
  • 看演出：Event Service 查库返回演出、场馆、座位，读多改少，前面放缓存。
  • 搜演出：Search Service 查 Elasticsearch，PostgreSQL 是真相，CDC 同步过去。
  • 订票：Booking Service 先预留再支付，支付成功在 PostgreSQL 事务里转正。预留层是什么见深入。
6

深入

预留：填完支付发现票没了

方案做法预留存在哪问题
长事务行锁SELECT ... FOR UPDATE 开着事务等用户付完未提交的事务连接独占几分钟，服务有状态，B 是阻塞等待不是立刻被拒，不可用
状态 + 过期 + cronTicket 加 reserved 状态和 expires_at，cron 定期改回 available已提交的数据过期到 cron 跑到之间票空置，cron 是单点
隐式状态预留条件写成 status='available' OR (status='reserved' AND expires_at < now())，过期的直接被覆盖已提交的数据读路径多一个 OR 条件。纯数据库的最优解
Redis 锁SET seat:{id} {bookingId} NX EX 600，TTL 到期自动释放Redis key多一套组件，座位图要合并两个源，Redis 故障时预留退化
  • 教程选 Redis 锁，理由是预留次数远大于成交，大量选座后放弃的写入不该打数据库。流程：拿锁 → 建 in_progress 的 Booking → 客户端用 Stripe.js tokenize 卡号 → webhook 回来开事务 UPDATE tickets SET status='booked' WHERE id IN (...) AND status='available'，bookingId 做幂等键 → Lua 比对 value 再 DEL 锁。
  • 多座位：多个 key 的 SET NX 不原子，用 Lua 先全部 EXISTS 检查再逐个 SET，Cluster 下 key 带 hash tag 落同一 slot。SET NX 是非阻塞 try-lock，没有等待就没有死锁，最坏是部分成功要清理。
  • 三个坑：座位图要合并数据库的 booked 和 Redis 的 reserved，用 sorted set 按过期时间做索引一次取出，或把 reserved 写穿到数据库；Redis 挂了预留停摆但不双卖，数据库那条 AND status='available' 兜底；TTL 在支付中途过期会让两人都付成功然后一个被退款，点支付时续期 EXPIRE。
  • 正确性永远在数据库：四个方案最终都靠支付时那条条件 UPDATE 只让一个成功，锁和状态只决定体验和效率。

热门场次：几百万人同时抢

  • 问题：座位图是静态快照，用户点的座位已经没了，反复失败，同时预留请求把 Redis 和后端打满。
  • SSE 实时座位图：座位被订走就推给所有看这一场的客户端。Taylor Swift 量级下座位瞬间消失，实时也救不了体验，而且不解决过载。
  • 虚拟排队（教程选择）：请求购票页先进 Redis sorted set 按时间排队，SSE 推排位，调度按容量定期放行，放行的拿带 TTL 的 admitted 标记，预留接口校验标记。机制见知识图谱的排队。
  • 公平：按到达时间排队脚本永远在前，开售前候场随机排序，开售后才按到达时间。

锁还是排队（自己的判断，教程没有合起来比）

教程把 Redis 锁和虚拟排队放在两个 deep dive 里分别回答"预留怎么做"和"热门场次怎么扛"，没有合起来看。合起来看，两者都挡在数据库前面，是二选一。

Redis 锁排队
管什么争用，同一个座位谁拿到过载，总共放多少人进来
预留存哪Redis，座位图读两个源数据库隐式状态条件写，座位图读一个源
谁赢SET NX 先到先赢，网络竞速，脚本占便宜按放行顺序，可以先到先得也可以随机
用户体验立刻知道抢到没有先等，知道排第几
正确性都靠数据库支付时的条件 UPDATE
  • 放行速率本来就按数据库容量定，放进来的人直接条件写预留，偶尔撞同一座位的重试代价可以忽略，再加锁是重复建设。
  • 选法：请求量数据库接得住，隐式状态条件写；接不住又不想让用户等，Redis 锁；量级大到 Redis 也要分片或要公平，排队。
锁的做法：每座一个 key
预留   SET seat:{eventId}:{seatId} {bookingId} NX EX 600，多座位用 Lua 先全部 EXISTS 再逐个 SET
       同时在 bookings 表插一条 in_progress，票表不动
支付   webhook 回来开事务 UPDATE tickets SET status='booked' WHERE id IN (...) AND status='available'
       影响行数等于座位数才提交，否则回滚退款
释放   Lua 比对 value 是自己的 bookingId 再 DEL
过期   TTL 到了 key 自己消失，座位自然可用
读     座位图合并两个源：数据库给 booked，Redis 给正在锁着的

预留期间数据库一笔预留写入都没有，几十万人选座放弃全在 Redis 里消化。

排队的做法：放行后条件写预留
排队   ZADD queue:{eventId}，按数据库容量放行，放行的拿带 TTL 的 admitted 标记
预留   放行的人直接 UPDATE tickets SET status='reserved', booking_id=?, expires_at=now()+10min
       WHERE id=? AND (status='available' OR (status='reserved' AND expires_at < now()))
支付   UPDATE tickets SET status='booked' WHERE id=? AND status='reserved' AND booking_id=?，为 0 退款
过期   不用回收任务，过期的票被下一个人的预留条件直接覆盖
读     座位图只读数据库

读扩展：1000 万人看详情

  • 演出、场馆、演出者信息读多改少，Redis 缓存 read-through，key 用 eventId，失效靠数据库触发器通知加 TTL 兜底。
  • Event Service 无状态，负载均衡后横向扩。

搜索：500 ms 内

  • 加索引和 SQL 优化：LIKE '%keyword%' 走不了索引，部分匹配仍然慢。
  • 数据库全文索引：PostgreSQL tsvector 加 GIN，比 LIKE 快很多，维护成本高。
  • Elasticsearch（教程选择）：倒排索引、模糊匹配，PostgreSQL 通过 CDC 同步过去，ES 只做读不当真相。
  • 热门搜索词缓存：ES 自带 shard 级 filter 和 request cache，结果不带个性化可以再上 CDN。
