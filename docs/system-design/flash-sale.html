Flash Sale（秒杀）

1

功能需求

核心

  • 用户查看秒杀商品和剩余库存。
  • 活动期间用户预留一件，预留有时限。
  • 预留成功的用户在时限内完成支付。

范围外

  • 商品目录浏览和搜索。
  • 物流、退货、退款、订单历史。
  • 后台创建和配置活动。
2

非功能需求

核心

  • 不超卖：1 万件就是 1 万件，预留和支付转正都要强一致。
  • 规模：几千万用户在开售几秒内涌入，请求数远超件数。
  • 低延迟：预留请求几百毫秒内返回成功或售罄。
  • 公平：先到先得，防脚本刷单。

落到答题框架的三个点

  • CAP：预留和支付转正要 C，库存展示要 A（余量是派生值，几秒过时可接受）。
  • 延迟：预留几百毫秒内，大部分请求在排队层或 Redis 就被挡回去，不碰数据库。
  • 规模：开售瞬间每秒几十万到百万请求，成功的只有 1 万，预留写入和成交写入差四五个量级，这个差距决定预留不能放数据库。
3

核心实体

  • Item：商品、总量、活动起止时间。
  • Inventory：库存。单计数器方案是一行 sold / total，拆行方案是一件一行带 status。
  • Order：用户、商品、状态 pending / paid / expired、预留到期时间，orderId 做幂等键。
4

API

  • GET /items/{itemId} → 商品信息、剩余库存、活动状态。
  • POST /items/{itemId}/orders → orderId 或售罄。用户 id 从认证取，不传参。
  • POST /orders/{orderId}/pay → 支付结果。orderId 就是幂等键，重试不重复扣。
5

高层设计

客户端 ──► 排队层（虚拟队列，按容量放行）──► API 服务器 ──预留──► 库存（Redis 计数器 或 DB 拆行）
                                                    │                    │
                                                    └──建 Order pending──► 订单库 ◄──支付 webhook：条件写转正
客户端 ──看库存──► 缓存（余量，几秒刷一次）
  • 看库存：余量是派生值，从库存源定期算好放缓存，所有人读缓存，不打库存源。
  • 预留：排队层先把流量压到系统能承受的速率，放行的请求去库存源抢一件，抢到建 pending 订单带到期时间，抢不到返回售罄。
  • 支付：用户在时限内付款，webhook 回来用条件写把订单转正。到期没付，库存还回去。
6

深入

极端争用下不超卖

核心矛盾是所有请求争同一份库存。单行计数器 UPDATE stock = stock - 1 WHERE stock > 0 所有请求争一行锁，串行，每秒几百到顶。热点行悲观乐观都不行，要把冲突散开。

做法预留不超卖靠什么吞吐代价
单行计数器条件 UPDATE 减一行锁加条件每秒几百热点行，基线
DB 拆行一件一行，SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1 随便锁一行没人用的一行同一时刻只能被一个事务锁每秒几千只多扛一个数量级。假售罄要重试，补货单独锁，降到 RC 避 Gap 锁。好处是库存和订单在同一个事务里，不用对账
Redis 预扣DECR stock:{sku}，结果小于 0 就 INCR 回去Redis 单线程原子，DB 落库时条件写兜底每秒十万级多一个组件，过期回补要延迟队列，两边要对账
  • 拆行为什么用 SKIP LOCKED 不用乐观锁：乐观锁是"我知道改哪行，赌没人抢"，拆行抢购是"我不在乎哪行，给我一行没人在用的"。乐观写法先查后改，高并发下大家查到同一行，999 个失败重试，拆了等于没拆。SKIP LOCKED 让数据库把不同的行分给不同的事务，一次往返零重试。持锁只有预留事务的几毫秒，符合"冲突多、事务短、必须成功"用悲观的规则。
  • 怎么选：默认 Redis 预扣，数据库只见到真正付钱的。拆行是备选，只在团队只有关系库、不想加组件、峰值每秒几千内、不想做两系统对账时用。量级更大或要公平，排队放行，见下一节。
  • 和 Ticketmaster 的对应：座位有身份，每座一个 key 用 SET NX EX，过期靠 TTL 自动消失。库存可互换，一个计数器 DECR，过期要主动 INCR 还回去。

预留之后：等支付、过期、转正

两种做法同一个形状：短事务占位，长时间等支付，到期回收，支付成功转正。

  • DB 拆行：
    • 预留事务把行改 reserved 带 reserved_until 和 orderId，提交即释放锁，之后靠状态占位。
    • 支付成功 UPDATE unit SET status='sold' WHERE id=? AND status='reserved' AND order_id=?，为 0 说明预留已过期被别人拿走，退款。
    • 过期回收两种：cron 定期把过期行改回 available，有延迟。或者预留条件写成 status='available' OR (status='reserved' AND reserved_until < now())，过期的行直接被下一个人拿走，不要回收任务。
  • Redis 预扣：
    • DECR 成功后建 pending 订单，同时发一条 10 分钟后到期的延迟消息。
    • 支付成功 DB 事务 UPDATE inventory SET sold = sold + 1 WHERE sku=? AND sold < total，为 0 说明 Redis 计数漂了已超卖，退款。这条是最终兜底，Redis 挂了也不超卖。
    • 延迟消息到期查订单，没付就 INCR 还回去。不用 Redis 的 key 过期事件，它不可靠会丢。
  • 假售罄：剩 3 件来 10 人，7 人看到售罄，但 3 人可能不付，货又回来。售罄提示留重试余地。

锁还是排队（自己的判断）

Redis 预扣和排队都挡在数据库前面，是二选一。排队的放行速率按数据库容量定，放行人数可以直接等于库存数，放进来的人直接条件写扣减，几乎没有争用，再加 Redis 预扣是重复建设。

Redis 预扣排队
管什么争用，DECR 原子分胜负过载，按数据库容量消费订单
预留存哪Redis 计数器，过期要延迟消息 INCR 还回去数据库 reserved 计数，worker 消费 MQ 时条件写，过期靠隐式状态或 cron
谁赢DECR 先到先赢，网络竞速，脚本占便宜按入队顺序消费，先到先得
用户体验立刻知道抢到没有显示抢购中，轮询结果
正确性都靠数据库支付时的条件写 WHERE sold < total
  • 选法：请求量数据库接得住，单行条件写或拆行；接不住又不想让用户等，Redis 预扣；量级大到 Redis 也要分片，订单进 MQ 任务排队。
  • 和 Ticketmaster 的对应：座位有身份，锁是每座一个 key，过期靠 TTL 自动消失；库存可互换，锁是一个计数器，过期要主动 INCR。排队也不同，座位要用户自己挑所以人排队发许可，库存点抢购时已选好所以订单进 MQ 当任务排队，判据见知识图谱的排队。
锁的做法：Redis 计数器
预留   DECR stock:{sku}，结果 >= 0 成功建 pending 订单并发一条 10 分钟延迟消息，< 0 则 INCR 回去返回售罄
支付   UPDATE inventory SET sold = sold + 1 WHERE sku = ? AND sold < total，为 0 退款
过期   延迟消息到期查订单没付就 INCR 还回去

DECR 本身是原子的，不需要 NX 和 Lua。所有抢购请求都到 Redis，失败的在 Redis 就被挡回去，数据库只见到付钱的。

排队的做法：订单进 MQ
入队   点抢购时商品已选好，订单直接进 MQ，返回 orderId，页面显示抢购中
消费   worker 按数据库容量的速率消费，每单一条条件写
       UPDATE inventory SET reserved = reserved + 1 WHERE sku = ? AND reserved + sold < total
       为 0 则订单标售罄
结果   客户端轮询 GET /orders/{id}，成功进支付，失败显示售罄
支付   条件写转正，为 0 退款
过期   cron 或隐式状态把过期的 reserved 还回去

用户点抢购时已经选好商品，剩下的扣件建单机器能替他做，所以排的是订单不是人，不需要放行许可那一套。

扛住开售瞬间的流量

  • 排队层：选排队方案时，订单进 MQ，worker 按库存源能承受的速率消费。几千万人点抢购，库存源每秒只见到几千条。
  • 提前拒绝：库存已经为 0 时在网关或缓存层直接返回售罄，请求不进排队。
  • 库存展示不打源：余量放缓存几秒刷一次，或者 SSE 推，几千万人刷页面不碰 Redis 计数器。

公平与防刷

  • 按到达时间排队的结果是脚本永远排最前。开售前开放候场，候场内随机排序，开售后才按到达顺序。
  • 每用户限购一件：orderId 幂等键之外，预留时 SET bought:{sku}:{userId} NX 或订单表 (sku, userId) 唯一约束。
  • 验证码、设备指纹、限流放在排队层之前，不进入正文。

变体：12306 的区间库存

  • 库存单位是车次 × 日期 × 座位 × 区间。一列车停 10 站是 9 个区间，一个座位卖了北京到南京占前 7 段，南京到上海的 2 段还能卖。
  • 每座位一行一个位图记哪些区间被占。买 [i, j) 要求目标位全 0：UPDATE seat SET occupied = occupied | :mask WHERE ... AND (occupied & :mask) = 0，为 0 换下一个座位。就是拆行加条件写，"可用"的判断从一个状态位变成一段位的 AND。
  • 余票是派生的，每个区间对要扫所有座位算，放缓存定期刷，显示的只是参考，下单以条件写为准。
  • 开售加排队系统，提交后异步出票、客户端轮询结果，没票可登记候补由后台撮合退票。
