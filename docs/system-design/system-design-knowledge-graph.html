PART 0

总览

答题框架

流程约 40 分钟：需求 5 分钟，核心实体 2 分钟，API 5 分钟，高层设计 10 到 15 分钟，深入 10 分钟。

  • 非功能需求的落脚点：
    • CAP（分布式系统 P 一定要保证，只在 C 和 A 之间取舍，两者不能同时满足）：同一个系统里不同功能点的取舍可以不一样（e.g.: Ticketmaster 搜索和浏览要 A、订票要 C，Tinder 卡片 feed 要 A、滑动配对要 C etc.）
      • 大部分功能点要 A，保证最终一致就行（e.g.: Dropbox 多设备同步晚几秒、News Feed 新帖晚几秒出现、Ad Click 计数分钟级更新、Live Comments 评论允许丢、Ticketmaster 搜索结果走 CDN 缓存 etc.）。
      • 少数功能点要 C（e.g.: Ticketmaster 不能双卖、Uber 一个司机只派一单、Tinder 一次互滑只产生一个 match、Gopuff 库存不超卖、竞拍出价、支付 etc.）。
    • 延迟：一般 200 到 500 ms（e.g.: feed 200 ms 内、搜索 500 ms 内 etc.），实时交互要更低（e.g.: Tinder 滑动 100 ms 内 etc.）。
    • 规模：先问 DAU 和读写比，估 QPS 和存储量，决定读写扩展怎么做。
    • 大部分系统上述三点就够，少数系统还要加：
      • 持久性（e.g.: Dropbox 文件丢了要能恢复、WhatsApp 消息必须送达 etc.）。
      • 容错（e.g.: WhatsApp 单个组件挂了不影响整体、Flink 挂了从 checkpoint 恢复 etc.）。
      • 安全（e.g.: Ad Click 点击带 HMAC 签名防伪造 etc.）。
      • 环境约束（e.g.: Uber 司机每 5 秒上报一次位置要省电省带宽、Dropbox 要传 50 GB 大文件 etc.）。
      • 突发流量（e.g.: Ticketmaster 开售、Uber 同一地点 10 万请求、Flash Sale etc.）。
  • API 设计：
    • 按资源命名，动作交给 HTTP 方法（e.g.: POST /bookings、GET /events/:id etc.）。
    • 分页用游标不用 offset，游标是上一页最后一条的 id 或时间戳，offset 深分页要扫过前面所有行。
    • 写接口带幂等键，客户端重试不会重复下单（e.g.: bookingId、Stripe 的 idempotency key etc.）。
    • 用户 id 从认证里取不从参数取，敏感信息不进 URL（e.g.: 支付信息在客户端 tokenize 后只传 token etc.）。
  • 服务划分：
    • 按领域：一个核心实体一个服务（e.g.: Ticketmaster 的 Event、Search、Booking etc.）。
    • 按流量：读写比例悬殊或流量量级不同的拆开单独扩（e.g.: 搜索服务独立扩读 etc.）。
    • 按状态：有状态的和无状态的分开，持连接的服务器独立成一层（e.g.: WhatsApp 的 chat server、Live Comments 的 SSE 服务器 etc.）。

总体原则

  • 真相只有一份，其余都是派生（缓存、ES 搜索副本、OLAP 聚合结果）：先写真相再写派生层，派生层丢了从真相重建。消费者能凭游标从真相补回的通道可以 best effort，否则要持久日志。
  • 锁和数据不在同一个系统里时，锁负责效率，条件写负责正确性：分布式锁（Redis、ZooKeeper/etcd）挡掉大部分冲突，让大流量不压垮数据库。存储端的条件写（数据库 WHERE 条件的乐观锁）保证最后只有一个成功。

    • 不常用：HTAP。一个数据库同时接 OLTP 写和 OLAP 查，内部行式列式双存实时同步（TiDB、SingleStore）。省掉外部 CDC 链路，代价是两头都不是最优，分析查询和线上事务抢资源。

存储布局

布局怎么放优点缺点代表产品
行式一行的所有列连续存在一起，一页放若干行

  • 改一行改一处
  • 插入删除按行操作简单

  • 连续同类型值可向量化计算

  • 事务弱

分布

分布怎么放写扩展读扩展一致性可用性跨行事务代表产品
单机一台机器全部数据无无强主挂即停完整单机 PostgreSQL、SQLite
主从复制一主写，多从异步或半同步复制，从只读无，只扩读有，读打从库主强，从可能延迟主挂需切换，几秒到几十秒完整PostgreSQL / MySQL 主从、Redis 主从
分片 + 每片主从按 key 切成多片，每片一主多从有，按分片有分片内强，跨片弱单片挂只影响那片分片内完整，跨片难MySQL 分库分表、Citus、MongoDB、DynamoDB、Redis Cluster
多主 / 无主每个节点都能写，写多副本，读多副本，靠 quorum 取交集有有最终一致，quorum 可调任一节点挂不影响读写基本没有Cassandra、DynamoDB global tables、CRDT
  • 分布不由模型决定，同一模型可配不同分布（模型只决定分片的代价：关系和图要牺牲 join 和事务，KV、宽表、文档天然按 key 分）：
    • PostgreSQL 同一个关系模型，可以单机、主从或 Citus 分片。
    • DynamoDB 和 Cassandra 同是宽表，前者每分区单 leader、Paxos 选主、三 AZ 复制，后者无主、一致性哈希环、可调 quorum（Dynamo 2007 论文对应无主这格，Cassandra 继承了它，DynamoDB 只继承了名字和分区模型）。
  • 事务范围取模型上限和分布限制中较小的那个（模型决定事务上限，分片破坏跨片事务，Spanner、TiDB 用 2PC 加共识买回来，付延迟）。

读写扩展

读扩展

手段解决什么代价什么时候上
索引单条查询从扫全表变成按索引定位写变慢，存储变大第一步，任何慢查询先看索引
去范式化省掉 join，一次读拿全冗余，写时多处更新读远多于写、join 成了瓶颈
只读副本读流量分到多台主从延迟，读到旧值单机读吞吐到顶，容忍秒级延迟
分片读写都按 key 分到多台跨片查询和事务难数据量或写量单机放不下，见分布
应用缓存热数据不碰库失效一致性，击穿穿透雪崩同一数据被反复读，容忍短暂过时
CDN静态内容在边缘返回，请求不到源站更新延迟，只适合非个性化内容对所有人一样且变化慢

写扩展

手段解决什么代价什么时候上
换引擎写密集换 LSM-tree，顺序追加读稍慢，compaction 抖动单机每秒几万写以上，见存储引擎
分片写按 key 分到多台，线性扩跨片事务没了，热 key 仍打一片单机写吞吐到顶
队列削峰突发写先进队列，后端按自己的速度消费写变异步，结果延迟可见写有尖峰且不要求同步返回，见异步处理

缓存

模式读路径写路径一致性适用
cache-aside应用先查缓存，未命中查库并回填应用写库，然后删缓存写和删之间有窗口，读到旧值默认选择，读多写少，缓存和库解耦
read-through应用只查缓存，缓存自己去库加载同 cache-aside同上想把加载逻辑收进缓存层，本地缓存库常用（e.g.: Caffeine 的 loader etc.）
write-through同上应用写缓存，缓存同步写库缓存和库同时更新，强写后立刻要读到，能接受写延迟变高
write-behind同上应用只写缓存，缓存异步批量刷库缓存先于库，缓存挂了丢数据写极多且允许丢一小批（e.g.: 计数、点赞 etc.）
  • 失效：TTL 兜底，写时主动删，本地缓存靠 Pub/Sub 广播失效。
  • 先更新库再删缓存：先删缓存再更新库，中间有人读未命中回填旧值，旧值一直留到 TTL。先更新库再删，窗口只有删之前那一瞬。要再压窗口就延迟双删，更新库后隔几百毫秒再删一次。
  • 三个经典问题：
    • 击穿：一个热 key 过期，大量请求同时回源。single-flight 只放一个请求回源，其他等它的结果。
    • 穿透：查不存在的 key，缓存永远不命中。缓存空值带短 TTL，或布隆过滤器挡在前面。
    • 雪崩：大量 key 同时过期或缓存整体宕机。TTL 加随机抖动，多级缓存，限流保护库。

流动路径

客户端 ◄──第一跳：server 到 client──── 服务器 ◄──第二跳：server 到 server──── 数据源
        轮询 / 长轮询 / SSE / WebSocket              Redis Pub/Sub 广播 / 注册表或一致性哈希直连
  • 第一跳 按客户端需求分，问"等一个结果还是等一个流"：
    • 一次性结果用轮询：秒级可接受用短轮询（e.g.: LeetCode 判题、上传进度 etc.），要更快又不想空转用长轮询。
    • 持续变化、毫秒级、大扇出用 SSE 或 WebSocket（e.g.: 评论、聊天、座位图、司机位置 etc.）【短轮询在这类方案里另有一个固定角色是保底】。
  • 第二跳 按服务器是否持连接分【长轮询、SSE、WebSocket 持连接，短轮询不持（客户端问无状态服务器、服务器查库即可）】：
    • 为什么需要：持连接的服务器有状态，事件源不知道客户端连在哪台上，需要一条 server 到 server 的投递路径（服务器自己定时查库也行，但只在小规模可行）。
    • 实现方式（三种，最后一种不可用）：
      • Redis Pub/Sub 广播：事件源发到频道，持连接的服务器各自订阅【频道零成本，订阅随客户端连接动态增减，服务器之间不需要知道彼此（最优选择，特别是大规模时是唯一选择）】。
      • 注册表或一致性哈希直连：注册中心记用户在哪台（ZooKeeper/etcd、Redis），或一致性哈希按 key 算出来，事件源查到后直连投递【优点是省一层中间件，代价是服务器要互相可达、注册表每次连接变动都要写（小规模可行，大规模开销太大不可用）】。
      • Kafka: 每用户一个 Kafka topic【topic 是重量级对象，动态订阅触发 rebalance，按用户动态订阅不可用，后端固定 topic 可用】。

第一跳：client ↔ server

协议怎么工作延迟服务器状态扇出成本断线代理 / 负载均衡适用
短轮询客户端定时发请求，服务器立即返回当前状态等于轮询间隔，秒级无状态每个客户端每个间隔一次请求，空转多无所谓，下次请求自然恢复普通 HTTP，全兼容
  • 一次性结果、秒级可接受、客户端少（e.g.: LeetCode 判题、上传进度 etc.）
  • push 方案的保底
长轮询客户端发请求，服务器挂住直到有数据或超时再返回，客户端立刻再发数据到达即返回，接近实时持连接，挂着的请求要被通知每个客户端一条挂起连接，每次返回后重建超时或断开后重发即可普通 HTTP，但代理超时要调长一次性结果但要快、不想空转、不能上长连接的环境
SSE一条 HTTP 长连接，服务器单向持续推文本事件实时持连接每个客户端一条连接，服务器推一次广播 N 条浏览器自动重连，带 Last-Event-ID 可补差走 HTTP，代理和 LB 兼容好，HTTP/2 可复用服务器到客户端单向流（e.g.: 座位图、评论、行情 etc.）
WebSocket握手后升级为双向长连接，任意一方随时发帧实时持连接同 SSE无自动重连，客户端自己重连并补差需要 LB 和代理支持协议升级，有些企业网络拦双向高频交互（e.g.: 聊天、协同编辑、游戏、司机位置上报 etc.）
  • SSE 和 WebSocket 的分界是方向：客户端只收不发用 SSE，收发都频繁用 WebSocket。客户端偶尔要发可以 SSE 收、普通 HTTP 发。
  • 长连接方案都要配心跳检测死连接，和一条短轮询兜底路径（连接断了或推送丢了，客户端定期拉一次真相）。

第二跳：server ↔ server

  • 持连接的服务器有状态：本地 map 记 userId 到连接（一人多设备就是多条），心跳 10 到 30 秒清死连接。这份状态临时、可重建，不是真相。
  • 事件源不知道客户端连在哪台上，投递要先定位再送达，三种方式：
方式谁记路由事件源怎么找到目标扩缩容单台故障每次连接变动的成本适用
Redis Pub/Sub 广播没人记，服务器各自订阅自己持有的用户频道不找，发到频道，谁订阅谁收新服务器起来订阅即可，旧的下线频道自动消失只丢它持有的连接，客户端重连到别台一次 SUBSCRIBE 或 UNSUBSCRIBE，零成本默认选择，大规模时唯一选择
注册表直连注册中心记用户到服务器的映射（ZooKeeper/etcd、Redis）查注册表，直接发给那台新服务器要在注册表登记，客户端迁移要改映射注册表里它的条目要清理，否则发给死机器每次连接建立和断开都写一次注册表服务器数量少、连接稳定
一致性哈希直连没人记，成员列表加确定性函数按 key 算出哪台，直接发成员变动时 key 重新映射，新旧两台都订阅过渡它的 key 段重新映射到邻居零，不记录同一 key 的客户端要聚到同一台（e.g.: Live Comments 同一直播的观众 etc.）
  • 注册表和一致性哈希都要服务器互相可达，Pub/Sub 不需要。一致性哈希是优化不是正确性，它把同一 key 的客户端聚到一台减少广播量，送达仍靠 Pub/Sub。
  • 投递允许丢，前提是先落库再发布，丢了这样补：
    • 连接建立时先订阅再从库里拉增量，两步之间不留缝。
    • 客户端凭序号检测漏消息，重连后从真相源拉增量（e.g.: WhatsApp 的 Inbox 表、Live Comments 的 lastSeenId、SSE 的 Last-Event-ID etc.）。
    • 多台服务器各自推送，到达顺序不保证，客户端按 NTP 时间戳排序。
Redis Pub/Sub 的内部机制
时间线                         pubsub_channels 字典内容
───────────────────────────────────────────────────────────
Redis 启动                      {}                         ← 没有任何 channel
S1: PUBLISH user:B "hi"         {}                         ← 合法，返回 0，消息丢弃
S2: SUBSCRIBE user:B            {"user:B": [conn_S2]}      ← channel 此刻"诞生"
S1: PUBLISH user:B "hi"         {"user:B": [conn_S2]}      ← 返回 1，S2 收到
S3 断线 / 最后一个退订           {}                         ← channel 消失
  • channel 只是字典 key，不需要创建，发布者和订阅者都是 Redis 客户端（PUBSUB CHANNELS / NUMSUB 能看实时内容）。
  • PUBLISH 查字典，把消息写进每个订阅连接的输出缓冲区，返回订阅者数。返回 0 可当作对方离线的信号，转走系统推送。
  • 频道粒度按用户不按会话（一个用户约 250 个会话）。同一直播的观众按 hash(videoId) % N 分频道。
  • 拓扑：单机。主从，PUBLISH 随复制流传播，订阅可连副本。Cluster 普通模式全集群广播，每次 N-1 条 bus 消息。Redis 7 sharded（SSUBSCRIBE / SPUBLISH）按 slot 路由，订阅方必须连对节点。
  • 订阅端用专用连接进入订阅模式，断线后重新 SUBSCRIBE 全部本地用户，并让客户端从库里拉一次增量。

消费者是后端程序，不是给客户端转发的服务器：

  • 异步处理，靠消息中间件卸载工作（中间件的另一用途是扇出通知，Redis Pub/Sub，主要用于实时更新，也用于跨实例的缓存失效广播），任务选 SQS、事件选 Kafka（任务是每条消息独立处理完就结束，事件是消费者的结果由所有消息共同决定、少一条就错）：
    • SQS 任务队列：一个 worker 领走处理一次、确认删除、失败重试进死信（e.g.: LeetCode 判题、Web Crawler、News Feed 写扩散、Uber 延迟通知 etc.）。
    • Kafka 事件流：消费结果依赖每一条、多消费方各读一份、可重放（e.g.: Ad Click 计数、Top-K、Post Search 索引 etc.）。
    • 定时批处理：按计划对全量数据跑一遍，结果允许晚到小时或天（e.g.: Ad Click 每日 Spark 对账 etc.）。

投递语义与丢失恢复

语义含义怎么做到代价代表
at-most-once最多送一次，可能丢，不会重发出去不等确认，不存丢了通道自己不知道，必须配兜底Redis Pub/Sub
at-least-once至少送一次，不丢，可能重存下来，消费者确认后才删或推进游标，没确认就重投消费者必须幂等SQS Standard、Kafka 默认
  • 消费者能不能自行恢复决定用哪种语义：能自行恢复用 at-most-once，不能就必须用 at-least-once（做聚合的消费者一定不能）。自行恢复要同时满足：
    • 有游标，能发现丢了（e.g.: lastSeenId、Inbox 行、offset etc.）。
    • 真相源能按游标补回，库里有完整历史或本身是 log（Cassandra 按 ad_id 分区就补不了按时间的缺失，DynamoDB Streams 是 log 可以）。
  • at-most-once 必须有兜底：先落库再发布，客户端凭游标从真相源补回丢的那条（e.g.: WhatsApp 的 Inbox 表、Live Comments 的 lastSeenId、SSE 的 Last-Event-ID etc.）。
  • at-least-once 必须有幂等：重复投递靠消费端去重，用业务键做幂等键（e.g.: bookingId 做支付幂等键、impression id 做 SET NX 去重、条件 UPDATE etc.）。
exactly-once 什么时候能用
  • 原理：严格的"恰好投递一次"不存在，发送方永远无法确认对方收没收到。能做到的是处理结果恰好生效一次，条件是读消息、处理、写结果、推进游标能绑成一个事务，所以只在输入输出都受引擎控制时成立。
  • 能用的场景（输入输出都在事务边界内）：
    • Kafka 读、Flink 算、写回 Kafka 或支持事务的库（e.g.: Ad Click 一分钟计数写 OLAP，checkpoint 把算子状态和 offset 一起快照，sink 用两阶段提交，checkpoint 完成才对下游可见 etc.）。
    • Kafka 读、处理、写回 Kafka 的流水线（Kafka Streams 一个配置开事务，输出和 offset 提交在同一事务，下游只读已提交的）。
    • 生产者重复发送去重（SQS FIFO 带 deduplication id，5 分钟窗口内重复丢弃，只管发送侧）。
  • 不能用的场景（输出是引擎管不到的外部副作用，退回 at-least-once + 幂等）：
    • 发邮件、推通知：重发就是重发，收件方不会回滚，靠消息 id 去重或接受偶尔重复。
    • 调第三方支付接口：靠对方的幂等键（e.g.: Stripe 的 idempotency key etc.）。
    • 写不支持事务的存储：靠条件写或业务键做幂等（e.g.: SET NX、UPDATE ... WHERE status = ? etc.）。

批与流

批：Spark流：Flink
输入有边界，一天的文件或一张表无边界，Kafka 持续到来
生命周期跑完退出，定时调度常驻 7×24
处理方式整个数据集分 stage，shuffle 最贵逐条流过算子，按 key 维护状态
时间数据里有时间列自己 groupBy，晚到的数据下次跑自然包含event time、watermark、窗口是一等公民
容错task 失败重跑，输入不变结果一样checkpoint 快照状态和 offset，失败从快照重放
延迟小时到天秒到分钟
结果准，输入齐了才算快，可能因晚到数据有误差
  • 选择看结果允许晚多久：T+1 报表用批，分钟级仪表盘用流，又要快又要准就两者都用。
  • 批流都用的两种架构：
    • Lambda：流算实时结果可能有误差，批定期全量重算覆盖，服务层合并两边。两套代码要保持语义一致（e.g.: Ad Click 的 Flink 一分钟窗口 + 每日 Spark 对账 etc.）。
    • Kappa：只有一套流代码，正确性靠引擎的 exactly-once 和 event time，要重算时从 offset 0 重放到新表再切换。前提是 Kafka 保留够久、流引擎够成熟。
  • 流处理比批处理需要多考虑的问题：
    • 时间：批的输入是完整的，一天的文件到齐了才跑，不存在数据晚到。流的输入没有边界，什么时候能认为一分钟的数据到齐了要自己定规则，而且要用事件发生时间不用处理时间，否则乱序和重放都会算错
      • watermark：时间戳小于等于 W 的事件我认为都到了，常取最大事件时间减容忍度。
      • 窗口：watermark 越过窗口边界就关窗刷结果（e.g.: Ad Click 一分钟窗口，watermark 30 秒 etc.）。
      • 更迟的：allowedLateness 内更新结果，超过的靠对账。
    • 状态：批把整个数据集读进来算一遍，中间结果是临时的。流逐条处理，一分钟的计数要一直攒在内存里等窗口关闭，这份攒着的东西就是状态，要管它多大、放哪
      • 一分钟窗口状态小，丢了从 Kafka 重放即可，checkpoint 可以不开。
      • 一个月滑动窗口状态大，必须开 checkpoint，Kafka 也要留一个月（e.g.: Top-K etc.）。
    • 容错：批失败了从头重跑，输入不变结果一样。流常驻运行，失败不能从头来，靠 checkpoint 定期把所有算子的状态和 Kafka offset 一起快照，失败从上一个快照恢复、从对应 offset 重放，结果和没失败一样。

        └─ Flink 算完再写 ──┬─ OLAP，给人分析

  • 要不要 Flink：只按时间桶计数、量在 OLAP 写入能力内，Kafka 直接灌 OLAP 靠物化视图在写入时预聚合就够（源表每插一批，按维度和时间粒度自动累加到一张聚合表）。以下任一成立才上 Flink：
    • 要窗口语义，滑动窗口、会话切分、晚到数据处理。
    • 要多流 join 或补维表字段。
    • 要 exactly-once 和去重。
    • 原始事件量大到 OLAP 直接接写不进或存不起，先聚合再落。
  • 结果写到哪：
    • 写 OLAP 给人分析：按查询过滤维度分片（e.g.: advertiser_id etc.），多粒度预聚合（分钟到天到周），仪表盘直接查预聚合表。
    • 写 KV 给线上服务：特征或计数写 Redis 这类加速层，在线请求毫秒级点查（e.g.: 推荐系统的用户最近 N 次点击、滑动窗口行为计数 etc.）。
    • 同一个 Flink 作业可以分叉两路各写一份，前者是实时分析负载，后者是加速型负载。
案例
  • Uber 叫车匹配：叫车请求量大且突发，匹配要按区域串行，匹配失败要重来，所以请求先进队列再由匹配 worker 消费
    • Kafka（首选）：按区域分区，区域内有序，匹配成功后才 commit offset，worker 挂了从上次 offset 重来。
    • SQS：FIFO 用 message group 当区域可保有序，但吞吐低。Standard 无序，同一区域并发匹配会冲突。
  • News Feed 写扩散：用户发帖要写进每个粉丝的 feed，粉丝多时写放大，不能在请求路径上做，扇出交给后台（粉丝极多的大 V 改为 fan-out on read，读时合并）
    • SQS（首选）：一条帖子扇出是一个独立任务，worker 做完即止，失败重试进死信，不需要重放和多消费方。
    • Kafka：也能，但保留、重放、消费组都用不上，topic 和 rebalance 白付。
  • Web Crawler 抓取：亿级 URL 分给成百上千 worker 抓，慢站点和失败站点要退避重试，抓取和解析节奏不同

    • 方案：
      • Kafka + Flink + OLAP（首选）：Click Processor 验签去重后写 Kafka，Flink 一分钟 event-time 窗口聚合写 OLAP，Kafka 保留 7 天就是原始事件存储，每日 Spark 从 S3 归档重算对账（Lambda）。

断点续传每块算指纹，元数据记每块状态和 ETag，重连后查元数据跳过已传的移动网络不稳定整文件指纹可做秒传去重

  • 上传完成后的处理是一个 DAG，由工作流引擎编排（e.g.: Temporal etc.）：视频切成 3 到 5 秒的段，每段并行转多种码率，生成 HLS 或 DASH 的 manifest，标记可播放。播放端按带宽在 manifest 里选码率。
案例
  • Dropbox 文件同步：50 GB 大文件、多设备同步、优先可用

  • YouTube 视频：每天 100 万上传、1 亿播放
    • 上传按上面的路径，S3 完成事件触发转码 DAG。
    • 元数据 Cassandra 按 videoId 分区，段和 manifest 放 S3，CDN 分发。
    • 自适应码率：客户端拿 manifest，按网络状况逐段选格式。

长任务与多步流程

长任务

客户端 ──请求──► API 服务器 ──写 job(status=queued)──► 任务表
                     │ 返回 jobId                 ▲
                     └──入队──► 队列 ──► worker ──更新 status / progress / result
客户端 ──轮询 GET /jobs/{id} 或 SSE 推──► 任务表
  • 形状：请求先落一条任务记录并立刻返回 jobId，活交给队列和 worker，客户端拿 jobId 查进度（e.g.: LeetCode 判题、YouTube 转码、Web Crawler 抓取 etc.）。
  • 任务表是真相：jobId、status、progress、result、尝试次数。队列只是传输，丢了按表重投。
  • worker 挂了：队列（SQS）的可见性超时让任务回队被别人领走，所以每个任务要幂等，用 jobId 做幂等键。
  • 进度：worker 定期写 progress，客户端轮询或 SSE 推，见实时更新。

多步流程

一个业务要跨多个服务、跨几分钟到几天，中间任何一步可能失败、超时、要等外部回调（e.g.: 下单扣款、锁库存、生成运单、发确认邮件 etc.）。

方式怎么做中途崩了适用
单服务器串行一个进程按顺序调各服务状态在内存，丢了不知道走到哪步骤少、全在一个事务里能回滚
Saga每步一个本地事务，失败则按反序执行补偿（退款、释放库存）要自己持久化走到第几步跨服务但步骤固定
事件驱动每步完成发事件，下一步的服务订阅事件自己触发事件在队列里不丢，但流程散在各服务，没人知道全貌步骤松耦合、各服务独立演进
工作流引擎流程写成一段代码，引擎持久化每步结果，崩了从断点续跑（Temporal、Step Functions）引擎重放历史恢复到崩溃前的状态步骤多、要等外部事件、要超时推进、要看全貌
  • 每步幂等：引擎重放时已完成的步不会再执行，但一步执行到一半崩了会重跑，步内的外部调用要带幂等键（e.g.: 支付用 bookingId、发邮件用消息 id etc.）。
  • 超时是流程的一部分：等不到外部回应要主动推进，不能永远挂着（e.g.: Uber 司机 10 秒不接单换下一个、Ticketmaster 预留 10 分钟过期 etc.）。
  • 等外部事件：流程挂起等 webhook 或人工操作，事件到了按 id 找回对应的流程实例继续（e.g.: 支付 webhook etc.）。
  • 流程版本：流程代码改了，跑到一半的老实例按老版本跑完，新实例用新版本。
案例
  • Uber 叫车匹配：找司机、通知、等 10 秒、没接就换下一个，直到成功或超时失败。每轮一步，司机锁加接单条件写保证只派一个，超时推进用 SQS delay queue 或 Temporal 定时器。
  • YouTube 转码：切段、每段并行多码率转码、生成 manifest、标记可播放，是一个 DAG，Temporal 编排，段级任务独立重试。
  • 电商下单：扣款、锁库存、生成运单、发邮件，Saga 补偿是退款和释放库存，或者 Temporal 一段代码写完。

并发控制

悲观锁和乐观锁

进程内的锁（mutex、synchronized）只管一个实例，服务多实例部署后共享状态都在数据库或 Redis 里，所以分布式并发控制不讨论单机锁。

悲观锁乐观锁
思路先锁住再改，别人等先改再验，冲突了重试
实现SELECT ... FOR UPDATE，或直接 UPDATE 隐式加锁UPDATE ... WHERE version = ?，或直接用业务字段 WHERE stock > 0，看 affected rows
冲突检测时机事前阻塞事后校验
持锁时长整个事务只有那条 UPDATE 的几毫秒，底层仍是行锁
适合冲突多、事务短、必须成功（e.g.: 余额扣减、状态机流转 etc.）冲突少、读多写少、跨请求（e.g.: 后台编辑表单、配置修改 etc.）
注意
  • 命中索引，否则锁全表
  • 不持锁做 RPC
  • 固定加锁顺序防死锁
  • 重试上限
  • 版本号用自增整数防 ABA
  • 多行校验退回悲观
  • 本质区别不是有没有锁，是持锁时长和冲突检测时机。乐观锁的那条 UPDATE 底层照样拿行锁，只是几毫秒就放。
  • 条件写就是把业务字段当版本号的 CAS：UPDATE ... WHERE status = 'requested' 拿到行锁后用最新值匹配 WHERE，第二个事务 affected_rows 一定为 0。能用一条原子语句就不显式加锁（e.g.: Redis INCR、SET NX、Lua、DynamoDB 条件表达式 etc.）。
  • 高冲突下乐观锁反而更差，999 个失败重试白烧 DB。热点行两种锁都不行，把冲突挪出 DB（分桶、拆行、攒批，见读写扩展）。

数据库中的锁

InnoDB 读不加锁靠多版本，写加行锁持到提交，应用层的乐观锁是一条带条件的 UPDATE 在语句内原子完成。

  • 读：MVCC，快照读不加锁
    • 每行隐藏列 DB_TRX_ID、DB_ROLL_PTR，旧版本进 undo log 串成链。
    • Read View 记当前活跃事务集合，沿链找第一个可见版本。RC 每条 SELECT 新建 Read View，RR 整个事务复用第一个。
    • 长事务卡住 purge，undo 膨胀，是线上最常见的危害。
  • 写：2PL 行锁，当前读
    • UPDATE、DELETE、SELECT ... FOR UPDATE 是当前读，加 X 锁。锁的是索引记录不是物理行，WHERE 不走索引等于锁全表。
    • 两阶段：扩张阶段只加不放，收缩阶段只放不加。InnoDB 用 Rigorous 2PL，所有锁持到提交，把加锁操作放事务最后能缩短持锁。
    • 为什么锁要跨操作持有：单条操作各自加放，会读到转账中间态、丢失更新。
    • 隔离级别决定锁范围：
      • RC 只有 Record Lock，死锁少但有幻读，很多公司线上默认 RC。
      • RR 用 Next-Key Lock 防幻读，锁范围大。
    • 死锁靠 wait-for graph 找环，回滚代价小的事务。锁等待默认 50 秒（排查用 performance_schema.data_locks、SHOW ENGINE INNODB STATUS）。
  • 条件 UPDATE 的原子性：CAS
    • 语句内拿 X 锁、用最新值匹配 WHERE、改、放，比较和写入在一条语句里完成。
    • 对应 CPU 的 LOCK cmpxchg、Java 的 Atomic*。坑：ABA 靠版本号防，高竞争自旋空转靠分段累加（e.g.: LongAdder、库存分桶 etc.）。
类型锁什么目的
Record Lock单条索引记录防止别人改这行
Gap Lock两条记录之间的开区间防止往区间插入，解决幻读
Next-Key LockRecord + 前面的 Gap，左开右闭RR 下的默认加锁单位
Insert Intention Lock插入前在 gap 上打的意向标记多个事务往同一 gap 不同位置插入不互斥

分布式锁

单库的行锁出不了这个库，锁要跨服务、跨请求持有，或者持有时间长到不能挂在数据库事务上，就需要一把所有参与方都看得见的锁，有三个要求：互斥，不死锁（要能过期），不误删（释放时比对持有者）。（过期和互斥天然矛盾，持有者没做完锁先过期，别人就进来了，整个设计都在这两条之间找平衡。）

实现互斥靠什么过期防误删故障时适用
DB 唯一索引插入唯一键，第二个插入失败没有，要自己清删除时带持有者条件和业务库同生死低频任务、已有 DB 不想加组件
Redis SET NX EX单线程，key 不存在才设置TTL 自动过期，Redisson watchdog 可续期value 存 token，Lua 比对再 DEL主从异步复制，主挂了锁可能丢。Redlock 靠多数派但依赖时钟效率型场景，默认选择（e.g.: Ticketmaster 选座、Uber 司机匹配 etc.）
ZooKeeper 临时顺序节点序号最小者持锁会话断了节点自动消失节点归会话所有多数派共识，不丢正确性要求高、锁数量少，只 watch 前一个防惊群
etcd leasekey 带 lease，revision 最小者持锁lease 到期自动删同上Raft 共识，不丢同 ZooKeeper，云原生环境
  • 锁负责效率，条件写负责正确性：锁和数据不在同一个系统里时（分布式锁），锁判定的互斥传不到写数据那一刻，中间任何环节都可能让两个人同时进来（过期、GC 停顿、主从切换丢锁、脑裂、锁服务宕机降级、客户端绕过），所以数据写入必须自带条件校验只让一个成功（乐观锁），锁只是把大部分冲突提前挡掉省掉无效工作（单库行锁和写在同一事务里原子，不需要这层）
    • 常用形式是用业务状态做条件（e.g.: Redis 锁加 UPDATE ... WHERE status = ?、Ticketmaster 的 bookingId 幂等键 etc.）。
    • fencing token 是把条件换成单调递增的数字，锁服务发号，存储拒绝比见过的更小的，等于把分布式锁降级成乐观锁。
  • 锁和分布式事务是两件事：锁管谁能进这段代码，2PC 管多库要么全成要么全败，2PC 是 2PL 的分布式延伸。能用单库事务就不用分布式锁（e.g.: Gopuff 跨库锁换成单库 SERIALIZABLE etc.）。
ZooKeeper/etcd 是什么
  • 小容量、强一致、支持 watch 的 KV，存集群元数据，所有用法从这三个特性推出来。
  • 用法：服务注册发现（临时节点）、leader 选举（临时顺序节点）、分布式锁、配置与开关、分片归属、成员列表（一致性哈希环的输入）。
  • 红线：不在数据路径上（存有哪些服务器，不存用户在哪台，后者由哈希函数算或由 Pub/Sub 订阅隐式维护）。

排队

流量过大数据库无法扛住时（e.g.: 商品秒杀、演唱会抢票、12306 放票 etc.），除了用锁还可以排队：按容量放行，放行的人拿一张带 TTL 的许可再去操作。

按量级选方案
  • 请求量数据库接得住：什么都不加，数据库 UPDATE ... WHERE 条件写。
  • 超过数据库极限（分库分表能解决总量问题，解决不了热点问题）：锁和排队二选一，都挡在数据库前面。
锁和排队
  • 相同点：都挡在数据库前面扛流量，正确性都靠数据库的条件写。
  • 不同点：
    • 锁是竞速，SET NX 先到先赢，网络近的、脚本快的占便宜，用户立刻知道结果。
    • 排队是排序，按放行顺序，可以先到先得也可以候场随机，用户先等、知道排第几。
入队  ZADD queue:{id} NX <时间戳> <userId>
排位  每几秒 ZRANK 算前面多少人，除以放行速率估等待时间，SSE 推给客户端
放行  调度进程每秒 ZPOPMIN queue:{id} N，对每人 SET admitted:{id}:{userId} EX 600，SSE 通知进入
门禁  业务接口先 EXISTS admitted:{id}:{userId}，没有就拒绝回排队页（防绕过前端直接调接口，许可只认服务端写的 key，不认客户端参数）
离场  许可 TTL 到了没操作就失效，重新排
命令做什么排队里的含义
ZADD key NX score member加成员，已存在不动入队，刷新不重排
ZRANK key member成员按 score 升序的排名，O(log N)前面排了多少人
ZPOPMIN key N弹出 score 最小的 N 个并删除放行队头 N 人
ZREM key member删成员用户放弃排队
  • 人排队用 sorted set，任务排队用 MQ：判据是排队之后的动作系统能不能替用户做。
    • 不能替用户做就人排队（e.g.: Ticketmaster 放行后用户自己挑座 etc.），要查每个人的位置、能中途退出、刷新不重复、候场随机、放行后用户继续操作（List 查位置 O(N)，MQ 不支持删除或修改已入队的消息，都不行）。
    • 能替用户做就任务排队，处理完给结果，没有复杂的中间过程（e.g.: 12306 提交订单后系统分座出票、秒杀点抢购后系统扣一件建订单，队列里是订单，页面显示排位或抢购中 etc.）。
  • 放行量和预计时间：
    • 放行量按数据库容量定，和库存多少无关（上限是数据库能承担的最大流量，可以小于也可以大于库存，条件写兜底不会超卖）。
    • 后面的人等两种空位：数据库一次接不完就分批，等下一批；库存已全部放出去，等预留过期和放弃的回流。
    • 预计时间按最近几分钟的实际放行速率估，排位除以速率，定期重算（排位是准的，时间是估的）。
  • 排队层自身扛不住时：排队 key 按活动分片到不同节点，单活动再按 userId 哈希分多个队列、排位用各分片排名加总估算，网关层限流让超出入队能力的请求退避重试。
案例
  • Ticketmaster 选座：锁的对象是一张票，用户填支付要持有 10 分钟
    • 方案：
      • Redis SET NX EX 600（首选）：预留不碰数据库，TTL 到期自动释放。
      • 隐式状态条件更新 WHERE status='available' OR (status='reserved' AND expired)：纯 DB 的最优解，不引入新组件。
      • status + expiration + cron 回收：有回收延迟，cron 是单点。
      • 长事务 FOR UPDATE：连接占几分钟，不可用。
    • 兜底：支付 webhook 事务里 WHERE status='available'，bookingId 做幂等键。TTL 过期与支付完成竞争时 DB 只让一个成功，另一个退款。
  • Uber 司机匹配：锁的对象是一个司机，10 秒
    • 方案：
      • Redis SET lock:driver:{id} {requestId} EX 10 NX（首选）。
      • DB status outstanding_request + cron：有回收延迟。
      • 内存锁：多实例不互斥，不可用。
    • 兜底：接单 UPDATE ride SET status='accepted' WHERE id=? AND status='requested'。超时推进用 SQS delay queue 或 Temporal。
  • Web Crawler 域名礼貌间隔：锁的对象是域名
    • Redis SET NX，TTL 等于爬取间隔（首选）。
    • SQS visibility timeout 当租约。
  • Gopuff 下单扣库存：反例，跨库分布式锁崩在中间、重叠库存死锁，换成单库 SERIALIZABLE 事务。能用单库事务就不用分布式锁。
  • Shopify 抢购库存：一件商品拆 1000 行，SELECT ... FOR UPDATE SKIP LOCKED 随便锁几行，降到 RC 避 Gap 锁，补货单独一把锁，所有路径固定加锁顺序防死锁（完整的秒杀方案见 Flash Sale）。
  • 无锁：Rate Limiter、Tinder、Bitly、WhatsApp 用一条原子命令代替锁，Lua 把 read-modify-write 做成一步、Redis INCR 单线程、DynamoDB 条件表达式。

JWT 怎么设计

  • 结构与签名：header.payload.signature，payload 明文只防篡改不防偷看，验证不查库。
  • 过期与刷新：
    • access token 短期，15 分钟。
    • refresh token 随机串、服务端存哈希、30 天，只在换 access 时用一次，放 HttpOnly cookie。
  • 登出与撤销：删 refresh 断续期，要立刻生效就把 jti 放进 Redis 黑名单。
  • 密钥与防攻击：
    • RS256 私签公验，kid + JWKS 轮换，公钥泄露无害。
    • 算法白名单防 alg:none 和算法混淆。
    • HTTPS、SameSite。
    • refresh rotation 加重放检测，同一 refresh 第二次使用即吊销整条链。

请求签名

  • 签名回答"是不是我发的"。签验同方、高频、签名要进 URL 用 HMAC，跨组织验签用非对称。
  • 签名、去重、反作弊是三个问题，分别回答"是不是我发的""是不是第一次""点的人是不是真的"。
