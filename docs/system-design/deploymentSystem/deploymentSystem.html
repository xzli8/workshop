Deployment System（发布 + 健康检查 + 自愈）

题外话：通用法则（从这道题提炼）
控制模型
  • 用户只写期望状态；Controller 不断比较期望状态和实际状态，有差异就处理（按差异驱动，不按事件驱动）。漏事件、重复执行、Controller 重启都天然容错。
  • 期望状态强一致，作为唯一数据源；实际状态的上报可以最终一致。
变更安全
  • 先小范围再扩大（实例 → 可用区 → 区域），每一波观察一段时间再继续。
  • 门禁看业务指标，并和同期的旧版本对比；回滚就是一次反方向的发布。
  • 新旧版本会同时在线，接口和数据要兼容 N 和 N-1。
故障判断
  • 就绪探针只查自身，不查共享依赖，否则依赖一抖动，所有实例都会被摘掉。
  • 大面积同时失联更可能是网络或控制面的问题，这时要降速甚至停止驱逐。
  • 数据面不依赖控制面（静态稳定性）：控制面挂了，已运行的实例照常服务。
1

功能需求

核心

  • 发布：指定服务和版本（镜像 + 配置），按策略分批发布到所有实例，可以查看进度。
  • 健康检查与自愈：实例不健康时自动重启或替换；节点故障时把实例迁到其他节点。
  • 回滚：指标恶化时自动暂停并回滚；也支持手动暂停、继续、回滚。

范围外

  • CI 构建、配置中心、数据库 schema 变更（时间够的话可以聊）。
2

非功能需求与估算

核心

  • 安全：发布过程中可用容量 ≥ 75%；坏版本的影响范围可控。
  • 控制面和数据面解耦：控制面挂了，已运行的实例照常服务。
  • 收敛快：实例故障 30s 内发现，2 分钟内替换完成。
  • 规模：1 万个节点、10 万个实例、1000 个服务，同时有上百个发布在进行。
  • 一致性：期望状态强一致，实际状态最终一致。

估算

  • 心跳：1 万节点 × 每 10s 一次 ≈ 1k QPS。不能每次都上报全量状态，要把轻量心跳和状态上报分开。
  • 镜像分发：1GB × 1000 个节点 ≈ 1TB，全从中心仓库拉会打爆带宽 → 区域缓存 / P2P，发布前预拉。
  • 核心难点：安全地变更（分批、门禁、回滚）+ 准确地判断故障（不误杀、不漏判）+ 控制面自身可靠。
3

核心实体与 API

  • Service：一个服务，包含副本数和发布策略。
  • Release / Version：镜像 + 配置，不可变。
  • Rollout：一次发布，记录 from → to 版本、策略、当前批次、状态（RUNNING / PAUSED / SUCCEEDED / ROLLING_BACK / FAILED）。
  • Node：一台机器，上面运行 Node Agent。
  • Instance：一个运行中的实例，记录所在节点、版本、健康状态。
  • 期望状态（Service、Rollout）和实际状态（Instance、Node 上报的状态）分开存储。
POST /services/{service_id}/rollouts
  body: { version,
          strategy: { type: ROLLING | CANARY | BLUE_GREEN, maxSurge, maxUnavailable, minReadySeconds, waves },
          autoRollback: { maxErrorRate, maxP99Ms } }
  → { rollout_id }

GET  /rollouts/{rollout_id}                   → 当前批次、新旧版本实例数、健康数
POST /rollouts/{rollout_id}/pause | resume | rollback

（内部）Node Agent
  WATCH /nodes/{node_id}/assignments          → 本节点应该运行哪些实例、什么版本
  PUT   /nodes/{node_id}/lease                → 轻量心跳，每 10s 一次
  PUT   /nodes/{node_id}/status               → 实例状态有变化时上报

高层设计

Client ──► API Server ──► 状态存储（etcd：Service / Rollout / Instance / Node lease）
                               ▲ watch + 写回
              Controllers（租约选主）：Rollout Controller / Scheduler / Node Controller
                               │ watch 本节点的分配
Node × 1万：Node Agent ──► 拉镜像（区域缓存 / P2P）──► 启动 ──► 探针 ──► 上报
Instance ──► Metrics 系统 ──► Rollout Controller 的健康门禁
负载均衡只把流量转给就绪的实例
Global Rollout Orchestrator：按波次在各个 cell 发起 Rollout

① 发布：Rollout Controller 按批推进

  • Client → API Server → 状态存储（强一致，支持 watch）。
  • Rollout Controller watch 到新的 Rollout，每次选一批实例改成新版本；这一批健康并稳定后再推进下一批，进度写回 Rollout。

② 实例落地：Scheduler + Node Agent

  • Scheduler 按节点资源和反亲和规则（同一服务的实例分散到不同节点和可用区）选择节点。
  • Node Agent watch 本节点的分配，从区域镜像缓存拉镜像并启动，在本地缓存期望状态。

③ 健康检查：Agent 在本地执行三种探针

探针失败时应对的问题
启动探针超过阈值才重启；成功之前暂停另外两种探针慢启动的服务被误杀
存活探针重启容器进程卡死、死锁
就绪探针从负载均衡摘掉，不重启暂时没准备好、过载

连续 N 次成功或失败才改变状态，避免抖动。

④ 自愈：实例级 + 节点级

  • 实例级：Agent 重启失败的容器，指数退避（10s 起，每次翻倍，最长 5 分钟），避免重启风暴。
  • 节点级：心跳超时 → 标记 NotReady → 宽限期后驱逐上面的实例 → 副本数不足，在其他节点重建。
5

深入

安全发布

  • 分批滚动：maxSurge 是最多比期望副本数多出几个，maxUnavailable 是最多几个不可用。100 个副本、maxSurge=25、maxUnavailable=0 → 每次先起 25 个新版本，健康后再下掉 25 个旧版本，容量从不下降。
  • minReadySeconds：新实例要持续健康一段时间才算可用，挡住"启动时健康、几十秒后崩溃"的版本。
  • 分波次：1 个实例（canary）→ 1 个可用区 → 1 个区域 → 全部；每一波观察一段时间（bake time）再继续；不同时发布互为灾备的两个区域。Azure 的 Safe Deployment Practices 也是这个思路。
  • 健康门禁：不只看探针，还要看错误率和 P99；新版本实例和同期的旧版本实例对比，排除流量波动的影响。
  • 自动回滚：门禁不通过 → 暂停 → 回滚。回滚就是一次反方向的发布，保留旧版本的镜像和记录，可以快速切回。K8s 的 progressDeadlineSeconds 超时只会标记失败、不会回滚，所以回滚逻辑放在我们自己的 Rollout Controller 里。
策略做法回滚速度代价
滚动分批替换慢，要再滚动一次资源开销最小
金丝雀先放一小部分流量，指标没问题再扩大快，撤回金丝雀即可需要流量切分和指标对比
蓝绿整套新环境起好后切换流量最快，切回旧环境发布期间资源翻倍

健康检查要准确

  • 就绪探针不查共享依赖：数据库一抖动，所有实例都会变成未就绪，整个服务被全部摘掉。依赖故障用降级和熔断处理。
  • 本地检查 + 外部检查：Agent 本地探针发现得快，但看不到网络问题；负载均衡的外部探测能发现网络和路由问题。
  • 区分节点故障和网络分区：心跳丢失不代表实例挂了。大量节点同时失联（比如一个可用区超过一半）时，更可能是网络或控制面出了问题 → 降低驱逐速度甚至停止驱逐，避免在别处大量重建、压垮剩下的集群（K8s 的 Node Controller 也这么做）。

控制面自身的可靠性

  • Controller 多副本 + 租约选主：主挂了，新主重新读状态存储继续推进；Rollout 每完成一批就持久化进度，能从断点继续。
  • 静态稳定性：控制面不可用时，Agent 按本地缓存的期望状态继续运行和重启实例；只是暂时不能发布、不能跨节点迁移。
  • 防止同一实例运行两份：节点失联后在别处重建，原节点恢复后会多出一份。无状态服务可以接受；有状态服务要等旧实例确认删除后再重建（StatefulSet 的做法），或者用 fencing。

扩展到 1 万节点

  • 按 cell 拆分：每个集群或区域一套独立的控制面和状态存储，限制单个 etcd 的规模和故障范围；全局编排器只负责按波次在各个 cell 发起发布。
  • 心跳和状态分开：心跳只更新一个很小的 lease 对象，实例状态只在变化时上报。
  • 镜像分发：区域缓存 + P2P（Dragonfly、Kraken）；下一批开始前预拉镜像，把拉镜像从关键路径上移走。

新旧版本兼容（可选）

  • 滚动期间新旧版本同时在线，接口和消息格式要兼容 N 和 N-1。
  • 数据库变更拆成"扩展 → 迁移 → 收缩"三次发布，每一步都可以回滚。

面试讲述顺序

  1. 需求与估算：难点是安全变更 + 准确判断故障 + 控制面可靠。
  2. 主线：期望状态 + 调和循环 → 分批发布 → 三种探针 → 实例级和节点级自愈。
  3. 深入：分波次和自动回滚 → 健康检查的误判 → 控制面故障和静态稳定性 → 按 cell 扩展。
