1

功能需求

核心

  • 按出发站、到达站、日期查车次和余票。
  • 选车次、席别、乘车人下单，系统分配座位出票。
  • 出票后在时限内支付，超时释放。
  • 无票时登记候补，有退票自动兑现。

范围外

  • 实名核验、改签退票规则细节。
  • 选座选铺、静音车厢这类附加选项。
  • 线下窗口和代售点渠道。
2

非功能需求

核心

  • 一个座位的一个区间只卖一次：出票强一致。
  • 规模：春运单日售票 2000 万张，页面浏览近 900 亿次，出票峰值每秒 1000 多张。
  • 余票查询低延迟：几十毫秒，允许几秒过时。
  • 下单允许等：提交后排队，异步给结果。

落到答题框架的三个点

  • CAP：出票要 C，余票展示要 A，余票是派生值，查到有票下单失败是正常现象。
  • 延迟：查询几十毫秒，下单不要求同步返回，排队页显示排位和预计时间。
  • 规模：查询和出票差五个量级，900 亿次浏览对 2000 万张票，所以查询和交易必须分开部署，查询走内存和公有云，交易走排队。
3

核心实体

  • Train：车次、日期、停站序列。N 站就是 N−1 个区间。
  • Seat：车次、日期、车厢座位号、席别、occupied 位图。库存，真相。
  • Order：乘车人、区间、席别、状态 queued / ticketed / paid / failed / expired、分到的座位。
  • RemainingTickets：每车次每日每席别一张区间对矩阵 count[i][j]。派生值，只服务展示。
4

API

  • GET /trains?from&to&date → 车次列表，每车次各席别余票。
  • POST /orders，body 带 trainId、date、from、to、席别、乘车人 → orderId，状态 queued。
  • GET /orders/{orderId} → 状态，排队中时带排位和预计时间，出票后带座位。
  • POST /orders/{orderId}/pay → 支付结果。orderId 做幂等键。

高层设计

查余票  客户端 ──► 余票服务 ──► 内存里的余票矩阵（和交易隔离，可放公有云）

下单    客户端 ──► 订单服务 ──写 Order queued──► 订单库
                      └──► MQ（按车次分区）──► 出票 worker ──条件写──► 座位库（位图）
                                                   └──更新 Order ticketed / failed，更新余票矩阵
        客户端 ──轮询 GET /orders/{id}──► 订单库

支付    客户端 ──► 支付 ──webhook──► 条件写 Order paid
过期    定时任务把超时未付的 Order 置 expired，清座位位图，余票矩阵加回
  • 查余票：读内存矩阵，不碰座位库。
  • 下单：用户提交时车次席别乘车人都选好了，分座机器能做，所以订单当任务进 MQ，worker 出票，客户端轮询结果。
  • 支付和过期：和秒杀一样，条件写转正，超时释放。
6

深入

区间库存：座位乘区间

  • 库存单位不是座位，是座位乘区间。一列车停 10 站是 9 个区间，一个座位卖了北京到南京占前 7 段，南京到上海的 2 段还能卖给别人。
  • 每个座位一个位图，区间 k 对应 bit k。买 [i, j) 的掩码是 ((1 << (j−i)) − 1) << i，10 站的位图 2 个字节。
  • 出票是一条条件写：UPDATE seat SET occupied = occupied | :mask WHERE train=? AND date=? AND seat_no=? AND (occupied & :mask) = 0，影响行数为 0 换下一个座位。多个乘车人逐座出，一个出不来整单失败。
  • 和秒杀的拆行同一个形状，"可用"的判断从一个状态位变成一段位的 AND。

余票查询：派生矩阵

  • 问的是 [i, j) 还有几个座位满足 occupied & mask == 0。内存里现扫一千多个座位微秒级能算，但查询 QPS 几万时 CPU 不低。
  • 预算：每车次每日每席别维护 count[i][j]，10 站 45 个数，查询读一个数。
  • 增量维护：座位 s 卖出 [a, b) 位图从 old 变 new，对每个区间对，old & mask == 0 且 new & mask != 0 的 count 减一。每次出票最多算 45 个掩码。退票反过来加一。
  • 余票是派生值不是真相，允许晚几秒，和交易分开部署，春运时 75% 的查询流量放在公有云。查到有票下单失败是正常现象，提示余票不足再查。

排队出票：任务排队

  • 为什么排订单不排人：用户提交时已经选好一切，分座是确定性的，机器替用户做完给结果，中间没有人要操作的步骤。和 Ticketmaster 放行后用户自己挑座不同，判据见知识图谱的排队。
  • MQ 按车次分区，一个车次一个 worker 串行消费，同一时刻只有一个事务改这趟车的座位，条件写不会撞。消费速率按后端响应时间自适应，后端慢了就放慢。
  • 排位用序号差：入队发单调递增序号，worker 更新已处理序号，差值就是排位，除以最近几分钟的处理速率就是预计时间。按车次单分区的 Kafka 直接用 offset 差。
  • 出不了票的订单标 failed，引导候补。排队结果靠客户端轮询订单状态，不用长连接。

候补

  • 无票时登记需求并预付票款，记车次、席别、区间、乘车人。
  • 退票和改签释放座位时发事件，候补服务按登记顺序撮合，出票成功通知用户，失败退款。
  • 候补在排队里有优先级，排在普通下单前面，所以放票瞬间经常是开票即候补。

扛流量

  • 查询和交易隔离：余票服务独立集群，内存计算，公有云扩容，交易库看不到查询流量。
  • 订单库按用户哈希分库分表，100 库 100 表。座位库按车次加日期分片，一趟车一天的座位在一片里，出票事务不跨片。
  • 排队就是限流，MQ 消费速率是数据库能承受的速率，再多的提交都在队列里等。
