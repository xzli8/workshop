Top-K YouTube Views

题外话：通用法则（从这道题提炼）
需求
  • 先问 scale 来找出难点；精确与否、窗口语义这类产品问题单独澄清，不要用"所以"串起来。
  • 新鲜度 SLA 就是批处理的时间预算（1 分钟可见 → 分钟级聚合）。
写
  • 写多时先聚合再落库；聚合之后的负载由 key 的基数决定，和原始流量无关。
  • 满足交换律和结合律的操作（加法、max、CMS）可以拆开算、在任意位置合并，这是加盐和分片的前提。
  • 按 key 分区保持局部性，只对热 key 加盐。
读
  • 结果对所有人相同时，预计算 + 缓存，读路径不做计算；定时预计算优于 cache-aside（避免过期击穿）。
  • 小、热、能接受短暂过期的数据放进程内缓存，定期刷新。
  • 发布结果时写带版本号的 key 再切换指针；故障时返回旧值。
数据结构
  • 频繁变化的列不要建索引。
  • 只关心头部就维护 top K；只增不减可以用堆，有减法要维护全量顺序或候选缓冲。
  • 可分解的聚合可以分片算再合并；高基数 + 只关心 heavy hitter，用概率数据结构换内存。
正确性
  • 日志是事实来源，状态和 offset 一起快照，通过重放恢复。
  • 非幂等的写入要配去重，或改成覆盖写；加减必须对称（减掉的正是当初加上的）。
1

功能需求

核心

  • 查询 1h / 1d / 1month / all-time 的 top K 视频（K ≤ 1000）。
  • 时间窗口一律从当前时刻往回看。

范围外

  • 任意历史区间（比如 10 月份时查去年 6 月的 top K）。
  • 任意起止时间。

窗口语义：tumbling（和面试官澄清后确定）

  • tumbling：10:06 查 last hour，得到的是 9:00–10:00。
  • sliding：10:06 查 last hour，得到的是 9:06–10:06。放到深入部分讨论。
  • 窗口语义和"1 分钟可见"是两回事：选 tumbling 的理由是它更简单，而且面试官接受；不是由新鲜度要求推出来的。
  • tumbling 下的新鲜度：hour / day / month 的结果分别只在整点、0 点、月初变化一次，1 分钟可见实际上只约束 all-time 窗口。
2

非功能需求与估算

核心

  • 新鲜度：一次 view 在 1 分钟内被计入。
  • 精确：先给出精确方案，近似放到深入部分。
  • 延迟：读取在几十 ms 内（需要预计算 + 缓存）。

估算

  • 写入：70B views/天 ÷ 100k 秒 ≈ 700k TPS。
  • 视频数：每秒上传 1 小时内容 ÷ 6 分钟/个 × 100k 秒 ≈ 每天 1M 个，10 年约 3.6B。
  • 全量计数：4B × (8B id + 8B count) ≈ 64GB。单机内存放得下，但写入扛不住。
  • 核心难点：高写入 + 高基数下的全局排序。
3

核心实体与 API

  • Video、View、Time Window（hour / day / month / all-time）。
  • GET /views/top-k?window={WINDOW}&k={K} → { videoId, views }[]。K 最大 1000，不需要分页。
4

高层设计

View Service ──► Kafka(view-events，按 videoId 分区)
  ──► Flink 预聚合（1min tumbling，按 videoId 求和）
  ──► Aggregator ─┬─► DB 计数（view_hour / view_day / view_month / view_total，RETURNING 新计数）
                  └─► 每个窗口一个 min-heap(K)
  ──► 每分钟写入 Redis（top-k:{window}）──► Top-K Service ──► Client

① 扛写入：Flink 分钟级预聚合

  • 输出：每分钟每个被看过的视频一条记录 (minute_ts, videoId, count)。
  • 700k TPS 降到"每分钟被看过的不同视频数"（热门视频压缩比高，长尾接近 1:1）。
  • 窗口长度 + 允许乱序 ≤ 1 分钟（比如窗口 30s、乱序 20s），或者改用 processing time。

② 写入 DB：表只负责计数

  • 每个窗口一张表，不在 views 上建索引（每次更新都要维护索引，代价太大；排序交给内存中的堆）。
  • 时间列 = 把 minute_ts 截断到这张表的粒度：10:37 的分钟计数累加到 view_hour 的 10:00 那一行。
  • 时间列的作用：已经封口的上一个窗口和正在累加的当前窗口是两行，互不覆盖。
表结构与写入
CREATE TABLE view_hour (
  hour_ts  TIMESTAMP,          -- date_trunc('hour', minute_ts)
  video_id BIGINT,
  views    BIGINT,
  PRIMARY KEY (hour_ts, video_id)
);
-- view_day(day_ts, ...) / view_month(month_ts, ...) 结构相同；view_total 没有时间列

INSERT INTO view_hour VALUES (date_trunc('hour', :minute_ts), :vid, :count)
ON CONFLICT (hour_ts, video_id)
DO UPDATE SET views = view_hour.views + EXCLUDED.views
RETURNING views;             -- 新计数交给堆

③ 聚合：每个窗口一个堆

  • 每个窗口（hour、day、month、all-time）维护一个大小为 K 的 min-heap。
  • 拿到 (window, videoId, newCount) 后：已经在堆里就原地更新（hashmap + 带位置的堆，或者 TreeMap）；不在堆里且大于堆顶就替换堆顶；否则忽略。
  • 为什么精确：tumbling 窗口内计数只增不减，一个视频要进入 top K，必然是因为它被加了一次，而每次加都会经过堆。
  • 窗口切换：整点时冻结上一小时的堆并作为"last hour"发布，新的一小时从空堆开始；day / month 同理，all-time 永不切换。

④ 扛读取：预计算 + 缓存

  • Aggregator 每分钟把每个窗口的 top 1000 写入 Redis top-k:{window}。
  • Top-K Service 读 Redis 后截取前 k 条，不访问 DB，也不做任何计算。
5

深入

热点写：爆款视频（参考 Ad Click Aggregator）

  • 按 videoId 分区，只给热门视频加盐：分区键 videoId:0-N。普通视频保持局部性，不需要 shuffle。
  • Flink 按加盐后的 key 聚合，输出时去掉后缀：同一个视频每分钟得到 N 条部分计数。
  • 在 DB 里合并：views = views + :partial 满足交换律，部分计数按任意顺序写入，结果都正确；RETURNING 的值单调递增，堆照样能正确更新。
  • 识别热点：静态名单（大 V 的新视频、历史播放量高的视频），或者动态检测（播放量超过阈值后发布"热点名单 + N"的配置）。N 在中途变化也没问题，因为 DB 端是累加。
  • 不选"随机分区 + 两阶段聚合"：每个 subtask 都会看到几乎所有视频，还要多一次全量 shuffle，等于让所有视频为少数热点买单。

聚合分片

  • 分片键：hash(videoId) % P（先去掉盐），Aggregator 的分片和 DB 的分片对齐。
  • 分片规模取决于每分钟的活跃视频数，和原始写入流量无关：一个视频一分钟被看 100 万次，也只产生 1 条记录。假设一分钟约 49M 次 view，其中不同的视频有 10–20M 个，折合 170k–330k 条记录/秒，每条更新 4 张表。
  • 全局合并必须保留：每个分片的堆只是本分片的 top K。因为一个视频只属于一个分片，全局 top K 一定在 P×K 个候选里。
合并方式做法问题
Merger 定时合并（选这个）每分钟读取 P 个分片的 top K，合并后写入 top-k:{window}多一个作业，要监控失败和延迟；故障时返回旧值
查询时合并 + 缓存缓存未命中时 MGET P 个 key 并合并，写入缓存，TTL 约 1 分钟过期瞬间大量请求同时去合并（缓存击穿），单次合并 10 万条数据，延迟偏高。加上 single-flight 和后台刷新后，就收敛成了左边的方案

版本对齐：分片按分钟写带版本号的 key top-k:{window}:{minute}:shard:{i}，合并时只取同一分钟的版本。

Sliding 窗口

  • 步长：比窗口低一级的粒度。hour 按 minute 滑动（60 个桶），day 按 hour 滑动（24 个），month 按 day 滑动（30 个）。
  • 计数维护：两个消费者组：一个消费最新数据做 +，另一个滞后一个窗口长度做 −（教程旧版的"两个指针"）。
  • 两个组都消费 Flink 输出的聚合 topic，不消费原始事件：减掉的正是当初加上的那条记录，对称性有保证；需要保留的数据量也远小于原始事件。Kafka 的保留时间 ≥ 最长的窗口。
  • top K 遇到减法会失效：堆里的视频被减下去后，该补位的是一个这一分钟计数没有变化的视频，堆看不到它。
窗口top K 怎么维护理由
hour每个分片一个 ZSET，ZINCRBY 正负增量，计数为 0 时 ZREM只包含近一小时的活跃视频（假设 1 亿量级 × 100B ≈ 10GB），不是 3.6B 全量。结果精确
day / month候选缓冲 K' > K + 定期全量重建；或者保持 tumbling活跃视频可能到十亿级，ZSET 太重。候选缓冲是近似的，要和面试官确认

热点读

  • 所有请求只读 4 个 key，每个 1000 条，每分钟才变化一次。
  • Top-K Service 在进程内缓存，每 5–10s 刷新；Redis 加只读副本；结果对所有用户相同，可以再加 CDN。
  • Merger 先写带版本号的 key，再切换指针。Merger 延迟或故障时返回上一版结果。

近似：Count-Min Sketch（面试官放宽"精确"时才适用）

  • 为什么：精确方案要为每个活跃视频保存一个计数（DB upsert 是写入的大头），而 top K 只关心 heavy hitter。
  • 结构：d × w 个计数器；add 时每一行加一次，estimate 时取 d 行中的最小值。只会多估，误差 ≤ εN 的概率为 1−δ；w = e/ε，d = ln(1/δ)。
  • 估算（hour）：N ≈ 2.9B；取 ε = 10⁻⁶、d = 5，约 1360 万个计数器 ≈ 54MB，误差 ≤ 2900 次 view，对 top 1000 的视频可以忽略。
  • 流程：add(videoId, count) → estimate → 更新大小为 K 的候选结构（低于当前第 K 名就跳过）。
  • 全部放在内存里（Flink state），没有 DB：分片和 Merger 的做法不变；相同 hash 函数的 CMS 可以逐格相加。
  • sliding：只减当初加过的值（复用滞后的消费者组），不能用 conservative update。Redis 没有 CMS.DECRBY，所以不放在 Redis 里。
  • 需要精确数据时：另做一条离线链路 Kafka → S3 → Spark 计算精确计数（lambda 架构）。

容错

对每个有状态的组件回答三个问题：状态在哪、怎么恢复、重放会不会重复计数。Kafka 是可以重放的事实来源。

组件状态挂掉之后防止重复计数
View Service → Kafka无重试，acks=allKafka 幂等 producer
Kafka原始事件 / 聚合 topic3 副本，保留时间 ≥ max(最长窗口, checkpoint 间隔)—
Flink 预聚合部分计数 + offset从 checkpoint 恢复 + 重放用事务写入聚合 topic
Aggregator（DB）DB 计数 + 堆计数不会丢；堆通过扫描本分片当前窗口的数据重建在同一个事务里写 applied(shard, minute)，已处理过就跳过
Aggregator（CMS）CMS + 候选 + offset加载 S3 快照 → seek offset → 重放状态和 offset 写在同一个快照里
Merger / Query Service无 / 进程内缓存重启，期间返回上一版结果Redis 覆盖写（带版本号的 key）
  • 为什么 CMS 方案必须做快照：tumbling hour 只重放一小时的数据还行，month / all-time 要从头重放，太慢。
  • 扩缩容：CMS 不能按 videoId 拆分，所以用固定数量的逻辑分片（比如 128 个），按 shardId 做 keyBy，扩缩容时整片迁移。

要不要 DB：Flink state + 堆 + checkpoint

Kafka ──► Flink 1min 预聚合 ──► keyBy(videoId)：每个窗口的计数存在 keyed state 里
      ──► keyBy(window, shard)：每个窗口一个堆 ──► Merger ──► Redis
checkpoint：计数 state + 堆 + Kafka offset 一起写到 S3
  • 只看 top K 这个功能，OLTP DB 可以去掉：省掉了每分钟"活跃视频数 × 4 张表"的 upsert，这本来是写入成本的大头。
  • 精确计数放不进纯内存：all-time 窗口约 3.6B 个计数，大约几百 GB，要用 RocksDB state backend（等于把 DB 嵌进了 Flink）。CMS 方案只要几十 MB，才是真正的纯内存。
  • 用增量 checkpoint：只上传变化的部分。故障恢复要先下载状态，需要几分钟，这段时间返回上一版结果。
  • 保留一个廉价的兜底数据源：把原始事件归档到 S3 数据湖。Flink 的 bug 写坏了状态，或者升级时状态结构不兼容，checkpoint 都救不回来；这时用 Spark 批量重算，再通过 State Processor API 初始化 Flink 状态。
DB 计数 + 内存堆（主线）Flink state + 堆 + checkpoint
写入成本每分钟 × 4 张表的 upsert只更新本地的 RocksDB
组件Flink + Aggregator + DB只有 Flink（加上 S3）
恢复计数在 DB 里不会丢，只需重建堆下载 checkpoint，再重放一小段数据
兜底DB 本身S3 数据湖 + 批量重算
单个视频的播放量 / 对账直接查 DB离线计算，或者把聚合结果异步写入 OLAP
面试风险低，容易讲清楚要讲清楚 RocksDB、增量 checkpoint、状态迁移（教程认为面试里容易讲偏）

选法：熟悉 Flink 的话，主线可以直接用右边的方案，同时主动说明两点：精确计数要用 RocksDB，兜底靠 S3 数据湖。面试官不希望深入 Flink 时，就退回左边。

面试讲述顺序

  1. 需求与估算：难点是高写入 + 高基数。
  2. 主线：Flink 分钟级聚合 → DB 计数 → 每个窗口一个堆 → Redis。
  3. 深入：热点写 → 聚合分片 → sliding → 热点读 → 近似 → 容错 → 要不要 DB。

和教程当前版本的区别：Hello Interview 的主线是"Postgres 每个窗口一张表，在 views 上建索引 + cron 预计算"，内存聚合（Flink + 堆）只列为"Great，但不推荐在面试里讲"。这份笔记的主线换成了内存堆，DB 只负责计数。
