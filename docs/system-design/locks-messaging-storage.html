PART 1

并发控制与锁

主线　单机行锁 → 悲观 / 乐观两种策略 → 三个底层机制 → 分布式锁 → 教程里锁的实际用法 → 锁只管效率，条件写管正确性。

InnoDB 行锁

  • 锁的是索引记录，不是物理行。WHERE 不走索引等于锁全表。只有 InnoDB 有行锁，MyISAM 只有表锁。
  • 普通 SELECT 是快照读，不加锁；UPDATE / DELETE / SELECT ... FOR UPDATE 是当前读，加 X 锁。
  • 两阶段锁协议：事务提交或回滚时统一释放。把加锁操作放事务最后能缩短持锁时间。
  • RC 只有 Record Lock，死锁少但有幻读；RR 用 Next-Key Lock 防幻读，锁范围大。很多公司线上默认 RC。
  • 排查：performance_schema.data_locks、SHOW ENGINE INNODB STATUS；锁等待默认 50 秒，死锁检测回滚代价小的事务。
类型锁什么目的
Record Lock单条索引记录防止别人改这行
Gap Lock两条记录之间的开区间防止往区间插入，解决幻读
Next-Key LockRecord + 前面的 Gap，左开右闭RR 下的默认加锁单位
Insert Intention Lock插入前在 gap 上打的意向标记多个事务往同一 gap 不同位置插入不互斥

悲观锁 vs 乐观锁

悲观锁 Pessimistic Locking乐观锁 Optimistic Locking (OCC)
实现SELECT ... FOR UPDATE，或直接 UPDATE 隐式加锁UPDATE ... WHERE version = ?，或直接用业务字段 WHERE stock > 0，看 affected rows
时机事前阻塞事后校验
持锁整个事务只有那条 UPDATE 的几毫秒（底层仍用行锁）
适合冲突多、事务短、必须成功：余额扣减、状态机流转冲突少、读多写少、跨请求：后台编辑表单、配置修改
注意命中索引；不持锁做 RPC；固定加锁顺序重试上限；版本号用自增整数防 ABA；多行校验退回悲观

两者本质区别不是"有没有锁"，而是持锁时长和冲突检测时机。高冲突下乐观锁反而更差，999 个失败重试白烧 DB。热点行两者都不行，真正的解法是把冲突挪出 DB。OCC 的 O 是 Optimistic，不是 Optimal。

CAS · MVCC · 2PL

CAS　Compare-And-Swap

  • CPU 原子指令：x86 LOCK cmpxchg，ARM 用 LL/SC 模拟。
  • Java 的 Atomic*、AQS 建在它上面，自旋重试。
  • DB 里就是带条件的 UPDATE，InnoDB 语句内加 X 锁保证原子。
  • 坑：ABA 靠版本号防；高竞争自旋空转，用分段累加（LongAdder、库存分桶）缓解。

MVCC　Multi-Version Concurrency Control

  • 每行隐藏列 DB_TRX_ID、DB_ROLL_PTR，旧版本进 undo log 串成链。
  • Read View 记 m_ids / min / max / creator，沿链找第一个可见版本。
  • RC 每条 SELECT 新建 Read View，RR 整个事务复用第一个。
  • 长事务卡住 purge，undo 膨胀，是线上最常见的危害。

2PL　Two-Phase Locking

  • 规则只有一条：扩张阶段只加锁不放锁，收缩阶段只放锁不加锁。按锁点排序就是等价的串行顺序。
  • 为什么需要：单条操作各自加锁再放锁，会出现读到转账中间态、丢失更新。锁必须跨操作持有。
  • Basic 2PL 有级联回滚；Strict 2PL 把 X 锁持到提交；Rigorous 2PL 所有锁持到提交，InnoDB 用这个。
  • InnoDB 锁管理器：按 (space_id, page_no) 哈希，每页一个位图记哪些记录被锁；死锁用 wait-for graph 找环，回滚代价小的。
  • 三者关系：2PL 是悲观并发控制的理论基础；CAS、MVCC 是乐观路线的两个工具。InnoDB 读走 MVCC，写走 2PL，应用层再用 CAS 式条件 UPDATE 做乐观锁。

分布式锁

  • 三要求：互斥、不死锁（要过期）、不误删（比对 token）。过期和互斥天然矛盾，整个设计史都在这两条之间找平衡。
  • DB 唯一索引：简单，无过期，低频任务用。
  • Redis：SET key token NX PX 30000，Lua 比对 token 再 DEL；Redisson watchdog 续期；主从异步复制会丢锁，Redlock 靠多数派但依赖时钟，Kleppmann 批评过。结论：适合效率型场景，不适合正确性场景。
  • ZooKeeper 临时顺序节点，序号最小者持锁，只 watch 前一个防惊群，会话断了节点自动消失；etcd 用 lease + revision。
  • fencing token：锁服务发单调递增 token，下游拒绝比见过的更小的。本质是把分布式锁降级成乐观锁，锁只减少冲突，正确性靠最后写入的条件校验。
  • 和分布式事务的区别：锁管"谁能进这段代码"，2PC 管"多库要么全成要么全败"，2PC 是 2PL 的分布式延伸。

PART 2

数据流动：通知、消息、认证

主线　DB 落库 + 轮询 → push 降延迟 → 服务器有连接状态需要路由 → 注册表转发或 Pub/Sub → push 会丢，DB 兜底补差。

因果链与两跳框架

数据源 ──第二跳：server 到 server──► 持连接的服务器 ──第一跳：server 到 client──► 客户端
        Redis Pub/Sub / SQS / Kafka                       轮询 / 长轮询 / SSE / WebSocket
  • 第一跳问"等一个结果还是等一个流"。一次性结果、秒级可接受、无扇出用轮询（LeetCode 每秒查判题、上传状态、兜底同步）；持续变化、毫秒级、大扇出用 push（评论、聊天、座位图、司机位置）。轮询在 push 方案里还有一个固定角色：保底。
  • 第二跳问"丢一条要不要紧"和"订阅关系是静态业务维度还是动态用户维度"。
  • 轮询不是一定错。"引入队列会破坏 500ms 延迟约束"，Gopuff 下单、Bitly、抢票都在同步路径上，一个都没用队列。

Redis Pub/Sub 细节

时间线                         pubsub_channels 字典内容
───────────────────────────────────────────────────────────
Redis 启动                      {}                         ← 没有任何 channel
S1: PUBLISH user:B "hi"         {}                         ← 合法，返回 0，消息丢弃
S2: SUBSCRIBE user:B            {"user:B": [conn_S2]}      ← channel 此刻"诞生"
S1: PUBLISH user:B "hi"         {"user:B": [conn_S2]}      ← 返回 1，S2 收到
S3 断线 / 最后一个退订           {}                         ← channel 消失
  • channel 只是字典 key，不需要创建；发布者和订阅者都是 Redis 客户端。PUBSUB CHANNELS / NUMSUB 能看实时内容。
  • PUBLISH 查字典，把消息写进每个订阅连接的输出缓冲区，返回订阅者数；返回 0 可当作"对方离线"的信号。
  • 拓扑：单机；主从（PUBLISH 随复制流传播，订阅可连副本）；Cluster 普通模式全集群广播，每次 N-1 条 bus 消息；Redis 7 sharded（SSUBSCRIBE / SPUBLISH）按 slot 路由，订阅方必须连对节点。
  • 订阅端套路：专用连接进入订阅模式；断线后重新 SUBSCRIBE 全部本地用户，并让客户端从 DB 拉一次增量。
  • Redis 三种消息原语：List（LPUSH/BRPOP，简单队列，无 ack）、Pub/Sub（广播，不存）、Streams（XADD/XREADGROUP/XACK，Kafka 式日志，有消费组和 pending list）。

Pub/Sub 还是 Kafka：本质

Pub/Sub 传的是提示："有新东西，去看"。Kafka 传的是带位置的记录。关键区别是订阅方丢了一条之后，能不能靠自己知道丢了什么、去哪补。

维度WhatsApp / Live CommentsAd Click
消费者人，通过一条连接机器，一个聚合任务
丢一条延迟，人会重连或刷新计费数字错，且 Flink 自己不知道
游标客户端 lastSeenId、Inbox 行没有，只有一个越来越不准的累加值
不在线时本来就送不到，上线再补Flink 重启那 30 秒的点击必须留着
订阅关系十亿动态频道，每条给一两个一个静态 topic，每条给同一组
重放不需要，DB 就是历史需要，修 bug 重算昨天
  • 三个判断：消费者输出是"展示最新状态"还是"全部事件的函数"；消费者自己有游标吗；真相源支持"从游标顺序读"吗。任一为否就需要 Kafka。
  • Ad Click 存 Cassandra 再 Pub/Sub 不行：Cassandra 按 (ad_id, 小时桶) 分区，没有"按时间全局顺序读"，Flink 补不回来；手工建一张按时间追加的表就是重新发明 Kafka。存 DynamoDB 用 DynamoDB Streams 可以，因为 Streams 就是 log。
  • WhatsApp 不用 Kafka：不是不可靠，是它的持久化和 Inbox 表重复了，而 topic 开销和 rebalance 是实打实的代价。

案例

WhatsApp

  • 六张表：Chat、ChatParticipant（含 GSI）、Message（按 chatId，存内容，TTL 30 天）、Inbox（按 clientId，存"还欠哪条"，ack 即删）、Client（多设备）、LastSeen（只在断线时条件写）。
  • 发送顺序：查成员展开设备 → 写 Message 1 行 + Inbox 每设备 1 行 → 回发送方 → PUBLISH user:{id} → 对方 server 查本地 map 推 WebSocket → ack → DELETE Inbox。
  • 登录：认证 → 本地 map → 先 SUBSCRIBE 再拉 Inbox，两边不留缝。离线时 PUBLISH 返回 0，走系统推送。
  • 每用户一 Kafka topic 标 Bad（50KB × 10 亿）；一致性哈希 + ZK 是 Good（服务器要互连）；Redis Pub/Sub 是 Great。按用户分频道而不按会话分，因为一个用户约 250 个会话。
  • 服务器不是无状态，它持有临时可重建的连接状态；Pub/Sub 解决的是让服务器不需要知道彼此。心跳 10 到 30 秒，序号检测漏消息，NTP 时间戳排序。

Live Comments

  • SSE 单向推送，发评论走 POST。naive 全订阅 → hash(videoId) % N 分频道 + 一致性哈希把同一直播的观众聚到同一台 server。Dispatcher 服务是替代方案。
  • Kafka 扛不住观众切直播的动态订阅；丢了刷新从 DB 读，连 Inbox 都不要。一致性哈希是优化，Pub/Sub 是正确性，扩缩容时新旧两台都订阅即可。
  • 重连和翻页走独立 GET，游标分页；SSE 自带 Last-Event-ID 可在同一连接先补差再推实时。

其他

  • Ticketmaster 虚拟排队用 Redis sorted set，放行的进带 TTL 的 admitted:{eventId}。
  • Uber：叫车进 Kafka/SQS 按区域分区，匹配成功后才 commit offset；司机超时用 SQS delay queue 或 Temporal 持久化工作流。
  • LeetCode：SQS 削峰，容器崩了自动重试，客户端每秒轮询，WebSocket 是过度设计。News Feed：SQS fan-out-on-write，大 V 打标记读时合并。
  • Web Crawler 明确选 SQS 不选 Kafka：内建退避、DLQ、托管；抓取和解析拆两个队列。YouTube：S3 CompleteMultipartUpload 事件 exactly-once 触发 Temporal DAG。
  • Slack：Redis 队列被积压塞满连出队都失败，前面加 Kafka 做持久缓冲，relay 落到 Redis 后才 commit offset。教训：积压存储不能放有界内存。

ZooKeeper / etcd

  • 本质是小容量、强一致、支持 watch 的 KV，存集群元数据。所有用法从这三个特性推出来。
  • 用法：服务注册发现（临时节点）、leader 选举（临时顺序节点）、分布式锁、配置与开关、分片归属（Kafka KRaft 之前、HBase）、成员列表（一致性哈希环的输入）。
  • 红线：不在数据路径上。存"有哪些服务器"，不存"用户 B 在哪台"，后者由哈希函数算或由 Pub/Sub 订阅表隐式维护。
  • 一致性哈希在 L7 LB 做，按 URL 里的 videoId 算；它把路由状态压缩成"成员列表 + 确定性函数"，和 dispatcher 的"每观众一条记录、每秒几十万次写"是两个量级。

JWT 七步递进

  1. 直接带 user=lee → 谁都能改。
  2. 加签名 header.payload.signature，payload 明文只防篡改不防偷看。到这 JWT 已完整：验证不查库。
  3. 加 exp，15 分钟。
  4. 加 refresh token：随机串、存哈希、30 天，只在换 access 时用一次，放 HttpOnly cookie。
  5. 登出：删 refresh 断续期；要立刻生效就 jti 进 Redis 黑名单。
  6. RS256 私签公验，kid + JWKS 轮换，公钥泄露无害。
  7. 防攻击：算法白名单防 alg:none 和混淆；HTTPS；SameSite；refresh rotation + 重放检测，同一 refresh 第二次使用即吊销整条链。
  • Gateway 统一鉴权后内部传 X-User-Id 是标准做法，与 session/JWT 无关。前提是内网可信、所有入口经 Gateway。长连接、异步任务、服务间自发调用三种情况 Gateway 管不到。Gateway 做认证，服务做授权。
  • HMAC 签名的 impression ID：投放服务签 imp_id | ad_id | exp，点击时验签失败照跳转不计数，SET imp_id NX EX 原子去重，先写 Kafka 再写缓存宁重不丢。用 HMAC 不用非对称：签验同方、每秒万次、签名要进 URL。签名答"是不是我发的"，去重答"是不是第一次"，反作弊答"点的人是不是真的"。
PART 3

数据存放与计算

主线　LSM 为写优化 → 四个坐标轴定位需求 → 真实系统是温度链，每层丢了从下一层重建 → 热点散点再合并 → Flink 算增量、Spark 算全量、OLAP 存结果 → Lambda 两套互校，Kappa 一套重放。

LSM 树　Log-Structured Merge-tree

写入 → ① 追加 WAL → ② memtable（内存有序）→ 满了 ③ 顺序刷成不可变 SSTable
                                                  → ④ 后台 compaction 合并、去重、清 tombstone
读取 → memtable → L0 → L1 → ...（每个文件先看 bloom filter）→ 第一个匹配即返回
B 树（MySQL、Postgres）LSM（Cassandra、RocksDB、HBase）
写随机 IO，找到页改页顺序追加，极快
点读一次树遍历，稳定可能查多个文件，靠 bloom filter
范围扫描叶子有序链表，快多文件归并，慢一些
后台开销几乎没有compaction 持续吃 IO，延迟抖动
事务行锁、MVCC 成熟单行原子，跨行弱
compaction—Size-tiered 写放大低读放大高（Cassandra）；Leveled 反之（RocksDB）

Cassandra 的 counter 类型最终一致且不幂等，超时重试可能多加，计费场景不能用。所以 Ad Click 存原始事件再聚合，而不是直接 +1。

Flink · Spark · OLAP · Lambda / Kappa

Spark（批）Flink（流）
输入有边界，一天的文件无边界，Kafka 持续来
生命周期跑完退出常驻 7×24
处理整个数据集分 stage，shuffle 最贵逐条流过算子，keyBy 状态
时间数据里有时间列自己 groupByevent time、watermark、窗口是一等公民
容错task 失败重跑checkpoint barrier 快照 + Kafka offset 重放，exactly-once
在 Ad ClickGood 方案定时聚合、Great 方案每日对账Great 方案一分钟窗口
  • watermark："时间戳 ≤ W 的事件我认为都到了"，常取最大事件时间减容忍度；越过窗口边界就关窗刷结果；更迟的靠 allowedLateness 或对账。
  • 状态大小决定容错策略：Ad Click 一分钟窗口状态小，教程说 checkpoint 可不开，重放即可；Top-K 一个月滑动窗口必须开，Kafka 也要留一个月。
  • OLAP 列式只读需要的列、高压缩、向量化，扫十亿行秒级；写要批量、点查慢。按查询过滤维度分片（advertiser_id），多粒度预聚合（分钟 → 天 → 周）。
  • Lambda：流快可能错、批慢但准，两套代码互相校验，服务层合并。Kappa：一套流代码，正确性靠引擎 exactly-once，需要时从 offset 0 重放到新表再切换。不是"两遍"，重算按需。

Ad Click Aggregator 全链路

用户点击  GET /click?imp=…&ad=42&exp=…&kid=k3&sig=…      ← 302 服务端跳转，与 Bitly 同构，必须 302 不能 301
   ▼
Click Processor（无状态）  验 HMAC → SET imp NX 去重 → 写 Kafka → 302
   ▼
Kafka（按 ad_id 分区，热广告加盐 ad_id:0..N，retention 7 天）
   ├──► Flink：去盐，一分钟 event-time 窗口，watermark 30 秒 ──► OLAP（按 advertiser_id 分片，日/周表预聚合）
   └──► Kafka Connect ──► S3 原始事件 ──► 每日 Spark 重算 ──► 对账修正 OLAP
  • Bad：写 DB 查时 GROUP BY。Good：Cassandra 原始事件 + 每 N 分钟 Spark + OLAP。Great：Kafka + Flink + OLAP，Cassandra 被 Kafka retention 取代。
  • 去重按 impression 不按用户：重定向广告同一用户多次看到都是真实点击。先写 Kafka 再写缓存，重复有对账兜、丢失没有。
  • Kafka 之外的替代：DynamoDB Streams / Cassandra CDC 是 log 形状，可以；Cassandra + Pub/Sub 不行。

贯穿全部的原则

01

先写不可逆的真相，再做可失败的加速

Inbox 再 PUBLISH，Kafka 再缓存，Message 再推送。加速层丢了只损失延迟。

02

锁负责效率，条件写负责正确性

Redis 锁挡掉大部分冲突，UPDATE ... WHERE status = ? 保证最后只有一个成功。fencing token 和乐观锁是同一个思想。

03

游标决定能不能用 best effort

消费者自己知道看到哪了、真相源能从那里顺序读，就可以用 at-most-once 的通道。否则要 Kafka。

04

把一个点的压力散成多个点

写加盐再合并，读复制多份，库存拆行，观众按直播聚合。合并的成本放到异步环节。

05

每一层都要回答"丢了从哪恢复"

热层从冷层重建，流从批修正或从日志重放，Pub/Sub 从 DB 补差。

06

付了什么代价要说得出来

默认站中间，需求推你才移动。用 NoSQL、用队列、用锁，都要能说出不用的话哪里撑不住。
